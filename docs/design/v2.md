## 0. 相对 v1 的变更

```yaml
变更:
  A_上下文升级:
    v1: 数据通道 (AppInfo + Get/Set)
    v2: 唯一能力来源 (数据 lookup + 能力 resolve), 服务/引擎经 root ctx 调用下层
  B_事件总线:
    v1: 仅作为 ctx.Emitter() 挂载点
    v2: 作为一个 engine 实现, 并进入启动优先级序列
  C_配置语义:
    v1: 含糊的 "AppInfo", ctx.App()
    v2: 拆分为 config(启动时固定) 与 settings(运行时动态), 统一 key lookup
  D_命名:
    v1: web engine
    v2: window engine (对齐目录 engine/window)
继承 v1:
  - 应用信息统一由 config 引擎加载 (唯一事实来源)
  - window 也是 engine, 统一注册与生命周期
  - 分层 domain / engine / service / api, domain 之间互不依赖
```

## 1. 核心观点 (v2)

### 观点 A — 上下文是唯一引擎调用来源 (自上而下)

- root context 是**所有引擎能力的唯一注册与解析中心**: 引擎在启动时把能力 (句柄) `Provide` 进 ctx; 上层通过 `Resolve` 取用.
- 调用是**自上而下**的: `api → service → engine → engine`, 每一层都只面对 ctx, 不 import 下层的具体实现.
- 直接收益: **service 层不 import engine 层**, 甚至感知不到 engine 层存在 (只依赖 domain 能力接口 + ctx 解析).

```
api(window binding)  --Resolve service-->  ctx
service              --Resolve capability--> ctx
engine               --Resolve peer/下层-->  ctx
```

- 反向 (下层通知上层) 不走 Resolve, 走**事件总线** (观点 B). 形成清晰原则:
  - **调用向下**: `ctx.Resolve(capKey)`
  - **通知向上**: `event bus`

### 观点 B — 事件总线即引擎

- 事件总线以 **engine** 形式实现, 同样 `Provide` 到 ctx, 同样纳入生命周期与优先级.
- 关键: **启动优先级**必须前置. 因为后续引擎/服务在各自的 `Start` 阶段就可能需要 `On/Emit` (订阅配置变更、广播自身就绪等), 总线必须先就绪.
- 总线自身参数 (缓冲、是否异步、重试) 可能来自 config, 故总线**不能早于 config**.

### 观点 C — config 与 settings 分离 + 统一 key lookup

- config 与 settings 是两类不同语义的状态, 不能混为一谈:

| 维度 | config | settings |
|---|---|---|
| 时机 | 启动时固定加载 | 运行时动态变化 |
| 可变性 | 只读快照 | 可读写 |
| 来源 | `data/conf/*.json` (embed + 外部覆盖) | 用户操作 / 运行时决策 |
| 变更通知 | 无 | 经事件总线广播 |
| 持久化 | 随包/文件 | 需运行时回写 |
| 定位 | 程序自身的控制状态 | 运行时的控制状态 |

- **统一 lookup**: 不应出现 `ctx.App()` 这类专用取值方法; 而应统一为 `lookup(key)`, 由 ctx 对 config / settings 做统一寻址 (settings 覆盖 config), 调用方只认 key.
- 这同时呼应观点 A: 键空间统一后, 数据 (`Value`) 与能力 (`Resolve`) 共用同一套 `Key` 机制.

## 2. 程序启动链路 (更新)

### 2.1 目标链路

```yaml
阶段:
  1_引导(bootstrap):
    动作: 创建 root ctx (含空 resolver 与统一 lookup), 判定模式
    产物: ctx(根) —— 未来的唯一能力来源
  2_引擎(tiers, 按优先级):
    动作: 逐层 Init -> Start; 每个引擎 Start 时 Provide 能力/值到 ctx
      - config  : 加载 data/conf/*.json, Provide 静态值 (含应用元信息/窗口参数)
      - eventbus: Provide 总线能力 (先于一切需订阅者)
      - settings: 初始值取自 config, 变更经 eventbus 广播
      - domain  : 领域能力 (browser/agent/...)
      - window  : 最后启动, 依赖全部就绪
    产物: 引擎就绪 + ctx 已 Provide 全部能力
  3_编排(service):
    动作: 组装 service; service 不持有引擎实例, 运行时从 ctx Resolve
    产物: service 实例 (可同样 Provide 进 ctx 供 api 解析)
  4_暴露(api):
    动作: 按形态暴露 (web 绑定 / cli 命令)
  5_运行(run):
    动作: window engine Run() 阻塞 / cli 执行后退出
  6_退出(shutdown):
    动作: cancel 根 ctx -> 逆序 Stop (按 tier 逆序)
```

### 2.2 时序 (desktop, 强调"唯一来源")

```
main
 └─ bootstrap               建 root ctx (空 resolver)
     └─ registry.Start(ctx)  按 tier 正序
         ├─[P0] config    : Provide app.*/window.* 等静态值
         ├─[P1] eventbus  : Provide bus; 后续者即可 On/Emit
         ├─[P2] settings  : 建运行态, 订阅/广播经 bus
         ├─[P3] browser.. : Provide 领域能力
         └─[P4] window    : Resolve 所需能力/值, 建 wails 应用 + 窗口
     └─ service.Assemble     service 只依赖 domain + ctx (不 import engine)
     └─ api.Expose           api/web 绑定; 方法内 Resolve service
     └─ window.Run           app.Run() 阻塞
     └─ shutdown             ctx.Cancel() -> 逆序 Stop
```

### 2.3 启动优先级 (新增, 回应观点 B)

```yaml
tiers:
  P0_config:    [config]                 # 最高: 唯一配置来源, 框架自身硬依赖
  P1_platform:  [eventbus, log]          # 平台设施: 供后续一切订阅/通知, 必须尽早
  P2_state:     [settings]               # 运行态: 依赖 eventbus 广播, 初值取自 config
  P3_domain:    [browser, agent, ...]    # 领域能力: 提供业务 capability
  P4_present:   [window]                 # 表现层: 最后启动, 依赖全部就绪

规则:
  start_order: tier 正序, 同 tier 按注册序
  stop_order: tier 逆序 (P4 -> P0)
  rationale:
    - config 最先: 其它引擎可能读配置; 且是框架基础
    - eventbus 次之: 后续引擎在各自 Start 中就需订阅/发布
    - settings 再次: 变更需经 eventbus 广播
    - window 最后: 消费者, 不产出被依赖能力
```

> 说明: v1 用"注册顺序即依赖序". v2 引入 **tier** 使顺序自解释、可校验 (启动期可断言"高 tier 不依赖低 tier 未就绪能力"). 是否落成 `Tier()` 方法见 3.1.

### 2.4 阶段职责边界

```yaml
bootstrap: 只建 ctx 与判定模式, 不碰业务
config:    只读配置 -> Provide 静态值, 不消费
eventbus:  只做 pub/sub, 不做业务路由
settings:  只管运行态读写 + 变更广播, 不解释业务含义
registry:  只管 tier 排序 + 启动/回滚, 不理解引擎语义
service:   只编排, 经 ctx Resolve 能力, 不 import engine
api:       只做形态适配, 不做业务决策
```

## 3. 引擎 + Service 编排 (更新)

### 3.1 Engine 契约

```go
// 示意 (非实现)
type Engine interface {
    Name() string
    Tier() Tier                       // 启动优先级 (新增)
    Requires() []Key                  // 声明依赖的能力/值 key (新增, 用于启动期校验)
    Init(ctx context.Context) error
    Start(ctx context.Context) error  // 在 Start 内 Provide 自身能力到 ctx
    Stop(ctx context.Context) error
}
```

设计要点:
- `Tier()` 让优先级**显式声明**于引擎自身, 而非散落在注册处 (对齐 spec "显式优于隐式").
- `Requires()` 把"服务定位"的隐式依赖重新**显式化**: Registry 在 `Start` 前校验所需 key 是否已就绪, 缺失即 **fail-fast**, 避免运行期才发现 (见 5.2).

### 3.2 Registry: 排序 + 回滚

```go
// 示意
type Registry interface {
    Register(e Engine)
    Start(ctx context.Context) error  // 按 tier 正序: 校验 Requires -> Init -> Start
    Stop(ctx context.Context) error   // tier 逆序 Stop
}
```

规则:
- **显式清单**: 引擎列表仍写死在 bootstrap 一处, 可读全貌.
- **顺序由 tier 决定**: config → eventbus → settings → domain → window.
- **失败回滚**: 任一失败 → 逆序 Stop 已启动者; 未启动者不动.

### 3.3 能力注册与解析 (核心新增)

```go
// 示意 — 单一的 Key 机制, 两种语义
// 数据 (config/settings 统一 lookup)
func Value[T any](ctx context.Context, k Key[T]) (T, bool)
func Set[T any](ctx context.Context, k Key[T], v T) error   // 仅 settings 可变分支
// 能力 (引擎句柄)
func Provide[T any](ctx context.Context, k Key[T], v T)     // 引擎启动时注入
func Resolve[T any](ctx context.Context, k Key[T]) (T, bool) // 上层取用
```

- 引擎在 `Start` 内 `Provide`, 上层在调用时 `Resolve`.
- **同一个 `Key[T]` 类型**同时服务数据与能力 → 真"统一 key" (回应观点 C).
- 键空间需分区避免碰撞 (见 4.3).

### 3.4 Service 编排 (关键变化)

```go
// 示意 — service 只 import domain, 不 import engine
package explore

import "backend/domain/browser"   // 能力接口 + Key, 不是 engine

func (s *Explore) Run(ctx context.Context) error {
    b, ok := browser.Resolve(ctx)   // 从 ctx 取, 感知不到 engine/browser 的存在
    if !ok { return browser.ErrUnavailable }
    ...
}
```

- 对比 v1: v1 是"bootstrap 建好引擎 → 注入 service 构造"; v2 是"service 运行时从 ctx Resolve".
- 结果: **service 与 engine 解耦**, 甚至无需知道其存在; 换/加引擎不影响 service 代码.
- service 自身可 `Provide` 进 ctx, 供 api 以同样方式解析 (保持全链路一致).

### 3.5 API 暴露

- **api/window**: 作为 wails `application.Service` 注册; 方法内 `Resolve` service 能力 → 调用. 只做入参适配 + 结果整形.
- **api/cli**: 命令表, 暴露完整执行接口:
  - `automan window` → 同一 bootstrap, 触发 window engine 建窗并 Run.
  - `automan run <task>` → 走 service 编排, headless (server 模式).
- 两者共用同一启动链路, 差异仅在 bootstrap 模式判定与最终暴露形态.

### 3.6 window 作为 engine

```yaml
window_engine:   # 对齐 xengine/window
  职责:
    - 持有 wails application 实例
    - 从 ctx lookup 应用元信息/窗口参数 (不再硬编码)
    - 注册 wails Services (来自 api/window)
    - Start: 建窗; Run: 阻塞; Stop: 优雅退出
  读取方式: ctx value lookup(key), 而非 ctx.App()
  模式:
    desktop: 建窗 + Run 阻塞
    server : 仅 HTTP/资源服务, headless
```

## 4. domain 设计 (更新)

### 4.1 分层与依赖方向

```yaml
domain:
  context : 根基础 —— Context/Key/lookup/resolve/lifecycle/events/meta
  config  : 静态配置能力 (启动时固定), 实现 context 的 Provider
  settings: 运行态能力 (动态可变), 实现 context 的 Provider + 变更通知
  event   : 事件总线能力 (emit/on)
  engine  : Engine/Registry 契约
  <domain>: 业务领域能力 (browser/agent/..., 后续展开)
依赖:
  - context 为根, config/settings/event/engine 依赖 context (基础 -> 能力)
  - 业务领域之间互不依赖, 只使用 context (Key 解耦)
  - domain 不 import engine/service/api
```

> v1 的 "domain 之间互不依赖" 在 v2 修正为: **业务领域之间互不依赖**; 框架领域 (context/config/settings/event/engine) 以 context 为根形成单向基础层. 这既避免循环, 又让统一 Key/lookup 有落点.

### 4.2 Context 契约

```go
// 示意 (非实现) — 窄接口聚合, 遵循接口隔离
type Context interface {
    lifecycle   // Done() <-chan struct{}; Err() error; Cancel()
    values      // value(k) (any,bool); set(k,v); lookup 统一 config/settings
    capabilities// provide(k,v); resolve(k) (any,bool)
    events      // emit(topic,p); on(topic,fn) unsubscribe
    meta        // Mode() Mode; Logger()
}
```

> 注意 (Go 约束): 接口**不支持泛型方法**, 故 `Lookup[T]` 不能作为方法. 统一用**自由函数** `Value[T]/Resolve[T]` 包裹非泛型的内部 `value/resolve`, 既保类型安全又满足语言限制.

设计意图:
- **唯一来源**: 数据与能力都从 ctx 出 → 上层不改签名即可拿到新依赖.
- **向下调用**: `Resolve` 是自上而下的能力获取.
- **向上通知**: 经 events, 不反向 Resolve.

### 4.3 统一 Key

```go
// 示意
type Key[T any] struct{ name string }

func NewKey[T any](name string) Key[T]

// 键空间分区 (避免数据与能力/不同层碰撞)
//   app.*     应用元信息        (config)
//   window.*  窗口参数          (config)
//   ui.*      运行期界面状态    (settings)
//   cap.*     能力句柄          (engine Provide, 上层 Resolve)
```

- 类型安全 (`Value[AppInfo]` 编译期校验) + 领域零 import.
- 新增数据/能力 = 新增 Key, **零改既有函数签名**.

### 4.4 config vs settings (重点)

```yaml
config:
  接口: Lookup(k) (any,bool)    # 只读
  加载: data/conf/*.json (embed) + 外部覆盖 (外部 > 内嵌)
  时机: 启动期一次性快照, 之后只读
  失败: 必需项缺失 -> 终止启动 (无兜底默认值)

settings:
  接口: Lookup(k); Set(k,v); Watch(k, fn)   # 读写 + 变更
  初值: 取自 config (config 为其默认层)
  变更: Set 后经 eventbus 广播 topic (如 "settings.changed")
  持久化: 需回写 (step 后续, domain/storage)

统一寻找(lookup)层叠:
  settings -> config -> (无)     # settings 覆盖 config, 调用方只认 key
```

- ctx 提供**统一 lookup**: 先查 settings, 命中则返回; 否则回落 config. 调用方无需区分来源.
- 需要严格区分时提供显式入口 (`ctx.Settings()` 用于写入/订阅), 读取仍走统一 key.

### 4.5 event domain

```yaml
event_bus:
  能力: Emit(topic, payload); On(topic, handler) -> unsubscribe
  形态: 作为 engine (P1) Provide 进 ctx
  语义: 异步投递 / 有序 / 背压 策略需明确定义 (见 5.3)
  用途:
    - settings 变更广播
    - 引擎就绪/失败等生命周期事件
    - 跨引擎解耦通知 (不引入相互 import)
```

### 4.6 domain 清单 (step1 框架)

```yaml
先定(框架):
  - context : Context / Key / Provider / 统一 lookup
  - config  : Config 契约 + Loader
  - settings: Settings 契约 (lookup/set/watch)
  - event   : Bus 契约
  - engine  : Engine / Registry / Tier
后定(step 后续, 占位不实现):
  - browser / agent / storage / notify ...
```

## 5. 考虑要点

### 5.1 依赖与循环
- 服务定位的最大风险是**隐式**. 用三招显式化 (对齐 spec "显式优于隐式"):
  1. Key 在 domain 静态声明 (编译期可见).
  2. bootstrap 引擎清单显式列出 (全貌可见).
  3. Engine `Requires()` + Registry 启动期校验 (缺失即 fail-fast).
- context 作为根基础, 打破 `service -> engine` 的直接依赖.

### 5.2 服务定位的显隐权衡 (新增)
- 优点: 解耦彻底, service 不感知 engine; 加/换引擎零改动.
- 代价: 依赖关系从"构造注入"变为"运行期解析", 可读性下降.
- 折中: 只对**能力句柄**用 Resolve; 对**必需数据**用 `Requires()` 声明 + 启动校验; 运行期解析结果可缓存于 service 字段 (Start 后不再反复查).

### 5.3 事件总线 (新增)
- 优先级: 必须在 P1 (见 2.3), 否则后续引擎 Start 无法订阅.
- 语义需明确: 同步 or 异步投递; 顺序保证; 慢订阅者背压; 错误是否影响发布者; handler 的 ctx 生命周期.
- 事件 topic 用常量集中声明 (避免字符串散落, 对齐 spec "业务 string 无硬编码").

### 5.4 config / settings
- config 加载优先级显式定义: **外部文件 > 内嵌 embed**.
- settings 需定义: 校验规则、默认层叠 (settings→config)、持久化时机、并发写.
- 二者共用同一 Key 类型但**键空间分区** (4.3), 避免语义混淆.

### 5.5 生命周期与失败回滚
- 顺序: tier 正序 `校验 Requires → Init → Start`; 停机 tier 逆序 `Stop`.
- 半启动: 任一失败 → 逆序回滚已启动者; 未启动者不动.
- ctx 是停机唯一信号: 根 ctx cancel → 各引擎 (含 eventbus) 响应并停投递.

### 5.6 并发与一致性
- ctx 的 resolver: 启动期单线程写入, 运行期只读 → 读多写少, 用 RWMutex 或"启动后冻结".
- settings 运行期可写 + 并发读: 需原子/加锁 + 变更广播按序.
- 事件回调不得阻塞启动链路.

### 5.7 运行模式
- 一进程一模式: `desktop`(建窗阻塞) / `server`(headless) / `cli`(执行即退).
- 模式在 bootstrap 判定一次写入 ctx; 引擎据 `Mode()` 决策, 而非各自判环境.
- 对齐 `Taskfile.yml` 的 `run` / `run:server`.

### 5.8 观测与错误
- 日志: 统一从 ctx 取 logger (可作 P1 平台引擎), 带应用名/版本.
- 错误: 引擎启动错误冒泡到 bootstrap, 统一格式化 (含引擎名/tier), 便于定位.
- 事件与能力解析失败需可观测 (计数/日志), 避免静默.

### 5.9 待澄清项
- `go.mod` 模块名仍为占位 `changeme` (影响绑定路径 `frontend/bindings/changeme` 与 import), 是否改名 `automan`?
- 非业务常量 (窗口默认宽高/背景色) 入 config 还是保留代码常量? (spec: 非业务 string 不过度配置)
- `Requires()` 是否必要, 还是仅靠 tier + 文档约定? (fail-fast 收益 vs 契约复杂度)
- 事件总线用自研最简实现, 还是引入成熟库? (注意 spec: 运行期不引入 npm 包, Go 依赖需先询问)

## 6. 接入其他组件 (更新)

```yaml
wails_v3:
  接入点: window engine + api/window
  方式: application.New(Options) 的值经 ctx lookup 获取; Service 用 application.NewService 注册
事件总线:
  接入点: engine/eventbus (P1) + domain/event
  方式: Provide 总线能力进 ctx; 引擎/服务 On/Emit (通知向上)
日志:
  接入点: engine/log (P1) 或 ctx meta
  方式: 统一格式与级别, 贯穿启动链路与事件
配置:
  接入点: engine/config (P0) + domain/config
  方式: 读 data/conf/*.json -> Provide 静态值; 统一 lookup 的底层
运行态:
  接入点: engine/settings (P2) + domain/settings
  方式: 运行时读写 + 经 eventbus 广播变更
持久化:
  接入点: domain/storage (step 后续)
  方式: data/<domain>/ 存放领域数据 (对齐 spec l3)
前端:
  接入点: frontend + 生成的 bindings
  方式: 只依赖 api/window 暴露的方法签名
CLI:
  接入点: api/cli
  方式: 复用同一 bootstrap, 暴露 window/run 等完整执行接口
```
