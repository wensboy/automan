# Automan 设计 v11 · bridge/ipc 重构 (ipc ≈ tcp, 桥接引擎 ≈ http)

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v8.md`(bridge 层) + `v9`(桥接引擎) + `v10`(三权边界) + **当前实现实测**
> 范围: `internal/ipc` 的职责收窄为**纯传输**; 负载解析、握手协议、消息分派全部上移.
> 目标: 明确两层的契约、边界与迁移映射. 非编码任务.

---

## 0. 定位与边界

```yaml
ipc 层 (类比 tcp/传输核心):
  职责:
    - peer 连接构建: 被动连接 (Listen/Accept) 与主动连接 (Dial)
    - 消息收发: 连接建立后投递与接收消息
    - 消息解析: 只解析"信封" (序列标识/类别/名称/负载), 不做负载解析
  不做:
    - 不解析负载 (负载是字节, 由上层解释)
    - 不关心消息被如何处理 (没有处理器/分派/回调)
    - 不含任何业务字段 (消息结构只有传输字段)
桥接引擎 (类比 http/应用协议):
    - 握手, 1:1 请求-应答, cmd 分派 (v9)
    - 负载编解码 (json 等)
```

---

## 1. 核心观点

### 观点 A — ipc 只依赖"信封", 不依赖"负载"

- ipc 需要知道如何把 `Message` 变成字节 (帧), **不需要**知道 `Payload` 里面是什么。
- 因此 `Codec` 一分为二: 传输用的 **`Framing`**(信封) 与协议用的 **`Codec`**(负载)。

### 观点 B — 消息结构只放传输字段

```go
type Message struct {
    ID      string // 序列标识 (配对唯一依据)
    Kind    Kind   // 类别
    Name    string // 名称 (分派键)
    Payload []byte // 负载 (ipc 不解释)
}
```

- 字段语义全部是"传输"的; 任何业务/协议字段 (如 daemon/codec/version/token)**只能出现在负载里**, 不能成为消息字段。

### 观点 C — 消息解析 ≠ 负载解析

```yaml
Framing (ipc):      Message  <-> []byte        # 信封编解码, 传输自用
Codec   (协议层):   any      <-> []byte        # 负载编解码, 引擎使用
现状问题: domain/bridge.Codec 把两者混在一个接口里 (Encode/Decode + EncodePayload/DecodePayload)
```

### 观点 D — peer 惰性构建, socket 风格

- `New` 只构造**抽象对象**, 不启动任何东西; `Listen`/`Dial` 才启动内部循环 (accept 循环 / 连接建立)。
- peer 像 socket: 阻塞读、写、关闭、地址; 不承载"处理器"概念。
- socket 通过有效的网络协议簇和ip和端口创建抽象对象, 项目中的 peer 通过 uds 的相对路径创建抽象结构.

### 观点 E — New 统一 func option

- `ipc.New(ipc.WithPath(...), ipc.WithFraming(...), ...)`, 不再用 `Config` 结构体 (除明确指定的场景)。

## 2. 消息模型 (传输字段)

```go
type Kind string

const (
    KindRequest  Kind = "request"
    KindResponse Kind = "response"
    KindEvent    Kind = "event"
    KindError    Kind = "error"
    KindStream   Kind = "stream"
)

// notice: 如果这里 kind 和 name 被认定为 ipc 无效字段, 下沉到payload
type Message struct {
    ID      string
    Kind    Kind
    Name    string
    Payload []byte
}
```

```yaml
边界澄清 (什么算"传输字段"):
  ID   : 传输层的配对标识 —— 传输不解释其取值, 只保证原样透传
  Kind : 类别枚举 —— 传输不解释语义 (request/event 对 ipc 无区别)
  Name : 名称 —— 传输不解释, 只当作字符串 (协议层用它做分派)
  Payload: 字节 —— 传输不解析
  # 因此: 业务/协议字段只能进 Payload (例如握手载荷 Handshake{daemon,codec,version,token})
```

## 3. 契约分层

| 契约 | 层次 | 归属 | 说明 |
|---|---|---|---|
| `Message` / `Kind` | 传输 | `domain/bridge` | 只有传输字段 |
| `Framing` | 传输 | `domain/bridge` | 信封编解码 (`Name/Encode/Decode`) |
| `Peer` | 传输 | `domain/bridge` | socket 风格连接 |
| `Listener` / `Dialer` | 传输 | `domain/bridge` | 被动/主动连接 |
| `Transport` | 传输 | `domain/bridge` | 传输门面 (原 `Bridge` 改名) |
| `Codec` | 协议 | `domain/bridge` | 负载编解码 (`Name/Encode/Decode`) |
| `Handshake` / `HandshakeResult` / `ProtocolVersion` / `NameHandshake` | 协议 | `domain/bridge` | 握手**载荷**类型与常量 |
| `Caller` / `Dispatcher` / `HandleFunc` / `Result` / `Stats` | 协议 | `domain/bridge` | 桥接协议契约 (v9) |
| 握手交互、负载编解码实现 | 协议 | `internal/kits/bridgekit` | 消费侧辅助 (v10) |
| repl / cmd 分派 / 进程管理 | 引擎 | `engine/bridge` | v9 |

## 4. 传输层契约 (ipc)

```go
// Framing 是信封编解码: 传输自用, 不碰负载.
type Framing interface {
    Name() string
    Encode(msg Message) ([]byte, error)
    Decode(data []byte) (Message, error)
}
// notice: 使用泛型接口, 解耦消息和帧的绑定
type Framing[T any] interface {
    Name() string
    Encode(msg T) ([]byte, error)
    Decode(data []byte) (T, error)
}

// Peer 是一条已建立的连接 (socket 风格).
type Peer interface {
    Read(ctx context.Context) (Message, error)   // 阻塞直到收到一条完整信封
    Write(ctx context.Context, msg Message) error // 并发安全
    Close() error
    Local() string
    Remote() string
}

// Listener 接受被动连接.
type Listener interface {
    Accept(ctx context.Context) (Peer, error)
    Addr() string
    Close() error
}

// Dialer 建立主动连接.
type Dialer interface {
    Dial(ctx context.Context) (Peer, error)
}

// Transport 是传输门面: 惰性构建, Listen/Dial 才启动内部循环.
type Transport interface {
    Name() string
    Addr() string
    Listen(ctx context.Context) (Listener, error)
    Dial(ctx context.Context) (Peer, error)
    Rebind(ctx context.Context) error // 幂等: 解绑 + 重绑 (uds 的陈旧 sock 处理)
    Close() error
}
```

### 4.1 生命周期 (惰性)

```yaml
New(opts...)          : 只保存参数 (地址/帧编码/上限/存储根), 不创建 socket, 不起协程
Listen(ctx)           : 确保目录 -> 处理已存在的 sock -> net.Listen -> 启动 accept 循环 -> 返回 Listener
Dial(ctx)             : 建立连接 -> 返回 Peer (阻塞读写, 无后台泵)
Accept(ctx)           : 从已启动的 accept 循环取一条 Peer
Close() / Rebind(ctx) : 停止/重启监听; 幂等
peer 自身             : 被动对象 (无内部协程), Read/Write 由引擎在合适时机调用
```

### 4.2 uds 特有部分留在传输实现内

```yaml
sock 路径/目录/stale 检测/权限(0600)/Rebind : 属 uds 传输实现的细节 (tcp 实现不需要)
依赖注入: WithStore + WithRooter (经 store 读写目录, 拿到存储根计算绝对路径)
ipc 不认识: Codec(负载)/握手/处理器/分派
```

## 5. 从 ipc 上移出去的东西 (落位)

| 现状 (在 ipc / 契约里) | 目标 | 理由 |
|---|---|---|
| `Codec.EncodePayload/DecodePayload` | `domain/bridge.Codec` (独立契约) + `bridgekit` 的 json 实现 | 负载解析不属于传输 |
| `ClientHandshake` / `ServerHandshake` (ipc) | `bridgekit` | 握手是协议, 不是传输 |
| `Handshake/HandshakeResult/ProtocolVersion/NameHandshake` | 保留在 `domain/bridge` (协议段) | 是负载 schema, 不是消息字段 |
| `Mux` / `Handler` (domain/bridge + ipc) | **删除** | 实测为死代码: 引擎自己的 dispatcher 分派 (v9), ipc 从未使用 |
| `Options.HandshakeTimeout` / `Options.Token` | 移到引擎/协议侧 | 握手是协议 |
| `Config` 结构体 (ipc.New(cfg)) | func option | 统一风格 |
| `Peer.Send/Receive` | `Peer.Write/Read` | socket 风格命名 |

## 7. 迁移映射 (逐项)

```yaml
1) 契约拆分
   domain/bridge/codec.go:
     改前 Codec{Name,Encode,Decode,EncodePayload,DecodePayload}
     改后 Framing{Name,Encode(Message),Decode([]byte)}      (新文件 framing.go)
          Codec  {Name,Encode(any),Decode([]byte,any)}       (只留负载语义)
2) ipc
   codec.go -> framing.go: JSON 只实现 Framing; RegisterCodec/Codec 改为帧编码注册
   删除 mux.go; 删除 Config (改 options.go, func option)
   peer.go: Send->Write, Receive->Read, 增加 Local()
   transport.go: New(opts...) Transport; 内部按 Framing 收发 (不再碰负载)
3) 协议侧
   ipc/handshake.go -> bridgekit/handshake.go (签名不变, 只换包与依赖)
   bridgekit 增加 payload.go (json Codec 实现) 供引擎 EncodePayload/DecodePayload
4) 引擎
   engine/bridge: 装配改为 func options; 握手调用 bridgekit; 删除 Mux 传参
   ipc.Options 里的 HandshakeTimeout/Token 改由引擎持有并传给 bridgekit
5) 文档/自检
   v10 的 lint-arch 不受影响 (无新目录跨越边界)
   迁移后需确认: internal/ipc 不再引用 Codec/握手/Handler (可用 grep 校验)
```

## 8. 考虑要点

### 8.1 并发与背压
- `Peer.Write` 必须并发安全 (引擎的 repl 与业务回包可能同时写): 保持写串行 (互斥或单写泵)。
- 背压策略显式: 依赖 ws 写缓冲阻塞 (当前), 或引入有界队列 (见 §9)。

### 8.2 超时与取消
- `Read/Write` 接受 ctx: 取消即中断等待 (不关闭连接, 由调用方决定)。
- 握手超时属协议层 (bridgekit / 引擎), 不进 ipc。

### 8.3 关闭语义
- `Peer.Close` 幂等; `Transport.Close` 停止 accept 并关闭监听 (uds 下顺带 unlink)。
- 关闭顺序: 停止 accept -> 关闭 peer -> 关闭监听 (由引擎编排)。

### 8.4 错误
- ipc 只报传输错误: 连接关闭/读超限/编解码失败/未连接; 业务错误一律走 `Kind=error` 的完成 (v9)。

### 8.5 可观测
- 传输层不做 Stats (引擎已有只读 Stats, v9 §10.6); 若日后需要字节/条数统计, 属"第二个使用者出现"再下沉 (v10 §8)。

### 8.6 与 v10 边界一致
- ipc 属 internal 的"可复用结构" (有状态、实例独立) ✓
- 握手/负载编解码属"domain 解析辅助" -> kits ✓
- 引擎只做编排 ✓
