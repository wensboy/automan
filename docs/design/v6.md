# Automan 设计 v6 · database 引擎

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v4.md` (store) + `docs/design/v5.md` (log) + 当前骨架
> 范围: 新增 **database 引擎** —— 与 store **同构**的指令式执行器, 指令集面向 SQL/DSL, 底层仅实现 SQLite (sqlx).
> 目标: 明确结构、指令、并发、配置归属与日志要求. 非编码任务.
> 落位: 已有空目录 `backend/engine/database`.

---

## 0. 定位与边界

```yaml
依赖: [config, eventbus, log]
本质:
  - 实现 **store 接口** (Task/Cmd/Handler/Submit/Do/Register/Stats), 与 store 同构
  - 与 store 的差异只有两点: 指令集合 (sql/dsl) 与底层实现 (sqlite/sqlx)
核心功能:
  - 指令参数侧重 SQL 与相关 DSL (含极小的事务步骤 DSL)
  - 当前只兼容 SQL; 内置完整交互实现只考虑 SQLite
  - 无单独 json 配置: 走 store 配置里的 database 子 namespace
  - 必要操作记录日志 (经 log 引擎)
  - 使用 sqlx
不是:
  - 不是 ORM (不做实体映射/关系建模)
  - 不替代 store 的文件 IO (db 只管自己的 sqlite 文件)
  - 不引入第二套队列语义 (队列/背压/限流与 store 同源)
```

---

## 1. 核心观点

### 观点 A — 同构执行器, 只换"指令集 + 后端"

- store 与 database 是**同一框架的两个特化**: 指令入队 → 分区 worker → 查表执行 → 结果回传.
- 因此队列、背压、并发上限、Stats 语义、注册表约束**全部复用**, 不重复实现 (spec: 0 冗余).

### 观点 B — 指令即 SQL (+ 极小 DSL)

- 指令参数承载 **SQL 文本 + 绑定参数**; 事务用"步骤列表"这一极小 DSL 表达原子多语句.
- 不做查询构造器/ORM (当前需求不需要, spec: 不做代码预留).

### 观点 C — 同名接口, 按引擎名区分

- 消费者拿到的是**同一个接口**: `engine.Of[store.Store](ctx, "database")`.
- 与文件 IO 的 `engine.Of[store.Store](ctx, "store")` 并存, 由引擎名区分用途.

### 观点 D — 必要操作必须可见

- 连接/开关、pragma 应用、慢查询、执行失败都经 `log.Logger` 投递 (v5 契约).
- 默认只记 **SQL 文本 + 耗时**; 绑定参数仅 Debug 且可关 (隐私).

### 观点 E — 尊重 SQLite 的现实约束

- SQLite 是**单写者**: 默认单车道串行, 事务在单个任务内完成, 不与其它写任务交错.

## 2. 与 store 的结构关系 (共享核心抽取)

```yaml
问题:
  db 要"实现 store 接口 + 同构语义", 若各自实现队列/worker/背压 -> 重复代码
方案:
  抽取共享核心 engine/dispatch (无业务):
    - 有界分区队列 / worker / 全局并发上限
    - handler 注册表 (按 Cmd 分派) / sealed 约束
    - Submit/Do/Stats 的实现骨架
  engine/store    : dispatch + fs.* handler      -> 面向文件
  engine/database : dispatch + db.* handler      -> 面向 SQL
依赖方向:
  engine/store    -> engine/dispatch
  engine/database -> engine/dispatch
  (两者之间无 import, 也不互为引擎依赖)
```

```yaml
收益:
  - 背压/并发/超时/Stats 只有一处实现, 行为天然一致
  - 新增"第三类存储"时只写 handler 与配置
代价:
  - 需要对现有 engine/store 做一次机械抽取 (行为不变)
备选 (不推荐):
  - database 自行实现队列: 违反 0 冗余, 且两套背压语义容易漂移
```

## 3. 指令模型

### 3.1 指令集 (与既有 fs.* 并列)

```go
// domain/store —— 复用已有框架类型 (Cmd/Task/Handler/Store/Keyed/Stats)

const (
    CmdExec  Cmd = "db.exec"
    CmdQuery Cmd = "db.query"
    CmdGet   Cmd = "db.get"
    CmdTx    Cmd = "db.tx"
)

// ExecArgs 面向 INSERT/UPDATE/DELETE/DDL.
type ExecArgs struct {
    SQL  string
    Args []any
}

// QueryArgs 面向 SELECT.
type QueryArgs struct {
    SQL  string
    Args []any
}

// TxArgs 是极小的事务 DSL: 一个任务内原子执行多语句.
type TxArgs struct {
    Steps []Step
}

type Step struct {
    SQL  string
    Args []any
}

// ExecResult 是写操作结果.
type ExecResult struct {
    RowsAffected int64
    LastInsertID int64
}

// Row 是一行结果 (列名 -> 值).
type Row = map[string]any
```

### 3.2 指令语义

```yaml
db.exec  : ExecArgs  -> ExecResult          # 写/DDL, 自动 BEGIN/COMMIT? 否 —— 单语句即一个隐式事务
db.query : QueryArgs -> []Row               # 读, 受结果集上限约束
db.get   : QueryArgs -> Row                 # 读单行; 无行 -> 错误 (区别于全空结果)
db.tx    : TxArgs    -> []ExecResult        # 一个任务内原子多语句, 失败整体回滚
```

### 3.3 分区键 (Keyed)

```yaml
目的: 同键串行 —— 事务/写入不得交错
取值:
  - db.tx / db.exec : 使用 "write" 语义键 (默认) 或 Args 显式指定 (如表名)
  - db.query/db.get : 使用 "read" 语义键
说明: 显式 Key() 由参数实现 (对齐 v4 §8 决定)
```

### 3.4 便捷函数 (调用面)

```go
// domain/store/db.go —— 与 fs 便捷函数同一风格
func Exec(ctx, s Store, sql string, args ...any) (ExecResult, error)
func Query(ctx, s Store, sql string, args ...any) ([]Row, error)
func Get(ctx, s Store, sql string, args ...any) (Row, error)
func Tx(ctx, s Store, steps ...Step) error
```

## 4. 并发与 SQLite 约束

```yaml
默认: shards = 1 (单车道串行) —— 直接对齐 SQLite 单写者
  - 事务不会被其它任务插入 (事务在单任务内完成)
  - 配置可调, 但多写者会撞 SQLITE_BUSY
连接池:
  - sqlx.Connect (database/sql) + SetMaxOpenConns 与车道数匹配
  - busy_timeout 兜底锁等待, 避免直接失败
pragmas (启动时显式应用, 并记日志):
  - journal_mode = WAL         (读写并发)
  - foreign_keys = ON
  - busy_timeout = <ms>
  - synchronous = NORMAL
后续可选 (待澄清):
  - "写串行 + 读并发": 独立读车道 (WAL 下读不阻塞写)
```

## 6. 必要操作日志

```yaml
级别与内容:
  Info : 引擎启动/关闭, pragma 应用结果, 慢查询 (耗时 >= slowMs)
  Warn : 慢查询 (可单独一档), 锁等待重试
  Error: 连接失败, SQL 执行失败, 事务回滚
字段:
  - sql      : SQL 文本 (默认记录)
  - dur      : 耗时
  - rows     : 影响行数 / 结果行数
  - args     : 绑定参数 (仅 Debug 级别, 且可经配置关闭)
隐私原则: 默认不记参数明文; 需要时显式打开
实现: Init 取 log.Logger 并持有 -> handler 内 Deliver(log.New(...))
```

## 7. 生命周期

```yaml
Name : "database"
Deps : ["config", "eventbus", "log"]      # 不依赖 store 引擎 (底层自持)
Init :
  - 解析 conf/store.database (driver 必须为 sqlite)
  - 注册 db.* handler
  - 取 log.Logger
Start:
  - 打开 sqlite (sqlx.Connect) + 应用 pragmas
  - 启动 dispatch worker (单车道)
Stop :
  - 停止接收 -> 排空队列 (不含未提交事务) -> 关闭连接
```

```yaml
依赖图 (相对 v5):
  runtime/config/eventbus : []
  store                   : [config, eventbus]
  log                     : [config, eventbus, store]
  database                : [config, eventbus, log]      # 只依赖日志, 不依赖 store
  settings/window         : [config, eventbus]
注意: log 先于 database 就绪 -> database 启动期即可打日志
```

## 9. 考虑要点

### 9.1 事务原子性
- `db.tx` 必须在**单个任务**内完成; 单车道串行保证不被其它写任务插入.
- 任一步失败 -> 整体回滚; commit 失败单独处理并记错误.
- 嵌套事务: 不支持 (显式拒绝, 不做隐式 savepoint).

### 9.2 SQL 安全
- 只允许**参数化**: `Args` 走占位符绑定; 不提供字符串拼接接口.
- 表名/列名等无法参数化的部分由调用方负责 (文档中明确边界).

### 9.3 结果集与内存
- `db.query` 受 `maxRows` 约束, 超限报错 (避免大结果集打爆内存).
- 行以 `map[string]any` 返回 (通用); 是否支持直接映射到调用方结构体见待澄清.

### 9.4 超时与锁
- 调用方 ctx 控制 + 引擎兜底 (对齐 v4); 再加 sqlite `busy_timeout`.
- 写冲突最终的兜底是忙等超时 -> 明确错误并记日志.

### 9.5 错误
- 复用 `internal/error`: 增 database 分段 (连接失败/执行失败/超限/不支持).

### 9.6 观测
- 复用 dispatch 的 `Stats` (队列深度/并发/完成/失败), 另可暴露 db 侧计数 (慢查询数).

### 9.7 与 store 的边界
- db **不通过 store** 写 sqlite 文件 (否则双重队列, 且 SQLite 须自己管理文件).
- 但两者共享"逻辑路径 -> 可写目录"的解析规则 (internal/paths).

### 9.8 与 spec 呼应
- **0 冗余**: 队列核心与路径解析各只有一处; db 只贡献指令与 handler.
- **不做代码预留**: 只实现 exec/query/get/tx; 迁移/ORM/查询构造器不做.
- **显式 > 隐式**: pragmas、并发上限、结果集上限、日志参数开关全部显式.
- **考虑边界**: 锁冲突/事务回滚/大结果集/参数隐私/SQLite 单写者.

## 10. 待澄清项

```yaml
- 指令集是否够: exec/query/get/tx? 是否需要 sqlx 具名参数 (":name") 变体? [不需要]
- 结果形态: []map[string]any (通用) vs 传入目标指针由 sqlx 直接填充到调用方结构体 (更强类型)? [考虑强类型]
- 并发模型: 默认单车道 (shards=1) 可接受? 是否要"写串行 + 读并发"双车道? [考虑写串行读并发]
- sqlite 驱动: modernc.org/sqlite (纯 Go, 免 cgo) vs mattn/go-sqlite3 (cgo)? [使用纯go驱动]
- 建表/迁移: 全部交给调用方经 db.exec, 还是引擎提供最小 schema 初始化钩子? [交给db.exec指令, 引擎不做schema假设]
- 指令集归属: 当前放在 domain/store/db.go (与 scaffold 一致); 是否要独立 domain/database? [不需要]
- 共享抽取: engine/dispatch 抽取会改动现有 engine/store, 是否接受? [可接受, 但在迁移的过程中不要变动store的实现, 测试通过后再删除冗余代码, 避免无法追踪复原的问题]
- internal/paths 是否合适 (还是并入其他共享包)? [合适]
- 大结果集: maxRows 报错 vs 分页游标? [分页游标, 针对大结果集合, 参数会考虑传入一个分页结构用于处理分页]
- 是否需要连接池健康检查/重连? [考虑]
```
