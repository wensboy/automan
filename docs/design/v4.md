# Automan 设计 v4 · store 引擎

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v3.md` + 当前薄骨架实现
> 范围: 新增 **store 引擎** —— 面向其他引擎的统一 IO/持久化执行入口; 采用**指令式 task 队列** + 协程并发.
> 目标: 说清指令模型、并发与限流、调用透明性、与现有体系(依赖/事件/配置/错误)的衔接. 非编码任务.
> 落位: 已存在的空目录 `backend/domain/store` 与 `backend/engine/store`.

---

## 0. 定位与边界

```yaml
核心作用:
  为其他引擎提供全面的 IO 读写能力 (唯一入口)
典型消费者:
  - log       : 日志刷盘写入日志文件
  - settings  : 运行期设置的持久化与加载
  - db        : 数据库 CRUD
  - 未来      : 文件类资源 (导出/导入/缓存)
不是:
  - 不是业务数据模型 (不懂"设置项含义", 只认指令)
  - 不是各引擎私有的文件助手 (不允许多份 IO 实现并存)
边界:
  对上: 只暴露"指令"与少量便捷函数, 不暴露文件系统细节
  对下: 统一收敛所有 IO 的排队、并发、限流、错误与观测
```

---

## 1. 核心观点

### 观点 A — 指令式, 而非膨胀的接口

- 反面: 若把能力做成接口, 会不断生长 —— `Read/Write/Append/Remove/Stat/List/Mkdir/Rename/Query/Exec/...`, 调用方被迫依赖全量接口.
- v4: 上层提交**指令 (Cmd + Args)**, 接口面保持极小:

```go
// 接口大小 O(1), 能力增长 O(n) —— 新增能力不改接口
type Store interface {
    Submit(task Task)                                  // 异步: 只入队
    Do(ctx context.Context, task Task) (any, error)     // 同步: 入队并等结果
}
```

### 观点 B — 处理器注册实现多态

- 每个指令绑定一个**已注册的处理函数**; 队列/worker 只做"取任务 → 查表 → 执行", 内部**没有业务 switch**.
- 新增指令 = `Register(cmd, handler)`, 满足开闭原则; 这即是"避免切换困难".

### 观点 C — 队列 + 协程并发, 显式并发上限

- 有界队列 (背压点) + worker 池; 并发上限可配, 目标是不让 IO 打满、也不让队列无限堆积.
- **同键有序**通过"按 key 分区 + 每分区串行"实现 (日志追加必须有序).

### 观点 D — 对调用方透明

- 调用方不构造任务、不接触队列/worker/分区/限流/重试; 只用 domain 的便捷函数.
- 任务、队列、调度是**引擎内部机制**, 只在扩展点 (注册/原生提交) 才露出来.

## 2. 指令模型

### 2.1 契约 (domain/store)

```go
// domain/store —— 纯契约与值类型

type Cmd string                       // 指令名, 形如 "fs.write"

type Task struct {
    Cmd  Cmd
    Args any                          // 指令参数 (类型化结构体)
    // reply: 内部结果回传通道, 由 Do 构造, 对调用方透明
}

type Handler func(ctx context.Context, args any) (any, error)

// Store 是调度入口 (极小接口)
type Store interface {
    Submit(task Task)
    Do(ctx context.Context, task Task) (any, error)
}

// Registrar 是扩展点: 允许注册指令的处理函数
type Registrar interface {
    Register(cmd Cmd, h Handler) error   // 重复注册 -> 报错
}
```

- `Cmd` 常量集中定义 (对齐 spec: 业务 string 无硬编码), 见 `domain/store/cmd.go`.
- `Args` 是**类型化结构体** (见 `domain/store/args.go`), 而非 `map`, 保证编译期可查.

### 2.2 内置指令集

```yaml
fs.read    : ReadArgs{Path}            -> []byte
fs.write   : WriteArgs{Path, Data}     -> 原子写 (temp + rename)
fs.append  : AppendArgs{Path, Data}    -> 追加 (同路径有序)
fs.remove  : RemoveArgs{Path}         -> void
fs.mkdir   : MkdirArgs{Path, Mode}     -> void
fs.stat   : StatArgs{Path}             -> Stat
fs.list    : ListArgs{Dir}             -> []string
```

- 内置指令由 store 引擎自身在 `Init` 注册.
- 其他引擎可注册**业务指令** (如 `db.query`), 复用同一套排队/限流/观测.

### 2.3 便捷函数 (透明调用面)

```go
// domain/store —— 调用方只面对这些
func Read(ctx context.Context, s Store, path string) ([]byte, error)
func Write(ctx context.Context, s Store, path string, data []byte) error
func Append(ctx context.Context, s Store, path string, data []byte) error
// ... Remove/Mkdir/Stat/List
```

```yaml
调用链:
  caller -> store.Write(ctx, s, path, data)
         -> 构造 Task{Cmd: fs.write, Args: WriteArgs{...}}
         -> s.Do(ctx, task)            # 入队 + 等结果
         -> 引擎: 分区 -> worker -> handler -> 返回
  调用方感知不到: 队列/worker/分区/限流/重试/原子写
```

## 3. 队列与并发模型

### 3.1 结构

```yaml
queue:
  形态: 有界缓冲
  作用: 背压点 (满了怎么办 —— 见 3.3)
shards:
  形态: N 个分区队列, 按 key(通常是 path/表名) 哈希取模
  作用: 同 key 落同一分区 -> 分区内串行 -> 同键有序; 跨分区并行
workers:
  形态: 每分区一个串行消费者 (或用信号量限制全局并发)
  上限: maxWorkers / maxInflight 可配
```

```
Submit/Do
  └─ 计算 key (Args 提供 Key() 或按 Path)
      └─ shard = hash(key) % N
          └─ 投递到 shard 队列
              └─ shard worker: task.Cmd -> registry[.Cmd] -> handler(ctx, args)
                  └─ 同步: 结果经 reply 回传; 异步: 结果仅落事件/日志
```

### 3.2 顺序性

```yaml
全局有序: 单 worker               (最简, 牺牲并发) —— 仅作降级模式
同键有序: 分区 + 分区串行          (推荐默认)     —— 满足日志/设置写
无序:     多 worker 共享一队列     (仅限互不相关指令)
```

### 3.3 背压策略 (必须显式定义)

```yaml
选项:
  block  : 队列满则阻塞提交 (可配超时) —— 默认; 简单, 但有尾延迟
  reject : 队列满立即返回 err          —— fail-fast, 调用方需处理
  drop   : 丢弃 (仅"可丢"指令, 如非关键日志) —— 必须由指令显式标注可丢
建议:
  默认 block + 超时; reject/drop 需按指令显式声明能力, 不做全局隐式兜底
```

### 3.4 限流与"避免 IO 打满"

```yaml
手段:
  - 并发上限: maxInflight (全局信号量) —— 直接约束同时在跑的 IO 数
  - 分区上限: shards 数 —— 约束并行度
  - 批量合并: 相邻同类任务合并一次系统调用 (如日志 append 聚合)
  - 速率限制: 可选令牌桶 (按字节/按条)
取值来源:
  - config 引擎: conf/store.{shards,inflight,queue}
  - 缺省值: 由引擎内置, 不做魔法自适应
```

## 4. 与现有体系的关系

### 4.1 引擎契约

```yaml
Name: "store"
Deps: ["config", "eventbus"]      # 遵循"除 config/eventbus/runtime/registry 外都依赖 eventbus"
Init :
  - 从 config 取存储根与并发参数
  - 注册内置 fs.* handler (缺失 -> fail-fast)
  - 需要时可订阅总线 (如收到 flush 请求)
Start:
  - 解析/创建可写根目录
  - 启动 shards worker
Stop:
  - 停止接收 -> 排空队列(带超时) -> 关闭 worker -> 最终 flush   # 日志不丢的关键
```

依赖图更新 (相对 v3):

```yaml
runtime  : deps []
config   : deps []
eventbus : deps []
store    : deps [config, eventbus]
log      : deps [config, eventbus, store]        # 刷盘依赖 store
settings : deps [config, eventbus, store]        # 持久化依赖 store
window   : deps [config, eventbus]
```

- 注册顺序保证: store 先于 log/settings 就绪, 后者才能在 `Init` 里向 store 注册业务指令.

### 4.2 事件

```yaml
topic 定义位置: domain/event/topic.go   (遵循"topic 集中")
候选:
  - store.task.failed : 异步任务失败 (载荷: Cmd/Key/Err)
  - store.flushed     : 排空/刷盘完成 (供停机观测)
  - store.pressure    : 队列深度超阈 (可选)
约束: 载荷类型定义在 domain/event/event.go
```

### 4.3 错误

```yaml
来源: internal/error (code -> error), 定义在 data/conf/error.json
建议新增分段:
  - store: 30000001 路径逃逸 / 30000002 队列满 / 30000003 写失败 / ...
调用: 同步 Do 直接返回该错误; 异步任务的错误经 store.task.failed 广播
```

### 4.4 配置

```json
{
  "meta": { "namespace": "conf/store" },
  "root": "runtime/store",
  "shards": 4,
  "inflight": 8,
  "queue": 256
}
```

- 键形如 `conf/store.shards` (遵循 v3 的统一 Lookup 与平铺键).
- `root` 为**逻辑名**, 由 store 引擎解析为实际可写路径 (见 §5).

## 5. 存储根与可写性 (关键约束)

```yaml
问题:
  data/ 是 //go:embed 的只读种子 (conf 只读), 运行期无法写入
分层:
  seed (只读): data/conf/*.json   —— 启动期配置, 经 config 引擎读取
  runtime(可写): 用户可写目录      —— 日志/设置持久化/数据库
解析:
  config: store.root = "runtime/store" (逻辑名)
  store  : 逻辑名 -> 实际路径 (XDG data dir / 平台约定 / 可覆盖)
边界:
  - 所有路径必须校验在根内 (防逃逸 ../)
  - 根不存在则创建; 无写权限 -> 启动期 fail-fast
```

## 6. 考虑要点

### 6.1 注册时机与完整性
- handler 注册只允许在 `Start` 之前完成 (启动后注册 -> 报错), 避免运行期能力漂移.
- 内置指令缺失 -> `Init` 失败 (fail-fast, 不做运行期兜底).

### 6.2 停机排空
- `Stop` 必须先停止接收, 再排空队列 (带超时上限, 避免卡死), 最后关 worker.
- 排空超时后: 明确记录丢弃数量与原因 (不静默丢).

### 6.3 错误传播
- 同步 `Do`: 结果与错误原样回传调用方.
- 异步 `Submit`: 无调用方等待 -> 失败必须走事件/日志, 不可静默.
- 重试: 仅对**幂等**指令允许 (写/追加不幂等, 默认不重试).

### 6.4 并发安全
- 队列/分区/注册表各自加锁或无锁 (channel 天然线程安全).
- 分区保证同键串行 -> 同一文件的写不发生并发.
- 注册表: 启动后只读 (读多写零) -> 普通 map 即可, 无需锁.

### 6.5 原子与一致性
- `fs.write`: temp + `rename` (同分区) 保证原子替换.
- `fs.append`: 由分区串行保证顺序; 大批量可做聚合写.
- 跨进程并发: 当前不处理 (单实例假设); 如需 -> 文件锁 (待澄清).

### 6.6 内存与背压
- 大对象: 参数按引用传递 (避免复制), 但需约束单次大小上限.
- 队列积压 -> `store.pressure` 事件 + 指标 (队列深度/等待时延).

### 6.7 观测
- 指标: 队列深度、分区深度、等待时延、执行时延、失败计数、丢弃计数.
- 对数/指标经 log 引擎与 eventbus 输出 (不做自建第二套).

### 6.8 与 spec 呼应
- **0 冗余**: IO 收敛到唯一入口, 各引擎不再各自 `os.WriteFile`.
- **不做代码预留**: 只实现当前需要的指令; 扩展靠注册, 不预埋空指令.
- **显式 > 隐式**: 背压策略、并发上限、可丢性都显式声明.
- **考虑边界**: 队列满/停机排空/路径逃逸/权限不足/大对象.

## 7. 目录落位

```yaml
backend/domain/store:              # 纯契约
  store.go   : Store / Registrar 契约 + 便捷函数
  task.go    : Task / Handler
  cmd.go     : 指令常量 (fs.read/write/append/...)
  args.go    : 各指令参数结构 + Key() 分区键
backend/engine/store:              # 实现
  store.go   : 引擎 (Name/Deps/Init/Start/Stop)
  queue.go   : 有界队列 + 分区
  worker.go  : worker 池 + 全局并发上限(信号量)
  registry.go: handler 注册表 + 分派
  fs.go      : 内置 fs.* handler
backend/domain/event:
  topic.go   : 追加 store.* topic
  event.go   : 追加对应载荷类型
data/conf/error.json: 追加 store 分段 code
data/conf/store.json: 新增 (root/shards/inflight/queue)
```

- Do 的超时是调用方 ctx 控制, 还是引擎再加一层超时? 调用方传递, 引擎层加一层兜底避免堆积.
