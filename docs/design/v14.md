## 1. 技术选型

```yaml
React 18   : 保持现状, 不升级 React 19 (骨架不需要; 避免连带改 @types)
TS / Vite  : 保持现状 (tsc + vite build 链路不变)
Tailwind v4: tailwindcss + @tailwindcss/vite —— CSS-first, **不生成 tailwind.config.js, 不用 postcss**
shadcn CLI : 4.x (style=new-york, cssVariables=true, iconLibrary=lucide)
路由       : react-router (库模式) + **createHashRouter**
             理由: Wails 生产环境由 asset server/自定义 scheme 提供页面, hash 路由无需服务端回退,
                   刷新/深链不会 404 (桌面应用最稳)
toast      : sonner (shadcn 现行 toast 方案; 满足"main.tsx 组织 toast provider")
主题       : 自实现 ThemeProvider (~30 行, class 策略), 不引入 next-themes (避免多余依赖)
```

```yaml
不引入: react-query / zustand / framer-motion / storybook 等 (本次不需要, 且骨架应最小)
字体    : 复用 public/Inter-Medium.ttf, 接入 --font-sans (见 §4.3, 可选)
```

> 数据分层: `mock/*.ts` 是**开发期测试数据**(.ts 直接 import, 便于类型与改动); `static/*.json` 是**真实应用数据**
> (纯英文/ASCII 的静态文本)。二者不混用: 真实数据不写进 mock, 测试数据不写进 static。
> 静态数据(layer view): `static/default/*.json` 是 **base 层**, `static/cover/*.json` 是 **cover 层**;
> `lib/static-data.ts` 用 `import.meta.glob` 汇总(文件路径即 key, 目录层级用点号连接, 新增/拆分文件不必改代码),
> `lib/static-store.ts` 是纯核心(叠加 / 取值 / 视图 / 订阅), React 接线在 `share/provider/static-provider.tsx`。
> ```yaml
> 访问: Value(jsonKey)       # 统一按点号路径取值; 叶子是字符串, 非叶子返回对象 (类型见 static/types/static.ts:
>                            #   StaticShape(由 json 推导) -> DotPaths -> StaticValue; 数组与原始值视为叶子)
> 变更: shadow(patch)        # 临时: 返回新视图, 不改动任何数据; 可叠加且内层掩盖外层 (局部作用域语义)
>       cover(patch)         # 永久: 叠加到 cover 层, 所有视图可见, 并触发订阅者重新渲染
>       <StaticProvider shadow={patch}>  # 给某棵子树一个局部视图 (只影响该子树内的读取)
> 叠加: 对象按 key 递归覆盖 (path 相同即覆盖, 例 a.b.c); 数组与原始值**整体替换**(不按下标合并)
> ```
> 组件**不直接 import json**; 图标名用 kebab-case 与 lucide 同名 (例 `"house"`), 由 provider 内的登记表解析,
> **未登记的图标直接抛错**(构建期数据, 不静默兜底); 需要渲染图标数据时用 `useStatic().icon(name)`
> (静态数据只存名字, 由 provider 解析为组件)。当前 `useStatic().sidebar` 兼容字段暂时保留。
>
> **键的定义规则**(替换静态文案时的统一口径):
> ```yaml
> 命名   : 一律小驼峰 (lowerCamelCase)
> 文件   : 文件名即 root 的一层字段 (static/default/sidebar.json -> sidebar.*), cover 同理
> 层级   : 按**组件语义**划分 —— 最大应用布局分为 sidebar / contentArea, 认证页独立 auth, 逐级向下
> end 节点: 按组件使用语义定义; 可以是简单 string, 也可以是 `[]` / `{}`
>          (批量渲染的列表、整体传递的对象 —— 例 contentArea.home.features)
> 取值   : Value("sidebar.user.name"); key 不存在返回 undefined, 不抛异常, 由调用方处理 (props 处用 ?? "")
> 抽取   : 是静态文本才抽到 static; 运行时数据 / mock 测试数据 / 代码标识符留在源码
> ```
>
> **替换状态**: 组件与页面里的静态文案已全部改为取值 —— sidebar / contentArea / auth 三棵树,
> 318 个字符串 end 节点(含 `contentArea.home.features`、`sidebar.settings.sections`、
> `sidebar.help.groups/versions`、`contentArea.logs.levels/timeRanges` 这类列表型 end 节点,
> 原先在 `mock/{features,settings,help}.ts` 的列表已整树迁入并删除对应 mock)。
> 取值形式: 组件内优先 `useStatic()`(可被子树 `shadow` 影响); 纯文案替换用模块级的
> `staticValue()` / `staticIcon()`(与 hook 同一容器, 但不感知子树 shadow)。
> **踩坑**: 列表数据里若存的是"图标名", 渲染时必须走解析(`icon(name)` 或 `<feature.Icon />`) ——
> 直接 `<item.icon />` 会把字符串当成 HTML 标签渲染(`"video"` 变成 `<video>`、`"link"` 变成 `<link>`,
> 表现为"图标不显示 / 文字左移不对齐")。

> 路由与鉴权: `App.tsx` 只负责路由表; 需要登录的路由元素用 `AuthGuard` 包住 (每次路由切换重新判定,
> 未通过则重定向且子树不渲染), 登录/注册页放在守卫之外; 会话 token 由 `lib/auth.ts` 管理 (sessionStorage),
> 退出登录收在 nav-user 的 Log out。

> **弹窗内嵌侧栏**(settings / help): `ui/sidebar` 的桌面侧栏是"为整页设计"的 ——
> `data-slot="sidebar-container"` 用 `fixed + h-svh` 渲染侧栏本体, 同时另有一个 `sidebar-gap`
> 在流内**占位预留宽度**: **占位与渲染是两套坐标**。并且 `Sidebar` 的 `className` 落在
> `sidebar-container` 上(外层 `data-slot="sidebar"` 的 class 是固定的, 传不进去)。因此:
> ```yaml
> 内容装得下      -> 原样用 <Sidebar collapsible="none" className="hidden md:flex">  (settings, 12 项)
> 内容溢出需滚动  -> 换掉容器: 普通 flex 列承载侧栏组成件
>                    (SidebarHeader/SidebarContent/… 仍在 SidebarProvider 内, useSidebar 照常可用),
>                    高度由 SidebarProvider 给定 (如 h-[480px] + min-h-0 抵消 ui 的 min-h-svh, 与同排内容区同高),
>                    滚动交给 SidebarContent 自带的 flex-1 + min-h-0 + overflow-auto  (help, 文档树)
> ```
> 反例(踩过): 用子层选择器 `[&>[data-slot=sidebar-container]]:h-full` 覆盖内部 class —— 匹配不到任何
> 元素; 改它的 height/position —— 与 gap 占位错位, 表现为"内容区移位/互相覆盖"。

> 外壳高度与内部滚动: `layouts/app.tsx` 的 `SidebarInset` 固定为 **`h-svh overflow-hidden`** ——
> 外壳不随内容增长(否则长内容会把 body 撑出滚动条, 表现为"终端越写越长、整页跟着滚"),
> **需要滚动的页面在自己的内容区内部滚动**。因此高度链上每一层都要"可收缩 + 有界":
> 页面根 `min-h-0 flex-1` → 日志容器 `min-h-0 flex-1 overflow-hidden` → 终端宿主 `min-h-0 flex-1`
> (滚动交给内建滚动区: xterm 的 `scrollback`、`ScrollArea` 等)。缺任何一层的 `min-h-0`,
> flex 子项会按内容撑开, 又回到"外壳被撑高"。

> 日志终端(pages/logs): xterm.js 挂载在内容区, 上方筛选只影响写入终端的行 (追加时只写增量,
> 筛选变化时整体重写, 历史滚动保留 —— `scrollback`)。主题色读 CSS 变量
> `--terminal-background` / `--terminal-foreground`: **xterm 不解析 oklch**, 所以这两个 token
> 用可解析格式 (是 `--background`/`--foreground` 的 hex 镜像), 级别颜色走 ANSI SGR (终端自带调色板)。
> 日志数据来自后端: 日志引擎的 stream out 经**二级总线**(不走主 eventbus)批量下发, window 引擎转成
> 前端事件 `log:stream`(载荷即 Record 的 JSON 形态); 页面订阅后追加到本地行缓冲(上限 500)。
> 只含**程序运行启动后**的日志; 溢出丢弃以"日志形式"提示(下一批批首插入一条 warn 记录)。
> 终端行格式: `YYYY-MM-DD HH:mm:ss LEVEL 消息 key=value …` —— 时间含**年月日**(本地时区),
> 因为日志常跨天查看, 只给时分秒无法区分日期 (`logs/model.ts` 的 `formatLogTime`);
> 附加字段按落盘的 ` key=value` 形式拼在消息后 (`toLogLines`)。
> 终端滚动条默认全隐藏, 样式收在 `logs/terminal.css`(在 `xterm.css` 之后 import, 用 `[data-slot=log-terminal]`
> 前缀保证特异性)。**关键: xterm 6 自带一套 VS Code 风格的滚动条元件, 不是浏览器滚动条** ——
> `.xterm-scrollable-element > .scrollbar`, 运行时给同一个元素加 `visible` / `invisible.fade` 做淡入淡出
> (实测: 日志持续写入时它不停淡入淡出 = "滚动条频繁闪动"), 所以必须对这个 `.scrollbar` 元素
> `display: none`;`::-webkit-scrollbar { display: none }` 只作为内核 overlay 滚动条的兜底。
> 另一个坑: 不要写标准属性 `scrollbar-width` / `scrollbar-color` —— WebKit 下一旦设置, 会改用标准滚动条
> 并**忽略 `::-webkit-scrollbar`** 样式, 隐藏规则会失效。
> 另外 `fit()` 用 `requestAnimationFrame` 节流(每帧最多一次) + 零尺寸跳过, 避免 fit 与重排互相触发。
> 隐藏滚动条后滚动仍可用: 鼠标滚轮 / `Shift+PgUp`·`Shift+PgDn`, 历史由 `scrollback` 维护;
> 代价是**不能再拖动滑块滚动**(滑块已不存在) —— 这是"完全隐藏"的固有取舍, 若要拖拽改为"常显无淡入淡出"。

> 布局记法(需求里的简写, 落到代码时翻译成 flex 方向与对齐): `v_u->d` = 纵向, 自上而下;
> `h_l->r` = 横向, 自左向右; `h_r->l` = 横向, 自右向左 —— **首个元素在最右**
> (例: `h_r->l(text button(save), text button(cancel))` => 视觉上 save 在右、cancel 在其左,
> DOM 顺序为 cancel/save, 整行右对齐)。

| 原则 | 落法 |
|---|---|

| 树形结构化 | 组合方向单一: `page → layout → custom → ui`;**自定义组件不得反向依赖 pages/layouts** |

| 单文件组件 | 每个文件 `export default` 一个主组件; 私有子组件/常量留在同文件内不导出 |
| ui/ 不改 | shadcn 组件只通过 props/className 定制; 需要行为变更时在 `custom/` 包一层 |

### 4.2 硬性禁止(骨架期就守住, 后面才不用返工)

```yaml
- 禁止组件内写死颜色: bg-white / text-gray-500 / border-slate-200 ...
  改用: bg-background / text-muted-foreground / border-border
- 禁止写死圆角: rounded-[10px] 改用 rounded-lg (随 --radius 统一)
- 禁止在页面里覆盖主题色 (如 text-blue-600); 需要新色时**先加 token**, 再用 token
- 禁止不同组件各自 import 一份主题; 主题只在 index.css 定义
- `static/*.json` **只放英文 (纯 ASCII)**: 展示文案的语言切换属本地化层, 不写进静态数据
- 禁止把 `DropdownMenuTrigger asChild` 套在 `SidebarMenuButton` 外面: React 18 下函数组件无法接收
  ref, Radix 拿不到锚点元素 -> 菜单"能打开但位置不可见"。正确写法是
  `<SidebarMenuButton asChild><DropdownMenuTrigger>…`(DOM 与属性完全等价, 见 nav-user/team-switcher)
- React 18 下凡 `asChild` 的子节点都必须是能透传 ref 的元素或 forwardRef 组件 (如 `<a>`/`<button>`/
  react-router 的 `Link`); 包一层自定义函数组件会静默丢 ref
- 特别注意 **CLI 生成的 `ui/button.tsx` 是 React 19 风格的普通函数组件 (没有 forwardRef)**:
  写成 `<DropdownMenuTrigger asChild><Button>` 会丢 ref —— 表现为"点按钮没反应"。实测: 菜单确实
  `data-state=open` 且内容已挂载, 但 Radix 锚点为空 -> popper 落到兜底定位 `transform: translate(0, -200%)`
  (屏幕外)。正确写法把 Button 放外层: `<Button asChild><DropdownMenuTrigger>…`, 视觉与 DOM 完全等价
  (见 `proxy/table` 的行操作菜单)
- 禁止在弹窗/抽屉等受限容器里覆盖 `ui/sidebar` 容器的 height/position (它是 gap 占位 + 绝对定位渲染
  两套坐标, 一改必然错位); 需要滚动时改为自建 flex 列承载侧栏组成件 (见 §2 "弹窗内嵌侧栏")
- 第三方**自绘 UI 元件**要先查来源再改样式: 如 xterm 的滚动条是它自己实现的 DOM 元件
  (`.xterm-scrollable-element > .scrollbar`, 用 `visible` / `invisible.fade` 做淡入淡出), 浏览器滚动条伪元素
  对它完全无效 —— 遇到"样式改了没反应 / 莫名闪烁", 先读该库的 CSS 与运行时类名, 不要默认是浏览器机制
- 隐藏滚动条只用 `::-webkit-scrollbar`, **不要写标准属性 `scrollbar-width` / `scrollbar-color`**:
  WebKit 下一旦设置这两个属性就会改用"标准滚动条"并忽略伪元素样式 (详见 §2 "日志终端")
- `Select` 一律写 `position="popper"` (**非触发器对齐**): Radix 默认的 item-aligned 会把选中项
  对齐到触发器位置, 与本地其它浮层不一致; 全仓 select 需统一
  (当前: `proxy/footer`、`records/footer`、`capture/select`、`logs/filters` 的级别/时间)
```
