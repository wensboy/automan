# Automan 设计 v9 · bridge engine (具体桥接引擎)

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v8.md` (bridge 层抽象与 ipc) + 当前实现 (`domain/bridge`、`internal/ipc`)
> 范围: **具体桥接引擎** `backend/engine/bridge/<name>` —— 子进程生命周期管理 + repl 消息 loop + cmd dispatch/fallback.
> 目标: 明确数据流、1:1 配对、双方对称处理模式、引擎结构、与 database 的衔接. 非编码任务.
> 落位: 空目录 `backend/engine/bridge`、`backend/bridge` (仅 readme 存根).

---

## 0. 定位与边界

```yaml
依赖: [config, database, eventbus, log, settings, store]
  - store    : sock 目录/文件操作 + 存储根 (v8 §3)
  - database : cmd 执行计划/结果 的审计与幂等 (§7)
  - settings : 业务可调项 (超时等以 config 静态为准, 见 v8 §10)
  - log      : 子进程与 cmd 的必要操作日志
  - eventbus : 桥接生命周期事件 (v8 topic)
核心作用:
  - 管理子进程生命周期 (源代码 + 启动指令 -> 子进程; 创建实例时经 option 设置)
  - repl 处理 loop (执行计划的投递/执行/完成 的循环)
  - 基于 cmd 的 dispatch handle 机制; **核心点火侧在 go 端**
不做 (边界):
  - 不做传输与编解码 (复用 domain/bridge + internal/ipc, v8)
  - 不定义业务 cmd 的语义 (由接入方注册 handle)
  - 不替被桥接进程实现业务 (node 侧源码在 backend/bridge/<name>, 同一套模式)
```

## 1. 核心观点

### 观点 A — 1:1 的执行计划与执行结果

```yaml
go  -> node : { cmd, 必要参数 }        # 执行计划
node -> go  : { cmd, 执行结果 }        # 完成消息
配对关系: 严格 1:1 —— 每条计划有且仅有一条完成
关联手段: 消息标识 (v8 Message.ID)
目的: 避免 "cmd 误执行" 与 "结果错误返回"
```

- 直接复用 v8 的信封, 不新增协议字段:

```yaml
ID   : 关联标识 (全局唯一, 配对唯一依据)
Kind : request  = 执行计划 (go -> node)
       response = 完成      (node -> go, 成功)
       error    = 完成      (node -> go, 失败)
       event    = 单向通知  (任一方向)
Name : cmd 名 (分派键)
Payload: 参数或结果
```

### 观点 B — 双方遵循同一套处理模式 (类 RPC)

```yaml
共同模式:
  1. 连接建立后先握手 (v8: codec/版本/身份/token)
  2. 各自跑单读 loop
  3. 按名 (cmd) 找 handle 执行
  4. 以标识 (ID) 关联计划与完成
差异 (角色):
  go  (主动方/点火侧): 持有 in-flight 表 (ID -> 完成回调), 负责投递计划
  node (被动方/执行侧): 持有 handle 表 (cmd -> 执行体), 负责执行并回完成
```

### 观点 C — fallback 就是"按 cmd 注册的回调", 双向都成立

```yaml
出站 (go -> node):
  go 投递 cmd + payload + fallback (等待完成的回调) -> 登记 in-flight
  node 按 cmd 找 handle (本质是 node 侧注册的 fallback) 执行
  node 回完成消息 + 必要负载
  go 按 ID 命中 in-flight -> 调用该 fallback (回填结果/唤醒 await)
入站 (node -> go):
  node 投递 cmd + payload -> go 按 cmd 找已注册 handle (go 侧 fallback) -> 执行 -> 回完成
```

### 观点 D — 进程管理是引擎职责, 传输是 v8 职责

- v8 的核心只保证 **可绑定/可重绑/可重连**; 本引擎负责 **启动/守护/退出感知/恢复编排**。

### 观点 E — 复用而非重造

```yaml
internal/ipc  : ws over uds 传输 + json 编解码 + 握手 + Mux 默认实现 (v8 已实现)
bridge.Mux    : 入站 cmd 的按名分派 (引擎复用它, 不重写分派表)
in-flight 表  : 唯一新增的分派结构 (完成必须按 ID 匹配, 不能按名)
```

## 2. 数据流

### 2.1 出站调用 (go -> node -> go)

```
Invoke(ctx, cmd, payload)
  |- 生成 ID (单调计数/UUID)
  |- 注册 in-flight: ID -> {cmd, done chan, fallback}
  |- Peer.Send(Message{ID, Kind:request, Name:cmd, Payload:encode(payload)})
  ...(node: loop -> handle[cmd] -> 执行 -> Send(Message{ID, Kind:response/error, Name:cmd, Payload:结果}))
  |- go loop 收到 -> Kind in {response,error} -> 按 ID 命中 in-flight
  |- 回填结果 -> 关闭 done -> 调用 fallback (即 Invoke 的返回)
  |- 从 in-flight 移除
```

### 2.2 入站调用 (node -> go -> node)

```
node 投递 Message{ID, Kind:request, Name:cmd, Payload}
  |- go loop 收到 -> Kind=request -> 按 Name 查 handle 表
  |    - 未注册 -> 回 Kind:error (完成, 同 ID), 记日志
  |- 执行 handle -> (结果, err)
  |- Send(Message{ID, Kind:response|error, Name:cmd, Payload:结果})
```

### 2.3 异常路径 (必须显式)

```yaml
未知 ID 的完成      : 丢弃 + 日志 (不误触发任何回调)
重复的完成 (同 ID)  : 仅第一次生效, 后续丢弃 + 日志
未知 cmd 的计划     : 回 Kind:error 完成 (node 侧同理: 未注册 handle)
超时/取消           : 移除 in-flight + 返回错误 + 日志; 晚到的完成 -> 未知 ID -> 丢弃
子进程崩溃          : 该连接上全部 in-flight 一次性回错 (fail-fast) + 广播事件
payload 解码失败    : 视为协议错误, 回 Kind:error (不静默)
```

## 3. 引擎契约与生命周期

```yaml
Name : "bridge.<daemon>"      # v8 §10: 例 bridge.node
Deps : ["config", "database", "eventbus", "log", "settings", "store"]
Init :
  - 取六引擎句柄 (config/store/log/ebus/settings/database)
  - 解析 conf/bridge.<daemon> 参数 (静态: sock/codec/上限/超时/token)
  - 选 codec (按名, 进程级固定) + 构造 Mux + 注册内部 cmd (如握手)
  - 准备子进程描述 (option) —— 不在 Init 启动
Start:
  - 子进程启动 (若有配置/option)  # 与桥接监听可并行, 无强顺序依赖
  - 桥接 Rebind (建目录/清理陈旧/监听)   # v8: 可连通则报错退出
  - 接受连接 -> 握手 -> 启动 repl loop -> 就绪
Stop (幂等):
  - 停止 repl -> 关闭连接 -> 终止子进程 (信号 -> 超时强杀) -> 关闭桥接 (删 sock)
恢复 (子进程 down 时):
  - 感知退出 (Wait) -> 广播事件 -> 按策略重启 或 等待外部重启
  - 重新 Rebind + 等待重连 + 重建 repl -> 广播连接事件
```

## 4. cmd dispatch / fallback 机制

### 4.1 调用面 (domain/bridge 扩展)

```go
// Result 是一次调用的完成结果 (1:1 对应一条执行计划).
type Result struct {
    ID      string
    Cmd     string
    Status  Kind   // response | error
    Payload []byte // 结果载荷原始字节
    Err     string // Status == error 时的原因
}

// Caller 是主动方能力: 投递执行计划.
type Caller interface {
    Invoke(ctx context.Context, cmd string, payload any) (Result, error)
    Notify(ctx context.Context, cmd string, payload any) error // 不等完成
}

// HandleFunc 是入站 cmd 的处理器 (返回结果载荷, 由引擎编码回送).
type HandleFunc func(ctx context.Context, payload []byte) (any, error)

// Dispatcher 是被动方能力: 按 cmd 注册处理器.
type Dispatcher interface {
    Handle(cmd string, h HandleFunc)
}
```

- `service` 侧只依赖这两个**领域契约**, 经 `engine.Of[bridge.Caller](ctx, "bridge.node")` 取用 —— 不 import engine (v3 约定)。
- 结果载荷的类型化读取复用 v8 的通用辅助: `bridge.Payload[T](codec, ...)` 的同族函数 (新增 `Result` 版本)。
- **fallback 的两种落点**:
  - 出站: 调用方 await (由 `Invoke` 内部登记进 in-flight)
  - 入站: 注册的 `HandleFunc`
  二者是同一套机制的两侧, 都不引入额外概念。

### 4.2 in-flight 表 (唯一的完成匹配结构)

```yaml
结构: map[ID]entry   (entry: cmd, done chan Result, 创建时间)
写入: Invoke 前登记; 完成/超时/崩溃时移除
上限: maxInflight (显式上限, 超限 -> 立即失败并记日志, 不隐式排队堆积)
匹配: 只按 ID; 命不中 -> 丢弃 + 日志 (满足"结果错误返回"的防护)
```

### 4.3 ID 生成

```yaml
当前: 进程内单调递增计数 (加 daemon 前缀便于排查), 满足"进程内唯一"即可
跨重启唯一: 若 database 审计/幂等需要跨会话唯一 -> 改用 UUID (见 §7, §11)
```

## 5. 子进程管理

```yaml
创建 (实例化时经 option 设置):
  WithCommand(cmd)       # 例 "node"
  WithArgs(args...)      # 例 入口脚本/参数 (源代码由启动指令决定)
  WithDir(dir)           # 工作目录
  WithEnv(kv...)         # 环境变量
  WithStdio(in/out/err)  # 输出接管 (默认继承, 便于开发期观察)
  WithRestart(policy)    # 重启策略 (显式, 见下)
语言无关: 引擎只认"命令 + 参数", 不内置任何 runtime 专属逻辑

生命周期:
  Start : 启动 -> 记录 pid/命令 (日志)
  Run   : Wait 阻塞感知退出
  Down  : 记录退出码/错误 -> 广播 bridge.disconnected -> 按策略处理
  Stop  : 优雅终止 (发送信号) -> 等待 grace -> 超时强杀 -> 等待回收 (幂等)

重启策略 (显式, 不做隐式重试):
  none    : 只感知, 不重启 (默认)
  on-fail : 非正常退出才重启
  always  : 总是重启
  退避    : 固定/指数 + 最大次数 (超过则停止并广播错误)
```

## 6. repl loop 细节

```yaml
go 侧 loop (单读协程):
  循环 Receive:
    Kind=response|error -> 按 ID 命中 in-flight -> 回填 + 移除 (+ 调用 fallback)
    Kind=request        -> 按 Name 查 handle -> 执行 -> 回 response|error 完成
    Kind=event          -> 按 Name 查 handle (只执行不回送)
    解码失败            -> 记日志 (+ 尽力回 Kind:error)
  退出条件: 连接关闭 / 引擎停机 / 致命协议错误

node 侧 loop (对称):
  循环收到计划 -> 按 cmd 查 handle -> 执行 -> 回完成 (成功/失败同一 ID)
  未注册 cmd -> 回 error 完成

写路径:
  Peer.Send 已做写串行化 (v8/internal/ipc) -> 任意协程可安全回送
  可选: 有界发送队列做显式背压 (满则阻塞/拒绝, 不静默丢)

并发:
  出站: 天然并发 (各自 in-flight, 以 ID 区分)
  入站: 默认串行执行 handle (简单可预期); 需要并行时按 cmd 显式声明 (见 §11)
```

## 7. 与 database 的衔接 (新增依赖)

```yaml
用途 (按重要性排序, 具体取舍见 §11):
  1. 审计/追溯: 每条计划与结果落库
       id, daemon, session, cmd, payload, result, status, cost_ms, created_at
  2. 幂等: 以 id 为主键, 防止重复执行/重复结果 (跨进程重启也成立)
  3. 恢复: 进程重启后能查"未完成"记录, 决定重放或标记失败
写入时机 (显式, 不做隐式批量):
  计划投递前 (status=pending) / 完成时更新 (status=done|failed)
  - 高吞吐下可只落"失败与超时", 或按 cmd 白名单落库 (可配置) -- 见 §11
表结构归属:
  - v6 的 database 引擎不做 schema 假设 -> 表由本引擎在 Start 时 DDL
    (CREATE TABLE IF NOT EXISTS ...) , 并记录日志
  - 若你更希望"调用方建表", 引擎则只读写 + 缺表报错 (见 §11)
```

  - 子进程"命令/参数/工作目录/env"以 **option 为主** (创建实例时设置):

  - settings 仅承载"业务可调项"; 传输超时/上限属 config 静态 (v8 §10)

## 10. 考虑要点

### 10.1 消息与配对
- 1:1 靠 ID: 未知/重复 ID 一律丢弃 + 日志 (宁可丢弃也不误调用回调)。
- `Notify` (不等完成) 仍保证 node 侧最终回一条完成消息; go 侧收到后**无 in-flight 可匹配** -> 丢弃 + 可观测计数 (需要时改为登记"无需等待"的占位)。

### 10.2 超时与取消
- 每次 `Invoke` 带超时 (config): 超时 -> 移除 in-flight + 返回错误 + 日志。
- ctx 取消语义同上; node 侧无法中断执行时, 其晚到的完成会被安全丢弃。
- 可选: 超时后向 node 发一条"取消"事件 (尽力而为)。

### 10.3 子进程崩溃与恢复
- 崩溃时把该连接全部 in-flight 一次性回错 (fail-fast), 广播 `bridge.disconnected`。
- 重启后必须 **Rebind**(v8) 并等待子进程重连; 旧连接一律视为失效。
- 会话标识 (session) 用于日志与 database 记录里区分"第几次连接"。

### 10.4 并发与背压
- 写: 依赖 `Peer.Send` 的写串行化; 需要背压时加有界队列 (显式策略)。
- 入站 handle 默认串行 (可预期); 高吞吐需并行时按 cmd 显式开启并受上限约束。

### 10.5 幂等与安全
- `Start`/`Stop` 幂等; 停机保证子进程不残留 (优雅 -> 超时强杀)。
- sock 权限 0600 (v8), 可选 token 握手; 不监听 TCP。
- 子进程继承环境变量需显式声明 (避免泄露敏感环境)。

### 10.6 可观测
- 只读 `Stats`: 子进程状态/重启次数、连接状态、在飞数、投递/完成/超时/丢弃计数。
- 事件: `bridge.connected` / `bridge.disconnected` / `bridge.error` (v8 已定; §10 结论为"足够, 不要 message 级事件")。

### 10.7 与 spec 呼应
- **0 冗余**: 传输/编解码/Mux 复用 v8; 仅新增 in-flight 表。
- **不做代码预留**: 只做"计划-执行-完成"这一条主链路 + 可选审计; 不做流式进度 (除非 §11 要求)。
- **显式 > 隐式**: 重启策略、超时、上限、背压、审计粒度、串/并行全部显式。
- **考虑边界**: 崩溃/半死连接/未知与重复 ID/大载荷/背压/停机竞态。

## 11. 待澄清项

```yaml
- 调用面归属: Caller/Dispatcher 放 domain/bridge (推荐, 便于 service 只依赖领域) 还是引擎方法? [放 domain/bridge下]
- 入站 handle 并发: 默认串行可接受? 是否需要按 cmd 显式声明并行? [考虑根据不同的入站类型做并发操作]
- 子进程崩溃时在飞请求: 全部 fail-fast 回错 (推荐)? 还是等待重连后重放? [快速回错, 引擎会考虑重新拉起新子进程需要reset in-flight]
- database 的真实用途: 审计 / 幂等 / 恢复, 还是三者都要? 落库粒度 (off/failed/all)? [当前可以不考虑使用, 后续处理调用处理]
- 表结构归属: 引擎 Start 时 DDL (推荐) 还是调用方建表? [当前不需要考虑实现]
- ID 生成: 进程内计数 (推荐) 还是 UUID (跨重启唯一)? [进程内计数]
- 子进程命令来源: option-only (推荐) / 配置 / option 优先 + 配置兜底? [option优先, 配置兜底]
- 重启策略默认值: none 是否可接受? 退避曲线与最大次数? [none可以接收, 按照指数退避, 当前最大上限设置到32]
- Notify (不等完成) 是否现在就需要? [需要考虑]
- 是否需要"中间进度消息" (会打破严格 1:1)? [需要考虑流消息处理, 1:1 语义上变为最少保持]
- node 侧源码形态与构建 (TS 编译产物 / 依赖安装 / 启动入口)? [包含完整源代码和构建后的产物]
- in-flight 上限缺省值? [允许在配置文件中配置, 考虑尽可能适中的大小]
- 是否需要 cmd 白名单/权限 (只允许注册过的 cmd 被 node 调用)? [这个在 node侧考虑, go侧不考虑对策处理的消息如何处理.]
```
