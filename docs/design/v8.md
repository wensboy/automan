# Automan 设计 v8 · bridge 层

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `v3` (引擎/依赖) + `v4` (store) + `v5` (log) + `v6` (database) + `v7` (settings) + 当前骨架
> 范围: **bridge** —— go runtime 与 node runtime 之间的父子进程 IPC 统一标准; **ws over uds** 传输 + **多态消息编码**.
> 目标: 明确分层、统一抽象、传输与消息设计、sock 生命周期与协作方式. 非编码任务.
> 落位: 已有空目录 `backend/domain/bridge`、`backend/engine/bridge`、`backend/bridge`; `data/conf/bridge.json` 存根 (meta.namespace = conf/bridge).

---

## 0. 定位与边界

```yaml
依赖: [config, settings, store, eventbus, log]
核心作用:
  - 桥接 node runtime 与 go runtime: node 子进程 <-> go 父进程 的 IPC 解决方案
  - 提供统一桥接抽象, 使不同桥接引擎可接入 (不限于 node runtime)
  - 本质上是一套 IPC 统一标准: 传输 + 信封 + 多态编码
不做 (边界):
  - 不管理被桥接进程 (启动/守护/重启/退出感知由具体桥接引擎实现)
  - 不定义业务协议 (方法语义由接入方按消息名注册处理器)
  - 不重复实现文件 IO (目录/探测/删除走 store)
```

## 1. 核心观点

### 观点 A — 三层落位, 且按 daemon 分子目录

```yaml
契约层: backend/domain/bridge          # 统一抽象 (纯契约, 无实现)
引擎层: backend/engine/bridge/<name>/  # 具体桥接引擎 (可多个)
被桥接侧: backend/bridge/<name>/        # 子进程侧源码 (可多个, 如 node 客户端)
```

- 除 `domain` 下的统一抽象外, **engine/bridge 与 bridge 一律用 `<name>` 子目录组织** —— 桥接 daemon 可能不止一个 (node / python / 未来其他 runtime)。

### 观点 B — 传输与编码正交

- 传输: **ws over uds** (双向、保序、内建 ping/pong)。
- 编码: **可替换的 `Codec`**, 内置 json (固定信封格式); 后续换 msgpack/protobuf 只加实现, 不动传输与分派。

### 观点 C — 消息 = 信封 + 名称 (多态由注册表实现)

- 传输层只认识信封的四个字段 (`id/kind/name/payload`), **不认识业务类型**。
- 多态: 按 `name` 注册"载荷 → Go 类型", 收到消息后按名反序列化再交处理器。

### 观点 D — 核心只保证"可绑定/可重绑/可重连"的幂等能力

- 桥接核心提供 `Rebind()` 这类**幂等**能力; "子进程 down 后恢复" 由具体引擎编排 (感知退出 → 重绑 uds → 重连 → 重建会话)。

### 观点 E — 复用既有引擎

```yaml
store   : 建目录 / 探测 / 删除 sock + 提供存储根 (uds 需要绝对路径)
log     : 绑定/解绑/连接/断开/失败等必要操作日志
settings: 桥接可调参数 (心跳/空闲超时/消息上限), 三层可覆盖
config  : 静态参数 (是否启用/编码/sock 名)
eventbus: 桥接生命周期事件对外广播
```

## 2. 分层与目录落位

```yaml
backend/domain/bridge:                 # 统一抽象 (纯契约)
  bridge.go : Bridge 门面契约
  peer.go   : Peer / Listener / Dialer
  codec.go  : Codec 契约 + 编解码实现注册
  message.go: Message / Kind
  mux.go    : Handler / Mux (按名分派) + 载荷类型注册表

backend/engine/bridge/<name>/:         # 具体桥接引擎 (可多个)
  <name>/   : 例 node/ —— 含被桥接进程管理 + 监护 + 调用 Rebind/重连

backend/bridge/<name>/:                # 被桥接侧 (子进程) 源码 (可多个)
  <name>/   : 例 node/ —— ws over uds 客户端 + 消息分派

backend/internal/ipc/:                 # ws over uds 传输实现 + 内置 json 编解码 (跨桥接引擎复用)
```

- `internal/ipc` 的定位与 `internal/flat`、`internal/paths` 同层: **按语义命名的共享实现**, 不是工具包 (不叫 kit/util)。
- 具体引擎与其被桥接侧源码同名同层 (`node` ↔ `node`), 便于对照演进。

## 3. uds 与隔离

### 3.1 路径与职责

```yaml
路径: <store root>/bridge/<name>.sock  ->  ~/.config/automan/bridge/<name>.sock
根来源:
  - 需要 store 暴露存储根 (新增 domain/store.Rooter { Root() string })
  - 理由: 若桥接引擎自行解析路径, 会与 store 的根 (可被配置/测试注入) 不一致
职责划分:
  store : fs.mkdir 建目录 (0700) / fs.stat 探测 / fs.remove 清理陈旧 sock
  引擎  : net.Listen("unix", abs) / chmod 0600 / close / 经 store 删除 sock
```

### 3.2 绑定策略 (幂等)

```yaml
Rebind 步骤:
  1. 确保 bridge/ 目录存在 (经 store 的 fs.mkdir)
  2. stat sock:
       存在 -> 解绑 (remove) 后重新绑定   # 存在即解绑重绑 (用户约定)
       不存在 -> 直接绑定
  3. 删除前校验"确实是 socket" —— 避免误删同目录下的普通文件
  4. listen + 权限收紧 (目录 0700 / sock 0600)
隔离 (程序级):
  - 一个 daemon 一个 sock 文件名; 同名即同一桥接 -> 天然不串
  - 位于同一 store 根内 -> 多实例/多用户/测试注入都各自隔离
```

## 4. 传输: ws over uds

```yaml
服务端 (go 父进程):
  net.Listen("unix", abs)
    -> http.Server{Handler: mux}
    -> websocket.Accept(w, r, opts)
  ws 端点: GET /<name> (路径携带 daemon 名, 便于同一 socket 上多路)
客户端 (子进程, 如 node):
  Node 侧: ws 库 + createConnection(socketPath) (不依赖 npm 运行期安装)
  go 侧:  http.Client{Transport: &http.Transport{DialContext: unixDialer}}
          -> websocket.Dial(ctx, "ws://bridge/", &DialOptions{HTTPClient: ...})
消息与帧:
  一条 ws 消息 == 一条 Message (json -> 文本帧; 二进制编码 -> 二进制帧)
  顺序: ws 保序, 同连接内按发送顺序到达
  心跳: ws ping/pong; 空闲超时 -> 关闭连接, 交上层决定重连
  背压: 受 ws 写缓冲约束; 引擎可加有界发送队列 (显式策略, 不隐式丢弃)
依赖: github.com/coder/websocket (已在 go.mod 中作为 wails 的间接依赖, 模块缓存可用)
```

## 5. 消息模型与多态编码

### 5.1 信封

```go
// domain/bridge —— 传输层只认这四个字段
type Kind string

const (
    KindRequest  Kind = "request"
    KindResponse Kind = "response"
    KindEvent    Kind = "event"
    KindError    Kind = "error"
)

type Message struct {
    ID      string // 请求/关联 id (响应与事件可空)
    Kind    Kind   // 消息种类
    Name    string // 方法名/事件名 (多态分派键)
    Payload []byte // 载荷原始字节 (由 Codec 解释)
}
```

### 5.2 编解码契约

```go
type Codec interface {
    Name() string                      // 用于握手与注册 (json/msgpack/...)
    Encode(msg Message) ([]byte, error)
    Decode(data []byte) (Message, error)
    EncodePayload(v any) ([]byte, error)      // 载荷 <- 具体类型
    DecodePayload(msg Message, into any) error // 载荷 -> 具体类型
}
```

- `EncodePayload/DecodePayload` 与信封编解码成对: 保证"编码可替换"在载荷层同样成立
  (否则编码握手/业务载荷会硬编码 json)。

```yaml
内置 json codec (固定格式):
  {"id":"1","kind":"request","name":"greet.hello","payload":{...}}
  - payload 为内联 json; Encode 时原样嵌入字节, Decode 时取回 raw
扩展方式:
  - 新增编码 = 实现 Codec 并注册; 传输层与分派层零改动
```

### 5.3 多态分派

```yaml
注册表 (domain/bridge):
  Register(name string, factory func() any)   # 声明 name -> Go 类型
流程:
  收到帧 -> Codec.Decode -> Message
    -> 按 Name 取 factory -> 反序列化到该类型 (json.Unmarshal 到具体结构)
    -> 交 Mux 上该 Name 的 Handler
未注册的 Name: 协议错误 (返回 KindError; 不静默忽略)
说明: 这一层让"传输不认识业务类型"与"强类型处理器"同时成立
```

## 6. 统一抽象 (domain/bridge)

```go
// Peer 是一条已建立的桥接连接.
type Peer interface {
    Send(ctx context.Context, msg Message) error
    Receive(ctx context.Context) (Message, error)
    Close() error
    Remote() string
}

// Listener 接受被桥接进程的连接.
type Listener interface {
    Accept(ctx context.Context) (Peer, error)
    Addr() string
    Close() error
}

// Dialer 主动连接 (子进程侧, 或父进程回连).
type Dialer interface {
    Dial(ctx context.Context, addr string) (Peer, error)
}

// Handler 处理一条消息 (已在 Mux 内完成解码与类型化).
type Handler func(ctx context.Context, peer Peer, msg Message) error

// Mux 按消息名分派.
type Mux interface {
    Handle(name string, h Handler)
    Dispatch(ctx context.Context, peer Peer, msg Message) error
}

// Bridge 是桥接门面: 只管传输生命周期 (编码与分派由构造时注入).
type Bridge interface {
    Name() string
    Addr() string
    Listen(ctx context.Context) (Listener, error)
    Dial(ctx context.Context) (Peer, error)
    Rebind(ctx context.Context) error // 幂等: 解绑 + 重绑
    Close() error
}
```

- 门面保持精简: 编码/分派在**构造桥接时注入**, 不摊到接口上。
- 该抽象与具体传输无关: 未来若换 stdio/pipe, 只需新的 `Bridge` 实现。

## 7. 生命周期

```yaml
Name  : "bridge.<daemon>" (例: bridge.node) —— 引擎名在注册表中唯一
Deps  : ["config", "eventbus", "log", "settings", "store"]
Init  :
  - 取五引擎句柄
  - 解析 sock 名/编码/超时 (config 静态 + settings 可覆盖)
  - 构造 Codec 与 Mux, 注册业务处理器 (由接入方提供)
Start :
  - Rebind (确保目录 -> 清理陈旧 sock -> listen) 并记录日志
  - 启动接受循环 (每条连接一个读协程 + 一个写协程)
Stop  :
  - 停止接受 -> 关闭全部连接 -> 删除 sock (逆序且幂等)
监护 (具体引擎实现, 非核心):
  - 启动/守护子进程; 感知子进程退出
  - 子进程 down -> 恢复: Rebind() + 重连 + 重建会话 + 广播事件
```

## 9. 考虑要点

### 9.1 并发模型
- 每连接: 一个读协程 (Receive 循环 → 分派) + 一个写协程 (消费发送队列, 串行写)。
- 共享状态 (连接表/统计) 用锁或原子; 分派回调内不得阻塞写路径。

### 9.2 背压与上限
- 有界发送队列 + 显式策略 (阻塞 / 拒绝并报错); 不隐式丢弃。
- `maxMessageBytes` 上限, 超限明确报错 (避免大消息打爆内存)。

### 9.3 分帧与容错
- ws 天然分帧, 无需处理半包/粘包; 但 Codec 必须自校验 (非法帧 → 协议错误 + 日志)。
- 单条消息解析失败不应拖垮整条连接 (可选: 回 KindError 后继续)。

### 9.4 安全
- 目录 0700 / sock 0600, 仅本机可连; 不监听 TCP。
  - 现状: store 的 `fs.mkdir` 无权限字段, 目录实际为 0755; sock 由传输层 `chmod 0600`
    (连接权限的关键项成立)。要 0700 需给 `MkdirArgs` 加 `Perm` 字段。
  - "删除前校验确实是 socket" 由传输层 `os.Lstat` 完成 (store 的 `FileInfo` 暂无 `Mode`)。
- 是否加 token/握手鉴权见 §11。

### 9.5 关闭语义
- 顺序: 停止接受 → 关闭连接 → 删除 sock; 全部幂等, 支持多次调用。
- 对端断开: 该 peer 关闭并广播 `bridge.disconnected`; 是否重连由引擎决定。

### 9.6 可观测
- 只读 `Stats`: 连接数 / 收发行数 / 收发字节 / 解码失败 / 分派失败 (对齐 v4/v7 的 Stats 风格)。

### 9.7 与 spec 呼应
- **0 冗余**: 传输实现只一份 (`internal/ipc`), 多引擎共用。
- **不做代码预留**: 本次只做 ws over uds + json codec + 基础桥接; 进程监护留待具体引擎。
- **显式 > 隐式**: 编解码选择、背压策略、超时、上限全部显式声明。
- **考虑边界**: sock 陈旧/被占用、子进程 down、大消息、非法帧、并发写、关闭顺序。
