# SPEC - 开发规约

**!NOTICE: 这个文件不允许 ai 修改, ai 只读并严格遵循.**

## 目录

```yaml
l1:
  docs: 所有文档相关内容的目录
  src: 项目源代码目录
  readme.md: 仓库介绍
l2:
  src:
    frontend: 前端源码
    backend: 后端源码
    main.go: 程序入口, 嵌入入口
    data: 所有非源代码级别的数据文件存放位置, 以一级子目录为 domain 存储
    Makefile: 包含所有必要的指令
l3:
  data:
    conf: 所有配置文件
    <domain>: 领域数据文件
  backend:
    api: "对外暴露的接口, 通常可以是: cli, sdk, web等"
    domain: 领域层, 能力接口和默认实现, 无相互依赖
    engine: 实现领域的引擎
    service: 服务层, 编排引擎, 使其对外完成一系列服务
    internal: 内部调用模块, 通常为三方封装模块或者std增强, 实现特定功能
```

## 原则

1. SOLID 开发模式 + 20+ 设计模式.
2. 0 冗余:
- 只被调用一次的函数展开到调用函数当中, 没有复用的必要.
- 跨包复用的函数在 domain 层单开领域并走默认实现, 包内领域内聚能力, 避免冗余转化函数定义和调用.
- 不做代码预留, 避免死代码.
- 不做不可能逻辑兜底, 避免不必要覆盖.
- 不写多余注释, 代码清晰 >> 注释, 只在关键决策说明为什么.
3. 代码清晰:
- pub 定义在前, private 在后.
- 不做无意义的模块拆分.
- 业务string无硬编码, 非业务string无过度配置引入.
- 显式行为由于隐式操作.
4. 针对多种情况考虑周到, 考虑边界情况.
5. 代码风格:
- 所有New创建选项采用func option形式.
6. 超时处理:
- 所有的测试都需要设置最大超时时间避免无止境的等待.
- 永远不要针对大仓库做 tsc 的编译检查, 避免 io 和 cpu 瞬间打满.

## 选择

1. json: 配置, kv值防硬编码, 批量数据条目.
2. yaml: 结构化信息描述, 文件元信息.
3. *.sh: 复杂流程化脚本(批量测试, 环境检测等).
4. Makefile rule: 单步简单操作, 构建, 测试, sh启动器, 长指令压缩.
5. npm: 环境 pnpm 未安装, 包完整.
6. pnpm: 环境 pnpm 安装, 包完整.

## 样式(针对前端)

- 轻圆角(小值), 多处圆角统一.
- 溢出滚动, 父容器约束, 避免撑开问题.
- 长文本截断, hover tooltip 全显示.
- 合适的 gap, 避免组件黏连.
- 无副标题(不要开发时频繁加入信息副标题), 避免去除困难, 始终遵循加原则.

## 术语

- h: 水平
- v: 垂直
- l: 左
- r: 右
- u: 上
- d: 下
- h_l->r(...): 水平方向, 左对齐从左到右
- h_r->l(...): 水平方向, 右对齐从右到左
- v_u->d(...): 垂直方向, 上对齐从上到下
- v_d->u(...): 垂直方向, 下对齐从下到上
- [...]: 属性说明
