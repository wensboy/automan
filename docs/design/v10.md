# Automan 设计 v10 · 结构调整 (domain / internal / engine 三权分立)

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `v3`(引擎/依赖) + `v4`~`v9`(各引擎) + **当前代码实测盘点**
> 范围: 三类目录的职责边界、命名规范、依赖方向与逐项迁移映射. 非编码任务.
> 目标: 让"该放哪"有唯一答案, 且可被机器校验 (grep / build).

---

## 0. 核心原则 (本次调整的宪法)

```yaml
domain/:
  - 只定义: 接口, 结构, 类型, 常量, 全局变量
  - 不放任何"有逻辑的自由函数"(解析/构造/调用 domain 值的辅助)
internal/:
  - kits/ : package name 固定为 <domain>kit, 每个 domain 一个 (按需存在)
            (domain 解析 kit: 针对某个 domain 值的解析/构造/调用辅助)
  - 其它 : 语义明确的内部包 (禁止 tools / common / const / utils / helper 这类空泛名)
  - 内容 : "engine 需要复用的结构的实现" —— 结构具备独立性: 一个实例有完整上下文与操作,
            不同实例之间互不影响
engine/:
  - 只包含引擎的核心实现; 可复用结构一律下沉 internal
  - 每个 engine/<name>/ 下的所有内容"恰好实现一个有完整生命周期、实现 domain 接口的 engine"
```

### 由原则推出的两条硬规则 (必须写进规范)

```yaml
R1 依赖方向: kits 依赖 domain; domain 永不依赖 internal (含 kits)
   推论: "仅供 domain 自身声明使用"的构造器必须留在 domain
         (例: key.New —— 各 domain 用它声明 Key 全局变量)
         其余"消费/解析 domain 值"的辅助一律进 kit
   现状是有利的: domain 目前对 internal 的依赖为 0 (见 §2 证据), 迁移后仍为 0

R2 判定树 (这个类型/函数放哪):
   1) 它"描述"领域吗 (接口/结构/类型/常量/全局变量)?        -> domain/<x>
   2) 它是解析/构造/调用 domain 值的自由函数 (无状态)?        -> internal/kits/<domain>kit
   3) 它是有状态、可独立实例化、被多个 engine 复用的结构?     -> internal/<语义名>
   4) 它实现 domain 接口且有完整生命周期 (Name/Deps/Init/Start/Stop)? -> engine/<name>
   5) 它只是某个 engine 的内部实现细节?                      -> 留在 engine/<name> 内
```

## 1. 三类目录的最终形态

```yaml
domain/:                      # 纯声明 (零逻辑自由函数)
  bridge/  config/  context/  engine/  event/  key/  log/  settings/  srv/  store/

internal/:
  kits/                       # 无状态, 依赖 domain; 供 engine/service/api 消费
    bridgekit/  configkit/  enginekit/  logkit/  settingskit/  srvkit/  storekit/
  cast/                       # 无 domain 依赖的纯工具 (不叫 <x>kit: 它不解析 domain)
  fallback/  flat/  paths/    # 同上
  dispatch/                   # 复用结构: 指令队列 + 分区 worker + 处理器注册表
  ipc/                        # 复用结构: ws over uds 传输 + 编解码 + 握手 + Mux
  registry/                   # 复用结构: 引擎注册表 + 依赖拓扑加载
  error/                      # 进程级错误码注册表 (命名见 §8 待澄清)

engine/:                      # 每个子目录恰好一个 engine
  config/  eventbus/  runtime/  store/  log/  database/  settings/  bridge/  window/
```

## 3. 迁移映射 (逐项)

### 3.1 新增 `internal/kits/`

| 现状 | 目标 | 说明 |
|---|---|---|
| `domain/cast` (整个包) | `internal/cast` | 无 domain 依赖 → 普通内部工具, **不叫 castkit** |
| `domain/srv` 的 `Register/Of` | `internal/kits/srvkit` | `Key`/契约留在 srv |
| `domain/config` 的 `Get` | `internal/kits/configkit` | `Provider`/键留在 config |
| `domain/engine` 的 `Of` | `internal/kits/enginekit` | `Engine`/`Registry` 契约留在 engine |
| `domain/settings` 的 `Get/Set` | `internal/kits/settingskit` | 契约/键留在 settings |
| `domain/log` 的 `New/F` + `ParseLevel` | `internal/kits/logkit` | `Level/Record/Field/Logger/Out` 留在 log |
| `domain/store` 的 7 个 fs 便捷函数 | `internal/kits/storekit` | 指令/参数/结果/接口留在 store |
| `domain/store/db.go` 的 4 个 db 便捷函数 | `internal/kits/storekit` | `db.go` 文件随之移出 domain |
| `domain/bridge` 的 `Payload` + `WithConcurrent` | `internal/kits/bridgekit` | 契约/消息/协议常量留在 bridge |

```yaml
不建 kit 的 domain: context, event, key
  原因: 它们没有"消费侧自由函数" (context 有 Mode 常量; event 是类型+常量;
        key.New 属 R1 例外, 必须留 domain)
```

### 3.2 下沉复用结构

| 现状 | 目标 | 理由 |
|---|---|---|
| `engine/dispatch` (3 文件) | `internal/dispatch` | 队列/worker/注册表被 store 与 database 共用; 实例独立 |
| `engine/registry` (1 文件) | `internal/registry` | 引擎注册表被 runtime 复用; 不是 engine |

### 3.3 保持不动

```yaml
domain/* 的接口/结构/类型/常量/全局变量 (含 key.New)
engine/* 的 9 个 engine (含 runtime: 见 §5)
internal/{fallback,flat,paths,ipc,error}
service/ api/ bootstrap/ main.go (bootstrap 仍是唯一组合根)
```

## 4. 依赖方向 (迁移后的图)

```yaml
domain/<x>            -> domain/<y>                        (仅 domain 内部)
internal/cast|fallback|flat|paths
                      -> (无)
internal/kits/<x>kit  -> domain/<x>, domain/key, internal/cast|fallback
internal/dispatch     -> domain/{store,cast,context}
internal/ipc          -> domain/bridge, internal/paths|fallback
internal/registry     -> domain/{engine,context}
internal/error        -> (无)
engine/<name>         -> domain/*, internal/*(kits 或结构)
service/ api/         -> domain/*, internal/kits/*
bootstrap             -> 全部 (组合根)
```
```yaml
无环论证:
  - domain 不依赖 internal/engine/service (§2.4 grep 可验)
  - internal/kits 只依赖 domain 与其它 internal 工具包
  - 结构包 (dispatch/ipc/registry) 只依赖 domain 与工具包
  - engine 依赖 domain + internal; 无 engine -> engine 依赖
  - 因此依赖图分层为: domain < internal < engine < service < api < bootstrap
```

## 5. 校验手段 (把规范变成可执行检查)

```yaml
1) domain 纯度
   - 依赖: grep -rn 'backend/internal/' backend/domain/        # 期望: 空
   - 逻辑: grep -rn '^func [A-Z].*{' backend/domain/ | grep -v '^.*func ('   # 期望: 仅 key.New
2) internal 纯度
   - 禁名: ls internal 中不得出现 tools|common|const|utils|helper
   - kits : kits/* 的 package name 必须等于目录名, 且形如 <domain>kit
3) engine 纯度
   - 每个 engine/*/ 内必须且只能有一个类型实现 domain/engine.Engine 的五个方法
   - engine/*/ 不得出现"没有生命周期"的复用结构 (应下沉 internal)
4) 全局
   - go build ./... && go vet ./... && gofmt -l backend
```

## 7. 命名规范 (写进工程约定)

```yaml
允许:
  domain/<domain>            : 领域包 (小写单词, 一个词)
  internal/kits/<domain>kit  : 固定后缀 kit
  internal/<语义名>           : dispatch / ipc / registry / cast / fallback / flat / paths / error
  engine/<engineName>        : 引擎名 (与 Name() 一致或为其前缀)
禁止:
  tools / util / utils / common / misc / shared / helper / const / base / core
理由:
  - 空泛名会让"该放哪"重新变得主观, 并诱导把无关实现堆在一起
  - 语义名 (dispatch/ipc/registry) 同时表达了"它是什么结构", 便于复用与审查
```

## 8. 待澄清项

```yaml
- internal/error 的 package name: error 与内建类型同名 (调用处需别名),
  是否改为更具体的 internal/apperr? [改为 internal/err, 所有调用方同步]
- 是否要为"没有消费侧自由函数"的 domain 也建空 kit (context/event/key)?
  本设计按需创建 (不建空包). 若要求"每 domain 必有 kit", 则建 contextkit/eventkit/keykit 空包. [按需创建即可]
- key.New 留在 domain 属 R1 例外, 是否接受? (替代: keykit.New + domain 内声明的全局变量改用结构字面量) [考虑如果方法在 domain 内被其他package调用用于定义则无需迁移到 internal/kits下]
- engine/<name> 内的"暂时只被自己用"的通用结构 (log 的 ring buffer, settings 的 notify/views)
  是否现在就下沉 internal, 还是等第二个使用者出现? (本设计: 等复用出现再下沉) [等待复用后再下沉]
- engine/bridge 未来出现 daemon 变体 (engine/bridge/node) 时, 现有通用引擎是留在 engine/bridge
  还是整体下沉 internal/bridge? (按 R4/原则 3, 届时通用部分应下沉) [延迟通用部分下沉]
- storekit 是否拆分 (fs.* 与 db.* 两组)? (本设计: 同一 domain 一个 kit, 不拆) [可做文件级别的拆分, 不做package级别的拆分]
```
