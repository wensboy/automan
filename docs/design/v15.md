## 1. 目标与范围

```yaml
目标: 打通"前端设置弹窗 ↔ Wails 绑定 ↔ settings srv ↔ settings engine ↔ 用户目录落盘"全链路,
      做到: 读取生效值 / 修改 / 落盘 / 外部改动回流 四件事可用。

范围内:
  - 后端: 新增 settings 的 api(Wails 服务) 与 service(srv) 两层, 装配进 bootstrap
  - 后端: 首次运行把 data/schema/ 下的用户文件与 schema 同步到用户目录(当前无任何代码做这件事)
  - 后端: 写入前的校验(依据 settings.user.schema.json)
  - 前端: 把 lib/settings.ts 的 load/save 从 dev 占位换成真实 binding 调用, 并订阅后端事件

范围外:
  - 设置项本身的增删改(仍由前端 static/default/settings.json 描述, 后端不做 UI 描述)
  - data/conf/*.json 程序配置(带 meta.namespace, 与 UI 展示无关, 保持现状)
  - 主题/语言等设置项的"真正生效"(本次只到落盘与回流; 生效逻辑另开)

已具备(不自造): engine/settings 已是可用的运行态引擎 —— 三视图 + 轮询监听 + 原子落盘 + 事件;
              缺的只是"对前端的一层"和"初始化同步"。
```

## 4. 对外接口契约(Wails 服务 → 前端)

```yaml
List(ctx) -> map[string]Entry                       # 一次拿全量生效值, 避免 N 次往返
  Entry = { Value any; View string }                # View: runtime|user|bottom|none (前端可提示"来源")
  # 实现: 遍历"描述键集合"(见第 5 节), 对每个 key 调 engine.Get / engine.View

Get(ctx, key) -> Entry

Set(ctx, key, value any) -> error                   # 只写 runtime 层(进程内), 不落盘
Reset(ctx, key) -> error                            # 抹掉 user+runtime 覆盖, 回落 bottom
Apply(ctx, patch map[string]any) -> error           # 批量 Set (前端 Save 用; 键值经校验)
Save(ctx) -> error                                  # 落盘当前 overrides (engine.Save)

错误: 统一的 err 约定(见第 10 节), 不 panic、不静默
```

前端调用形态(替换 `lib/settings.ts` 的两个函数):

```ts
import { List, Apply, Save } from "@/../bindings/github.com/wensboy/automan/backend/api/settings"
// hmm: 生成路径为 <module>/<pkg>, 前端用相对/别名引用; 具体路径在实施时以生成为准

loadSettings()  -> List()              # 得到 { key: { value, view } } 并摊平成 values
saveSettings(d) -> Apply(d) + Save()   # 先写 runtime 再落盘, 落盘成功由后端发事件
```

## 5. 描述键集合与默认值来源(需要你定, 见第 12 节)

问题: `bottom` 层目前来自 `conf/settings`(只有 watchMs/debounceMs/lastGreet)。
UI 键(`appearence.mode` / `general.language`)在 backend 侧没有默认值来源, 而前端按约定
**不参与默认值** —— 所以默认值必须在后端侧有出处。三个候选:

```yaml
候选 A: 用户文件模板兼作默认层
    data/schema/settings.user.json 当前内容 = { appearence.mode: "auto", general.language: "English", ... }
    正是这两个 UI 键的默认值 -> 作为 bottom 的第二个来源参与叠加
    优点: 零新增文件, 模板/默认/首次写入三件事同一份数据
    注意: 需与 conf/settings 的 bottom 合并(程序键来自 conf, UI 键来自模板)

候选 B(选择): 新增 data/defaults/settings.user.json 专作默认层, 模板与默认分离
    优点: 语义最清晰(默认值不许被用户文件形状影响); 代价: 多一份文件要同步

候选 C: 把 UI 键的默认值写进 data/conf/settings.json
    不推荐: 你已明确带 meta.namespace 的是**程序配置、与 UI 展示无关** —— 混进去会破坏这条边界
```

"描述键集合"(哪些 key 允许读写、类型是什么)的来源同样有三条路:

```yaml
路线 1(选择): 以后端 schema 为准 —— data/schema/settings.user.schema.json 决定允许的键与类型
              前端 settings.json 只决定"用哪个控件展示"; 两侧键名一致(点号路径), 类型一致
路线 2: 前端把 settings.json 的描述一并下发给后端(Set 时带 type) -> 后端信任前端
路线 3: 后端单独维护一份键表 -> 三处描述(前端/schema/后端), 不推荐
```

## 6. 初始化与文件系统同步(缺口 1)

```yaml
时机: settings 引擎 Init 之前(bootstrap 内, 或独立小步骤), 因为引擎启动就会读用户文件
动作:
  1) 确保 <UserConfigDir>/automan 存在
  2) 若 <UserConfigDir>/automan/settings.json 不存在 -> 从 data/schema/settings.user.json 拷入
  3) 若 <UserConfigDir>/automan/settings.user.schema.json 不存在 -> 从 data/schema/… 拷入
     (用户文件里的 "$schema": "./settings.user.schema.json" 依赖二者同目录)
  4) 升级场景: schema 版本变化时的策略待定(见第 12 节问题 C)

实现: 用 storekit 抽象(与引擎一致, 走 store.CmdWrite)而非直接 os.* —— 保证与落盘路径同一套;
      data 已通过 //go:embed data 打进二进制(src/main.go:14-15), 因此读取用 embed FS 即可
```

## 7. 校验

```yaml
写入前(Set/Apply):
  - 键必须在"描述键集合"内, 否则拒绝(错误码见第 10 节)
  - 值类型必须与描述一致: 标量 / enum<T> 必须落在枚举内 / array<T> 元素类型逐一校验
  - 依据: data/schema/settings.user.schema.json(JSON Schema draft 2020-12)
          -> Go 侧需引入校验库(候选: santhosh-tekuri/jsonschema/v6) —— 见第 12 节问题 D
落盘前(Save):
  - 用整份 schema 校验"合并后的用户文件文档"(overrides + 必要结构), 再走 storekit.Write
读入时(loadUser):
  - 校验失败不致命: 记录 warn + 跳过非法键(保持引擎现有"不让用户文件把应用搞崩"的取向)
```

## 8. 事件回流

```yaml
现状: window 引擎转发 settings.changed / settings.reloaded(window.go:60-61,130,138);
      settings.loaded / settings.saved **未转发**(settings.go:117 / persist.go:61 有 emit)

建议(考虑): 前端 Save 后最关心"已落盘", 因此补转发 settings.saved -> "settings:saved";
               load 时机的前端刷新也可以靠它, 但更简单的是前端自己在 Apply 后重新 List 一次。

前端订阅: 用 @wailsio/runtime 的 Events.On("settings:changed"/"settings:saved"/"settings:reloaded"),
         刷新本地 values(外部改文件时, 轮询检测 -> reload -> 事件 -> 弹窗自动更新)。
```

## 9. 落盘与一致性

```yaml
不变的部分(直接复用, 不改引擎):
  - 原子写: 临时文件 + rename (engine/store/fs.go:170-189)
  - promote(): 落盘成功后 runtime 并入 user 并清空 runtime (views.go:72-79, persist.go:58)
  - 自写抑制: stampNow() 避免把自身写入当成外部变更 (watch.go:40-46)
  - 退出重试: Stop -> saveWithRetry (3 次 / 200ms)

新增约定:
  - 前端 Save = Apply(runtime) + Save(落盘) 两步; 只 Apply 不 Save 属于"进程内临时值"
  - 并发: 引擎内部已有锁; srv 层不再加锁, 只做转发与校验
```

## 13. 实施步骤(第 ③ 步, 待你确认后执行)

```yaml
step1: service/settings(srv) + api/settings(Wails 服务) + bootstrap 装配; 仅实现 List/Get(读链路)
step2: 生成 bindings, 前端 lib/settings.ts 的 loadSettings 换成 List(); 验证弹窗能显示后端下发的值
step3: Set/Apply/Save(写链路) + 校验 + 落盘; 前端 saveSettings 换成 Apply+Save
step4: 初始化同步(data/schema -> 用户目录), 验证首次运行与升级路径
step5: 事件订阅(前端自动刷新), 验证"外部改文件 -> 弹窗自动更新"
step6: 清理: 删除 mock/settings.ts; 更新 v14.md 的设置链路章节(标注已接真实后端)
```

验收标准:

```yaml
- 首次运行: 用户目录自动出现 settings.json 与 settings.user.schema.json
- 弹窗显示值 = 后端 List() 结果(而非前端占位)
- 改值 + Save: 用户文件内容随之变化(只含覆盖键), 重新打开弹窗值保持
- 外部改用户文件: watchMs 轮询发现 -> 前端收到事件 -> 弹窗值自动刷新
- 非法输入(未知键 / 枚举越界 / 类型不符): 被后端拒绝并给出明确错误
- 退出应用: 有未落盘的 runtime 覆盖时, Stop 路径重试落盘成功
```

## 14. 风险与取舍

```yaml
- 轮询监听(watchMs=2000)意味着"外部改动回流"有最多 2s 延迟; 若要即时, 需换 fsnotify(不在本方案内)
- 用户文件混放程序键与 UI 键(第 12 节 B): 若拆文件, 引擎需多实例或按命名空间路由
- schema 校验库引入会增大后端依赖; 若你倾向零依赖, 校验强度会下降(见 D)
- bottom 层若不引入 UI 键默认值(候选 A/B 都不做), 则首次运行前弹窗会显示占位符 "—"(前端不造默认值)
```

## 20. 修复: 打开设置崩溃 `field.label.split` 报 undefined

```yaml
现象: 点击 Settings 直接抛 "undefined is not an object (evaluating 'field.label.split')"。
根因(数据形状与契约不一致, 两个错误叠加):
  1) 契约(src/static/types/settings.ts + lib/settings.ts 的 isFieldNode): 字段是**平铺**的
     —— { key, label, description, type, options?/range? } 同级;
  2) 实际 static/default/settings.json 写成了 { key, label, description, value: { type, options } };
  3) isFieldNode 只看 node.type -> 父节点不算字段 -> 递归进入 value;
     value 对象**有 type** 且无 key/label -> 被当成字段 -> 渲染时 label 为 undefined -> 崩。
修复:
  · 数据: 把 settings.json 的 value 层平铺(本轮 8 个配置项), 与契约一致;
  · 代码: isFieldNode 收紧 —— 必须同时有 key(字符串) 与 label(字符串) 才算字段,
    不符合的节点(如旧格式残留)不会被渲染, 从根上避免同类崩溃;
    __schema__ 注意: 这是**防御性收紧**, 正常数据不会因此少显示任何配置项。
验证: tsc 0 / build ✓; 8 个配置项全部被识别为字段(脚本核对); 后端未改动(13 包全过)。
```
