# Automan 设计 v7 · settings 引擎

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v2.md` (config ≠ settings) + `v4` (store) + `v5` (log) + `v6` (database) + 当前骨架
> 范围: **settings 引擎** —— 运行期动态的业务设置; **三视图叠加** + **HMR** + **退出/手动落盘** + 事件与日志.
> 目标: 明确视图模型、契约、事件、生命周期与协作方式. 非编码任务.
> 落位: `backend/domain/settings`(已有) 与 `backend/engine/settings`(已有薄实现).

---

## 0. 定位与边界

```yaml
依赖: [config, store, log, eventbus]
核心:
  - 运行期可变、且"属于业务"的设置; 支持 HMR (外部编辑文件 -> 自动重载)
  - 退出前同步到 <UserConfigDir>/automan/settings.json (用户 settings.json); 也支持运行期手动保存
  - data/conf/settings.json 定义所有同 key 的默认值 (只读底层视图)
  - 加载/变更/重载经 ebus 广播; 必要操作记日志
与 config 的区别 (v2 已定, 此处复述约束):
  config  : 程序自身的控制状态, 启动期固定加载, 只读, 无通知
  settings: 业务运行态, 运行期可变, 可写, 有通知, 需持久化
不是:
  - 不是 config 的替代/缓存; 不改写 data/conf/*.json
  - 不做 schema 校验器/迁移工具 (见 §12)
  - 不负责"引擎自身参数" (如上轮询间隔), 见 §12
```

## 1. 核心观点

### 观点 A — 三视图叠加 (runtime > user > bottom)

- 同一个 key 的值由三层决定, 高优先层"覆盖"低优先层, 而不是合并对象:

```yaml
runtime (内存):            运行期由接口写入 (通常来自 UI 设置更新) —— 优先级最高
user   (用户文件):         运行期落盘/外部编辑的显式覆盖项 —— 次之
bottom (内嵌默认):         data/conf/settings.json, 定义所有 key 的默认值 —— 兜底
生效值 = runtime[key] ?? user[key] ?? bottom[key]
```

### 观点 B — 三层各有唯一职责

```yaml
bottom: 只要"加载" —— 编译期内嵌, 启动期由 settings 引擎读入并平铺, 之后静止
user  : 要"监听"   —— 允许外部编辑, 需要变更检测 -> 自动 HMR
runtime: 由"接口"驱动 —— Set(key,v); 是唯一可被 UI 直接改写的层
```

### 观点 C — 变更即事件

- 加载、runtime 变更、外部重载、落盘完成都经 ebus 广播; 其他引擎**靠订阅事件**响应动态变更, 而不是轮询或反向依赖。

### 观点 D — 落盘是显式的

- 两个触发点: **退出前**(Stop 末次落盘) 与 **手动 `Save()`**; 不做隐藏的定时落盘。
- 写回目标是**用户层文件**: 把 user + runtime 叠加后写回, 使显式覆盖项持久化。

### 观点 E — 复用既有引擎, 不自建第二套能力

```yaml
config  : 底层视图的加载与平铺 (conf/settings.*)
store   : 用户文件的读/写/原子写 (fs.write = temp+rename) 与 Stat (变更检测)
log     : 必要操作日志 (加载/落盘/重载/失败)
eventbus: 广播与订阅
```

## 2. 三视图模型

### 2.1 视图定义

```yaml
bottom (data/conf/settings.json):
  位置: 编译期内嵌 (//go:embed data)
  形态: 嵌套 JSON + meta.namespace = "conf/settings"
  载入: 启动期由 config 引擎加载并平铺 -> 叶子键 conf/settings.<path>
  访问: config.Lookup("conf/settings." + key)   # 复用配置引擎, 不另写 loader
  性质: 只读, 生命周期内不变化

user (<UserConfigDir>/automan/settings.json):
  位置: 用户可写目录 (与 store/database 同一根解析规则)
  形态: 与 bottom 同构的嵌套 JSON, 无 meta (手改友好)
  载入: 启动期读取一次
  监听: 运行期轮询 Stat 检测外部编辑 -> 重载 (HMR)
  性质: 只记录"显式覆盖项", 不物化默认值

runtime (内存 map):
  形态: map[string]any
  写入: 仅经引擎接口 Set (UI/服务调用)
  性质: 启动为空; 落盘后清空 (见 §7)
```

### 2.2 key 与 json 路径的关系 (重要约定)

```yaml
约定: settings 的 key 名 == 该 key 在 settings.json 中的路径 (点号分隔)
  例: key "lastGreet"        <-> {"lastGreet": "world"}
      key "window.width"     <-> {"window": {"width": 800}}
  对应 config 叶子键: conf/settings.lastGreet / conf/settings.window.width
好处:
  - 三层视图与配置文件 1:1 对应, 无隐式前缀裁剪
  - 底层视图直接来自 config 引擎的既有平铺结果 (零新增 loader)
注意:
  - 现网键名 `settings.lastGreet` 需去掉冗余前缀 (见 §12)
```

### 2.3 读取解析

```
Get(key):
  runtime[key] ? --> 返回
  user[key]    ? --> 返回
  bottom[key]  ? --> 返回
  否则: 未命中 (ok=false)
```

## 3. 契约 (domain/settings)

```go
// domain/settings —— 纯契约
type Store interface {
    Get(name string) (any, bool)   // 三层叠加后的生效值
    Set(name string, v any) error  // 写 runtime 层 (最高优先) + 广播变更
    Save() error                   // user + runtime 叠加回写用户文件
    Reload() error                 // 重新读取 user 层 (HMR 语义的显式触发)
}

// 类型化辅助 (保持既有风格)
func Get[T any](s Store, k key.Key[T]) (T, bool)
func Set[T any](s Store, k key.Key[T], v T) error
```

- 契约面刻意保持很小: 三层细节不外泄; 调用方只面对 `Get/Set/Save/Reload`。
- 业务键在各 domain 包以 `key.Key[T]` 显式声明 (沿用 `key.New` 基元)。

## 4. 事件 (ebus)

```yaml
topics (集中在 domain/event/topic.go):
  settings.loaded   : 启动装配完成
  settings.changed  : runtime 层变更 (UI/服务写入)
  settings.reloaded : 外部编辑触发的重载 (HMR)
  settings.saved    : 叠加回写用户文件完成

载荷 (定义在 domain/event/event.go):
  SettingsLoaded   { Keys int }
  SettingsChanged  { Key string; Value any }        # 在既有 {Key} 上扩展
  SettingsReloaded { Keys int; Err string }         # 失败也广播 (Err 非空)
  SettingsSaved    { Keys int }
```

```yaml
其他引擎如何响应动态变更 (本设计的简单方案):
  - 需要感知的引擎: 在 Init 取 settings.Store 句柄 (或仅 ebus)
  - 订阅 settings.changed / settings.reloaded, 按 key 做局部重建
  - 与已有做法一致: window 已把 settings.changed 转发给前端
约束:
  - settings 不反向调用其他引擎的业务方法 (只广播)
  - 订阅回调内不得阻塞 (广播是同步派发)
```

## 5. 生命周期

```yaml
Name : "settings"
Deps : ["config", "eventbus", "log", "store"]
Init :
  - 取 config / store / log / eventbus 句柄
  - 装配 bottom 视图 (经 config 命名空间 conf/settings)
  - 解析用户文件路径 (<UserConfigDir>/automan/settings.json)
Start:
  - 读取 user 视图 (文件不存在 -> 视为空, 不报错)
  - 启动外部变更监听 (轮询)
  - 广播 settings.loaded
Stop :
  - 停止监听
  - 末次落盘 (叠加回写) -> 广播 settings.saved
  - 清理内存视图
```

```yaml
顺序保证 (来自依赖图):
  config/eventbus -> store -> log -> settings
  停机逆序: settings 先停, 其依赖 (store/log/config/ebus) 仍在 -> 末次落盘可用
```

## 6. 变更检测 (HMR)

```yaml
检测手段:
  方案A (本设计默认): 轮询
    - 经 store.Stat(用户文件) 比较 (mtime, size)
    - 无新依赖; 复用 store 引擎; 间隔为引擎内置常量 (可讨论外置, 见 §12)
  方案B (待评估): fsnotify 等文件系统事件
    - 实时性好, 但引入新依赖与平台差异

重载流程:
  Stat 变化 -> store.Read 用户文件 -> 解析 -> 替换 user 视图 -> 广播 settings.reloaded

自触发抑制:
  Save 写完文件后立刻记录新的 (mtime,size), 避免把自己写的内容当成外部编辑再重载一次

容错:
  文件不存在        : 视为空 user 视图 (首次运行, 静默)
  JSON 非法/结构异常: 保持旧 user 视图不变, 记日志 Warn/Error, 不改变生效值 (fail-safe)
  读取失败          : 保持旧视图 + 记日志 Error
```

## 7. 落盘与原子性

```yaml
写入内容:
  merge(user, runtime) —— 仅"显式覆盖项"的并集 (runtime 覆盖 user)
  不物化 bottom 默认值 -> 升级后默认值变化仍能自动生效

写入方式:
  经 store 的 fs.write (temp + rename) -> 原子替换, 不产生半截文件
  写入前确保目录存在 (store 已保证)

写入后:
  runtime 视图清空 (其内容已进入 user 层), 脏标记置 false   # 见 §12
  更新 (mtime,size) 记录 -> 抑制自触发

失败处理:
  写入失败 -> 保留 runtime (不丢未保存变更) + 日志 Error + 返回错误
  手动 Save 的失败对调用方可见; 退出路径的失败只记日志 (已无处上报)
```

```json
// <UserConfigDir>/automan/settings.json 形态示例 (与 data/conf/settings.json 同构)
{
    "lastGreet": "world",
    "window": { "width": 1024 }
}
```

## 8. 日志与错误

```yaml
Info : 装配完成 (key 数), 落盘完成 (key 数), 外部重载完成 (key 数)
Warn : 用户文件不存在 (首次), 非法 JSON (忽略本次)
Error: 用户文件读取失败, 落盘失败
实现 : Init 取 log.Logger, 各动作完成后 Deliver (v5 契约)
错误 : 复用 internal/error; 后续补 settings 分段 code (加载/落盘/解析)
```

## 11. 考虑要点

### 11.1 并发
- `Get/Set`、监听重载、落盘三处并发访问视图; 统一由引擎内 `sync.RWMutex` 保护。
- `Get` 在锁内取值即返回 (值不可变引用), 避免长时间持锁。

### 11.2 事件去抖
- 高频 `Set` (如拖拽滑块) 会连发 `settings.changed`; 订阅方 (前端转发) 可能被淹没。
- 方案: 引擎侧不做隐式去抖 (显式 > 隐式), 由**订阅方**自行合并; 若确需, 后续可加显式选项 (见 §12)。

### 11.3 一致性
- 落盘失败绝不丢弃 runtime (未保存变更必须保留)。
- 重载失败绝不改变已生效值 (fail-safe)。

### 11.4 首次运行与默认值漂移
- 用户文件不存在 = 空 user 视图, 不报错; 首次 `Save` 时创建。
- 不物化默认值 -> `data/conf/settings.json` 的默认值变更能自然生效。

### 11.5 只读边界
- `Set` 只写 runtime 层; bottom (内嵌) 永久只读; user 层只由 `Save`/外部编辑改变。
- 不允许绕过引擎直接改用户文件 (会有既成事实: 引擎下次检测到并重载)。

### 11.6 类型
- 经 config/JSON 读来的数字为 `float64` / 数组为 `[]any`; 由 `cast.As[T]` 统一转化 (既有约定)。

### 11.7 与 spec 呼应
- **0 冗余**: 不新写 loader (复用 config)、不新写文件 IO (复用 store)。
- **不做代码预留**: 只实现 Get/Set/Save/Reload; 不做 schema/迁移/加密。
- **显式 > 隐式**: 覆盖关系、落盘时机、检测间隔、容错行为全部显式声明。
- **考虑边界**: 首次运行/非法 JSON/写入失败/并发/事件风暴/默认值漂移。
