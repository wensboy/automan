# Automan 设计 v12 · bridge/ipc 重写 (peer 与 engine 解耦)

> 状态: 设计草案 (Design, 不含实现) —— **本版为完整重写**, 前一版 (流对象/多态编码协商/Transport 抽象) 的思路已部分推翻
> 依据: 现有实现 (`domain/bridge`、`internal/ipc`、`internal/kits/bridgekit`、`engine/bridge`) + v9 (引擎编排) + 本轮补充
> 目标: 用"两个对象 + 一个固定帧标准"把 ipc 层与业务层彻底解耦, 明确必要的细节. 非编码任务.

---

## 0. 范围与现状

```yaml
核心处理: golang 父进程 (server) 与 node 子进程 (client) 之间的通信
使用技术: ws over uds
依赖引擎: [config, settings, log, eventbus, store, database]
本轮只聚焦: ipc 层 (peer) 与 bridge engine 的职责划分、消息/帧规范、生命周期
```

现有实现里存在**过耦合与多余抽象**, 本轮据此收敛 (见 §10 删除清单):
`Transport` 契约、`Framing` 契约、`Listener/Dialer`、`Caller/Dispatcher/Result/Call`、
在飞表与自动应答、编码协商字段 —— 都属于"不必要的抽象/概念", 予以移除或下沉。

## 1. 对象模型

```yaml
ipc 层 (internal/ipc):  只做传输, 近似 socket
  peer   : 一条连接。Read(收)/Write(发)/Close/Local/Remote
  server : 服务端连接创建面。Bind(/Listen)/Accept/Addr/Close  -> 产出 peer
  client : 客户端连接创建面。Connect -> 产出 peer
  帧     : 固定的 message 编解码标准 (§4), 对业务无感

引擎层 (engine/bridge): 只做业务与编排
  业务处理      : 把业务信息编成"负载", 交给 peer; 收到 peer 的消息后按 name 分派
  负载编解码    : 业务层标准 (§5), 与 ipc 帧标准相互独立
  peer 生命周期 : 何时 listen / connect / rebind / close 全部由引擎决定
  子进程编排    : 启动/守护/退出感知/恢复 (v9 不变)
```

| | peer (ipc) | bridge engine (业务) |
|---|---|---|
| 认识 message/packet | 是 (id + 一段字节) | 是 (kind/name + 业务数据) |
| 解析负载内容 | **否** | **是** |
| 按 name 分派 | **否** | **是** |
| 编解码业务负载 | **否** | **是** |
| 决定何时建连/断连 | **否** (被动执行) | **是** (持有生命周期) |
| 处理子进程 | 否 | 是 |

### 数据流 (本轮补充里的链路)

```
bridge engine (server, parent)           node runtime (client, child)
        |                                          |
        | 业务负载 编码                              | 业务负载 解码
        v                                          ^
      peer --(message 标准: id + payload)--> peer   |
        |                                          |
        +------------ ws over uds ----------------+
```

```yaml
正向: 业务 -> engine 负载编码 -> payload -> peer 封装 message -> 帧标准 -> 字节
反向: 字节 -> 帧标准 -> message -> peer -> engine 解负载 -> 按 name 交业务
关键: peer 只认 "id + 一段字节"; engine 只认 "kind/name + 业务数据"; 二者以 payload 衔接。
```

## 2. 时序 (连接建立到关闭)

```
      服务器 (go, parent)                    客户端 (node, child)
            |                                        |
            |-- bind(<automan>/bridge/x.sock)        |     [engine 触发, peer 执行]
            |-- listen()                             |
            |                                        |
            |<--------------- connect() -------------|
            |<--------- HTTP Upgrade 请求 -----------|
            |---------- 101 Switching Protocols ---->|
            |                                        |
            |<--------- WebSocket 帧(请求/事件) -----|
            |---------- WebSocket 帧(响应/事件) ---->|
            |<--------------- Ping ------------------|
            |---------------- Pong ----------------->|
            |                                        |
            |<--------------- 关闭帧 -----------------|
            |---------------- 关闭帧 --------------->|
            |                                        |
            |-- close()                              |-- close()
            |-- unlink(socket 文件)                  |
```

| 步骤 | 归属 | 说明 |
|---|---|---|
| bind / listen / unlink / 陈旧 sock | **ipc** (server) | 目录经 store 创建; 权限 0600; 陈旧 socket 清理见 §7 |
| connect / HTTP Upgrade / 101 | **ipc** (client/server) | ws 握手是**传输层内部**行为, 与业务无关 |
| 何时 bind、何时关闭、何时重绑 | **engine** | 引擎编排 (启动/停机/子进程 down 后恢复) |
| 帧的编解码 | **ipc** | 固定标准 (§4) |
| 帧内 payload 的含义 | **engine** | 业务负载 (§5) |
| Ping/Pong | **ipc** | 心跳与空闲判定属传输控制 (§7.3) |
| 关闭帧 / close | **ipc** | `Close()` 幂等 |

## 3. 两层编码: 各自固定, 不协商

```yaml
ipc 帧标准 (peer):      由 ipc 实现决定, 选定后不变。类比 tcp 的边界规范 / http 的报文规范
业务负载 (engine):      由协作双方约定 (本项目 json), 升级时整体变更

原则:
  - 能否解码取决于编码实现本身; http/tcp 都不协商编码, 有规范就能从字节解析出来
  - 多态 = 同一标准的多种实现, **选定即固定**, 不是"能换就换"
  - 所以: 消息上不需要 codec 字段; 握手不协商编码, 只做版本/身份自检
  - 需要换编码时走"协议版本升级"(ProtocolVersion), 而不是每连接协商
```

## 4. 帧与消息 (ipc 层)

```go
// domain/bridge —— 帧内容: 只有传输规范要求的字段
type Message struct {
    ID      string // 连接内多路寻址(帧归属); 传输只透传, 不解释
    Payload []byte // 不透明字节 (= engine 的负载编码结果)
}

// Peer: 近似 socket 的连接
type Peer interface {
    Read(ctx context.Context) (Message, error)
    Write(ctx context.Context, msg Message) error
    Close() error
    Local() string
    Remote() string
}
```

### 4.1 帧标准 (内置 json)

```yaml
{"id":"<关联 id>","payload":"<base64>"}
```
```yaml
为什么 base64: 两层编码独立, 业务负载以后可能不是 json (二进制等), 传输不能假设其格式;
              用 base64 承载"不透明字节"即可, 代价 +33% 体积 (本地通道可接受)。
备选 (一行说明, 实现时二选一): 二进制帧 = [idLen][id][payload], 零开销、更贴近 tcp。
不做: kind / name / codec 字段 (它们要么属业务, 要么是固定标准不需要声明)。
```

### 4.2 传输层不过问的事

```yaml
不判断 kind, 不按 name 分派, 不维护"流"状态, 不解析/协商编码
只做: 连接创建 (被动 bind/listen/accept, 主动 connect) / 帧编解码 / 收发 / 心跳 / 关闭
```

## 5. 业务负载 (engine 层)

```go
// domain/bridge —— 协议段 (engine 与对端 node 共同遵守的业务标准)

// Kind 是消息类型: 流只是其中一种, 由业务层解释
const (
    KindStream Kind = "stream" // 1:n / n:n 关系 (流的唯一含义)
    KindEvent  Kind = "event"  // 单向通知
    KindError  Kind = "error"  // 失败 (Data 为原因)
)

// Envelope 是负载内的信封 (业务标准 = json)
type Envelope struct {
    Kind Kind   `json:"kind"`
    Name string `json:"name,omitempty"`
    Data []byte `json:"data,omitempty"`
}

// Packet 是引擎交给业务的一条消息
type Packet struct {
    ID   string
    Kind Kind
    Name string
    Data []byte
    Codec Codec // 供业务层解码 Data
}

// Outgoing 是业务要发出的一条消息 (ID 空则引擎生成)
type Outgoing struct {
    ID   string
    Kind Kind
    Name string
    Data any
}
```

```yaml
流语义的落法 (业务层, 引擎不参与):
  1:1  发一条(id=X, kind=stream) -> 对端回一条(id=X)
  1:n  发一条(id=X)             -> 对端回 0..n 条(id=X) -> 业务按约定终止
  n:n  双方各自发多条(id=X)      -> 任一方按约定终止
引擎的保障只有三条 (属传输/编排, 不属流):
  - 同连接内帧顺序 = 发送顺序 (单写泵)
  - 按 name 精确分派; 未注册 name -> 丢弃 + 计数 + 日志
  - 连接断开 -> 广播事件, 未完成消息的归宿由业务层决定
```

## 6. 契约与构造 (最小集)

```go
// domain/bridge —— 契约 (只留必要的)
type Message          // 帧内容 {ID, Payload}
type Peer             // 连接 {Read, Write, Close, Local, Remote}
type Codec            // 业务负载编解码 {Name, Encode(v), Decode(data, into)}
type Envelope / Kind / Packet / Outgoing
type Sender  interface { Send(ctx context.Context, p Outgoing) error }
type Handler func(ctx context.Context, p Packet) error
type Receiver interface { Handle(name string, h Handler, opts ...HandleOption) }

// internal/ipc —— 构造与传输对象 (直接把 ipc 的实现暴露给引擎, 不再套一层契约)
func Listen(opts ...Option) (*Server, error)      // bind + listen (+ 陈旧 sock/权限)
func Connect(ctx context.Context, opts ...Option) (bridge.Peer, error)
type Server struct{ /* Accept(ctx) (bridge.Peer, error); Addr() string; Close() error */ }
type Option func(*peerConfig)                     // WithPath/WithStore/WithRooter/
                                                  // WithMaxMessageBytes/WithHeartbeat/...
```

```yaml
说明: 引擎持有 *ipc.Server 并决定何时 Listen/Close/Rebind —— "peer 生命周期控制"属引擎 (§1)。
      因此不再需要 Transport 契约 (它会引入第二套生命周期语义)。
```

## 7. 生命周期与传输控制

### 7.1 服务端 (engine 编排, ipc 执行)

```yaml
启动: 引擎 Rebind -> ipc.Listen: 确保目录(store) -> 处理已存在 sock -> listen -> chmod 0600
陈旧 sock: 存在且"可连通" -> 报错退出 (不抢占存活实例);
           存在但连不通 -> 校验确实是 socket -> 删除 -> 重新监听
停机: 引擎 Close -> 停止 accept -> 关闭连接 -> 关闭监听 (unlink socket 文件)
恢复 (子进程 down): 引擎感知退出 -> 重启子进程 -> Rebind (重绑) -> 等待子进程重连
```

### 7.2 客户端 (node 侧同构)

```yaml
connect -> 若 sock 不存在/连不上 -> 由 node 侧重试 (引擎不代劳)
关闭 -> 关闭帧 + close (幂等)
```

### 7.3 传输控制 (属 peer)

```yaml
单写泵     : 所有写经一个有界队列串行化 (= 显式背压), 顺序保持
心跳       : 按间隔发 Ping, 超时未回 Pong -> 关闭连接 (间隔 0 = 关闭心跳)
读上限     : MaxMessageBytes, 超限报错 (不截断)
关闭语义   : Close 幂等; 先尽力冲刷队列再断开
错误       : 传输只报传输错误 (断开/超限/编解码失败/未连接)
```

## 8. 引擎职责 (bridge.<daemon>)

```yaml
Name/Deps : "bridge.<daemon>" / [config, settings, log, eventbus, store, database]
Init      : 取依赖引擎; 解析 conf/bridge.<daemon>; 构造业务 Codec; 装配(不启动)
Start     : (可选)启动子进程 -> Rebind -> accept 循环 -> 握手 -> 进入分派
Stop      : 停止 accept -> 关闭 peer -> 终止子进程 -> 关闭监听 (幂等, 逆序)
Send      : 业务负载编码 -> Outgoing -> peer.Write
Handle    : 按 name 注册处理器; 收到消息 -> 解 Envelope -> 交给处理器
握手      : 会话建立后、进入分派前: 交换 {daemon, codec?, version, token}, 只做自检
日志      : 启动/停机/连接/断开/握手失败/未注册 name/子进程退出 (logkit)
事件      : bridge.connected / disconnected / error (eventbus)
Stats     : 连接状态/子进程状态/发送/接收/丢弃 (只读快照)
```

## 10. 明确不做 (本轮删除的抽象与概念)

```yaml
- Transport 契约                     -> 引擎直接编排 peer 生命周期
- Framing 契约 + 按名注册            -> 帧是 ipc 的内部固定标准
- Listener / Dialer 契约             -> 收进 ipc (Server / Connect)
- Caller / Dispatcher / Result / Call / ProgressFunc -> 由 Send/Handle + Packet 取代
- 在飞表 + "计划 -> 完成" 1:1 校验    -> 引擎不做配对, 关联由业务层用 id 自决
- 引擎自动回送"完成"                 -> 需要应答的处理器自己 Send
- 编码协商字段 / 每消息 codec         -> 两层编码各自固定 (§3)
- Stream 对象 / Open / Accept 流编排  -> 流只是一种消息类型 (§5)
```

## 11. 待澄清项

```yaml
- 帧标准: json+base64 (本设计) 还是二进制帧 [idLen][id][payload]? [当前考虑 json + base64 即可]
- Envelope.Data: []byte (json 下 base64) 还是 json.RawMessage (零开销但绑定 json)? [考虑 json base64 用于后续快速切换到其他编解码器]
- 心跳缺省间隔与空闲判定阈值; 心跳缺失是否直接关闭连接? [考虑允许一定的回归窗口期, 窗口期结束后没有回复立即释放]
- 握手是否保留 codec 名 (仅作断言) 还是只留 version + daemon + token? [保留 codec 名]
- 未注册 name 的入站消息: 丢弃 (本设计) 还是回一条 kind=error? (回错误=重新引入自动应答) [当前考虑丢弃]
- Stats 是否保留; 若保留, 字段用消息计数 (Sent/Received/Dropped) 即可? [当前考虑去除, 后续细节化再考虑是否加入]
- 业务层做 1:1 很常见, 引擎是否提供可选"待应答表"糖? 默认不提供。[当前不考虑]
```
