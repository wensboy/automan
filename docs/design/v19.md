## 1. 目标与范围

```yaml
目标: 把"代理行"真正跑起来 —— Go 侧决定参数 -> 经 ipc 交给 node 子进程 -> 拉起 whistle 实例 -> 回传启动信息。
约束(你定的):
  · 启动参数以 **sqlite 中的值为唯一基准**(前端不参与参数拼装)
  · 参数经 ipc 传递; node 侧负责启动 whistle 并返回必要信息(pid/实际端口/storage 等)

  · rules 的完整 JSON 模板放 data/default/proxy.rules.json, 由 proxy 服务经 config 层取出返回前端
  · 冲突让步(三个): storage / port / uiport; 让步后**写回数据库**并记录映射
范围外: 导入导出; 规则的运行时下发(whistle 规则生效)暂不涉及; 前端 Stop 的进程治理细节见 §9 E
```

## 4. 冲突让步(核心规则)

```yaml
触发: 启动某代理前, 检查它的 storage / port / uiport 是否已被**其它**代理占用
  · storage: 目录是否已存在(store.Stat/List, 且不属于本代理) -> 占用
  · port/uiport: 是否已有实例在监听(见 §9 C 的探测方式; 当前可先按"数据库里其它 running 行"判定)
让步:
  · storage: 追加随机后缀 -> `<basedir>/<name>-<6位hex>`; 写回 rules.storage
  · port/uiport: 从原值向上找第一个空闲(上限 +100, 见 §9 C); 写回 rules.port / rules.uiport
记录映射: storage -> proxy id(以及 port/uiport -> proxy id), 便于失败重试与后续停用
  # 建议不新增表: 后缀已含 name, 可由 rules.storage 反推; 内存映射仅用于本轮重试
批量: 一次启动多个时, 写库**异步**(先返回启动结果, 再落库); 落库失败按映射重试(带退避, 上限 3 次)
```

## 5. ipc 契约(新增)

```yaml
node -> 处理器(Go 侧 Handle):
  proxy.started  { proxyId, pid, port, uiport, storage, startedAt }

Go 侧需要补的能力:

```

## 11. 模板显示修复 + whistle 真实启动

### 一、addproxy 模板不显示的根因(前端, 已修)

```yaml
根因: ProxySheet 是**常驻挂载**的(open 只是开关) —— useState 初值在**页面加载时**就执行,
      那时 Template() 还没返回; 关闭再打开也不会重建 state -> 编辑器永远停在 {}
      (上一轮"先取模板再打开"只解决了时序, 但 state 早已初始化, 所以看不到效果)
修法: 抽出 buildDraft(template); 在 open=true 且为"新增"时按**最新模板**重置草稿;
      页面侧保留"先取模板再打开"作为双保险
```

### 二、whistle 真实启动(node, 已实现)

```yaml
事实: whistle 2.10.11 的 CJS 入口 `require()` 时**就会启动服务**(导出只有 getWhistlePath),
      不能当库调用 -> 改为**每条代理 spawn 一个子进程**:
      node <whistle>/bin/whistle.js --port= --uiport= --storage= [--timeout=] [--dnsServer=]
就绪: 轮询 TCP 连接 uiport(不依赖它的日志格式); 15s 未就绪或子进程提前退出 -> 失败并回 proxy.failed
停止: SIGTERM -> 等 timeoutMs(bridge.json 的 services.proxy.stopTimeoutMs, 默认 5000) -> SIGKILL
pid : 用子进程真实 pid; 子进程 stdout/stderr 转发到桥接日志(Logs 页可见 whistle 自己的报错)
入口解析顺序: WHISTLE_BIN(env) -> 本地 resolve('whistle/bin/whistle.js')
依赖: backend/bridge/node 增加 whistle@2.10.11(esbuild external, 不打进 bundle)
```

### 三、必须知道的一个部署限制

```yaml
bridge 子进程运行在 <UserDir>/automan/bridge/node/ 下(内嵌资产只有 dist), **没有 node_modules**
-> 运行时 resolve 不到 whistle。二选一:
   (a) 在 data/conf/bridge.json 的 node.env 里设 WHISTLE_BIN=<whistle 的 bin/whistle.js 绝对路径>(推荐, 体积最小)
   (b) 把 node_modules/whistle 一起打进 bridge 资产(体积大, 需改 bridgeasset 的嵌入范围)
开发期直接用 (a) 指向 backend/bridge/node/node_modules/whistle/bin/whistle.js 即可联调。
```

## 14. 开发期经 node.env 快速启动 whistle

```yaml
问题: bridge 子进程运行在 <UserDir>/automan/bridge/node/(内嵌资产只有 dist, 没有 node_modules),
      运行时 resolve 不到 whistle; 而开发期仓库里 backend/bridge/node/node_modules/whistle 是现成的。
做法: 用 bridge.json 的 node.env 注入 WHISTLE_BIN, 但**不写死绝对路径**(换机器就失效), 而是支持占位符:
  data/conf/bridge.json -> node.env:
    ["WHISTLE_BIN=${AUTOMAN_ROOT}/backend/bridge/node/node_modules/whistle/bin/whistle.js"]

${AUTOMAN_ROOT} 的解析(engine/bridge/env.go):
  · 从**可执行文件目录**与**当前工作目录**分别向上找 go.mod, 找到即视为"开发期仓库内运行"
  · 解析后的路径必须**真实存在**, 否则该条环境变量整体丢弃(不注入假路径)
  · 打包运行时两者都找不到 go.mod -> 条目不注入 -> node 侧回落到 require.resolve, 失败时给出
    "whistle not resolvable (set WHISTLE_BIN or install it)" 的明确错误
  · 另支持 `~` / `~/x` 展开(用户主目录)
链路(已验证):
  Go 读 node.env -> expandEnv 展开 -> 追加到子进程 env(engine/bridge/process.go: os.Environ()+e.env)
  -> node 侧 process.env.WHISTLE_BIN -> spawn(node, [<bin>, --port --uiport --storage ...])
日志: "bridge: child started" 增加 env 字段, **只记键名不记值**(值可能含路径/凭据)
```

```yaml
验证:
  go test ./backend/engine/bridge/ -> 3 项新增测试全过
    · ${AUTOMAN_ROOT} 解析为仓库根, 且目标存在才注入
```

## 15. 启动失败排查(issue.md): 三个叠加的问题

现象: 点启动后 15s 超时; 日志里 `spawn .../installation/bin/node ENOENT` + `bridge: child exited ... status 1`。

```yaml
问题 1(主因): spawn 的 cwd 不存在
  bridge.json 的 services.proxy.root 是**相对路径** "proxies/", 原样作为 node 侧 spawn 的 cwd。
  Node 在 cwd 不存在时, 报的正是 **ENOENT** —— 看起来像"node 可执行找不到"(那条 fnm 路径其实存在, 已验证)。
  修复:
    · Go: service/proxy 新增 WithRoot(store.Rooter.Root()), resolveBase() 把 basedir 解成**绝对路径**
      (相对路径落到应用数据根下); storage 也一并绝对化(whistle 的 -S 需要真实目录)
    · node: ensureDir(cwd) 先建目录, 失败则退回 process.cwd()
问题 2: 未监听 error 事件 -> 桥接子进程被打崩
  spawn 失败的 'error' 事件没人接, 直接以未捕获事件终止 node 进程 -> ipc 断开
  -> 前端等满 15s 超时(而不是收到失败原因)。
  修复: 监听 'error' 并与"就绪等待"竞速(Promise.race), 失败立即回明确的错因;
        node 可执行也加了兜底(execPath 存在才用, 否则退回 PATH 的 node)。
问题 3: whistle 参数写法不对
  whistle 的 CLI 是 `<command> [options]`, 开关是**短名**; `--port=` 这种长格式会被当成未知参数,
  只打印 usage 后退出(实测输出 "Type 'whistle help' for usage.")。
  修复: 改为 `run -D <baseDir> -S <storage> -p <port> -P <uiport> [-H <host>] [-t <timeout>] [--dnsServer ...]`
```

```yaml
验证:
  真实拉起(同一组参数): node whistle.js run -D /tmp/... -S /tmp/.../store -p 18899 -P 18900 -H 127.0.0.1 \
      -t 30000 --dnsServer 8.8.8.8,1.1.1.1
      -> 输出 "Whistle@2.10.11 started"; ss 显示 18899 与 18900 均在 LISTEN
  go test -count=1 ./backend/... -> 9 个包全过; service/proxy 现 22 项(新增 basedir/storage 绝对路径断言)
  node: pnpm check(tsc) -> 0 ; pnpm build -> dist/index.js 142KB(Go 侧内嵌, 需重新 task dev)
```


## 24. 能否用 require('whistle') 替代 CLI 并打包进 bundle(实测: 不行)


## 25. 改名迁移目录 + 停止改为"端口反查"

```yaml
改名迁移(2):
  service/proxy.migrateBaseDir(oldName, newName, running):
    · 旧目录存在、目标不存在、且非运行中 -> os.Rename(<proxies>/<old>, <proxies>/<new>)
    · 运行中 -> 跳过并 warn(whistle 正在用该目录, 需先停止)
    · 目标已存在 -> 跳过并 warn(不覆盖, 避免数据丢失)
    · 迁移失败只告警, **不阻断 Update**(DB 是唯一事实, 目录只是运行时数据)
  测试: TestMigrateBaseDirOnRename(运行中跳过 / 正常迁移 / 目标已存在跳过)
停止(1):
  node/service/proxy.ts:
    · 实例表不再只存 ChildProcess, 而是 { child, port, uiport }
    · stop: ① 先对 wrapper 进程组 TERM -> 等 -> KILL
            ② 再按端口反查真正监听的进程(ss -ltnp -> lsof -ti 兜底) -> TERM -> 等 -> KILL
            ③ 端口未释放时打印明确错误(而不是静默成功)
  为何必须这样: whistle 把监听进程 detach 出去(pid 与 wrapper 不同、进程组不同), 且不写 pid 文件;
    `whistle stop -D <baseDir>` 实测返回 "No running Whistle instances"(它按内部状态找实例, 对不上)。

```

### 仍存在的问题(如实记录)

```yaml
· 端口反查依赖 ss/lsof: 极简容器里两者都可能缺失, 此时只剩 wrapper 的组信号(日志会给出"端口未释放")
· 停止是"信号 + 端口"的组合, 不是 whistle 官方语义; 若后续 whistle 提供稳定的实例句柄/pid 文件, 应改回官方途径
```

## 26. 改用 whistle 官方的 standalone service mode(`starting`)

```yaml
发现: whistle 的进程管理其实来自依赖 `starting`, 它导出了可编程入口:
  cli.start(main, options, cb)   # 按 options 启动并写 pid 记录(不依赖 CLI 参数解析)
  cli.stop(main, cb)             # 读同一记录 -> 精确回收该实例
  cli.readConfig(main)           # 读回 { pid, options, version }
  · 实例隔离键格式是 **`<main>#<id>#`**(必须**以 # 结尾**; starting/lib/cli.js 的 getHashIndex
    只在末位是 # 时才识别并剥离, 漏掉结尾会把整串当模块路径 -> MODULE_NOT_FOUND, 实测踩过)
  · options 直接生效: host/port/uiport/baseDir/timeout/dnsServer
落地(node/service/proxy.ts 重写):
  · 启动: 解析 whistle 根(vendor 优先) -> createRequire 取到 `starting` -> cli.start(`<index.js>#<proxyId>#`, opts)
          -> 等 uiport 可连(15s) -> 记录 { key, port, uiport }; pid 从 cli.readConfig(key) 读回
  · 停止: cli.stop(key) -> 端口校验兜底(stopByPort) -> 清理记录
  · 兜底: 若 `starting` 不可解析(例如只配了 WHISTLE_BIN 的精简部署), 退回原来的
          "spawn whistle CLI + wrapper 组信号 + 端口反查"
验证(用 dist/vendor 里的真实 whistle, 与生产代码同一路径):
  · cli.start(key, {port:18830,uiport:18831,baseDir:/tmp/st1}) -> 18830/18831 均在 LISTEN
  · ~/.startingAppData 下生成**该实例独立**的配置文件(1 个), 即多代理互不覆盖
  · cli.stop(key) -> 两个端口全部释放
  · node: pnpm check/build -> 0 ; go build/test -> 9 包全过 ; gofmt 0
```

### 与旧方案对比

```yaml
旧: spawn whistle CLI -> wrapper detach -> 真代理 pid 不可知 -> 只能靠端口反查 + 信号(且依赖 ss/lsof)
新: starting 记录 pid 到配置文件 -> cli.stop 精确回收; 端口校验仅作最后兜底
收益: 停止不再"杀 wrapper 留孤儿"; 多实例天然隔离(每条代理一个配置记录)
保留: CLI+端口反查作为兜底路径(精简部署时)
```
