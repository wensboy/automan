## 1. 目标与范围

```yaml
目标: 让"程序运行期产生的日志"实时到达前端日志页的终端, 并把磁盘日志文件变成"受最大体积约束的循环文件"。

范围内:
  - 后端: 新增 **stream out**(专门处理 stream log 的标准缓冲队列) + 引擎内**二级总线**(扇出给订阅者)
  - 后端: window 引擎订阅二级总线并 emit 前端事件(与 settings 的转发模式一致)
  - 后端: 日志引擎启动时做 fs 处理: 建目录 / 建文件 / 检查体积; 配置文件加入**最大体积限制**
  - 后端: out key 收敛到 `domain/log/` 统一定义
  - 前端: 日志页把 mock 定时器替换为订阅后端事件(不涉及 UI 结构调整)

范围外:
  - 日志页视觉/交互调整(筛选、终端、命令输入保持不变)
  - 落盘日志的回读/检索(真实日志源的历史查询另开)
  - 主事件总线(engine/eventbus)的语义变更: stream 不走它, 见第 3 节"二级总线"
```

## 3. 核心设计: stream out + 二级总线

```yaml
stream out (新增, out key = "stream"):
  定位: 专门处理 stream log —— 与 disk/console 平级的一个 out, 复用 out 自持策略的既有约定
  形态: **标准有界缓冲队列**(FIFO), 容量 `queue`
        - 溢出策略: 丢最旧 + 计数(与 disk 的 ring 语义一致, 终端看到的是"最新的连续片段")
        - 不做级别过滤以外的筛选(筛选在前端做, 见第 6 节)
  产出: 达到"批量条件"时把一批记录交给引擎的二级总线

二级总线(引擎内, 不经过主 eventbus):
  为什么: 主总线是全局语义(变更/通知), 日志是高频流; 走主总线会把所有订阅者卷进日志风暴
  形态: 引擎内部一份订阅者列表 `streamSubs []func([]Record)`, 对外暴露
        `SubscribeStream(fn) (unsub func())`(Register 封口后才可订阅, 见第 5 节)
  扇出: 一次批量分发给所有订阅者; 任一订阅者 panic/阻塞不得影响投递路径

批量与抖动(核心注意点):
  触发条件: 队列条数 >= maxBatch(立即发) **或** 距上次发送 >= intervalMs(定时冲刷)
  抖动处理:
    - 单批上限: 一次最多发 maxBatch 条, 余量留到下一次(避免"大爆发"把前端/传输压垮)
    - 定时器只存在一个(intervalMs), **不为每条日志起定时器**, 也不在 Emit 路径上做 IO/序列化
    - 空转不发: 队列为空时定时器不清扫、不发空批
    - 积压阈值: 队列积压 > queue 时按溢出策略丢最旧并上报(见 log.dropped)
  线程模型: Emit(投递路径) 只入队 + 唤醒冲刷(非阻塞); 冲刷在引擎自己的 goroutine

只转发"启动后"的日志:
  stream out 在引擎 Start 之前不缓冲(Init 阶段产生的启动日志不进 stream),
  Start 时清零并开始接收 —— 与"只考虑将程序运行启动后的 log 刷到 UI terminal"对齐。
```

## 7. 磁盘日志: 最大体积 + 循环文件

```yaml
配置新增(conf/log.json + domain/config/log.go):
  maxSize: int   # 单位 MiB, 缺省 8(与 dir/file/buffer/batch 同族, 走 conf 校验)

循环语义:
  - 日志文件是"基于最大体积的循环文件": 文件大小始终 <= maxSize
  - 追加前检查: 当前大小 + 本批大小 > maxSize 时, 丢弃**文件中最旧的内容**,
    将文件重置为"本批内容"(即保留最新的一段), 并把被丢弃的字节数计入 dropped/上报
  - 实现取向: 不读取全文重排(避免 IO 放大); 只在**超限时**重置写入, 正常追加路径保持现状(storekit.Append)
  - 尺寸来源: 引擎自己做 fs 处理时 Stat 一次并维护内存计数, 每批追加后累加;
    外部改动(用户删文件等)在下一次 flush 时以 Stat 校正
```

## 8. 启动时的 fs 处理(引擎 Start 内)

```yaml
时机: log 引擎 Start(封口)时完成, 之后的运行期只做 append/超限检查
动作:
  1) 建日志目录: storekit.Mkdir(logs) (已存在则忽略)
  2) 确保日志文件存在: storekit.Stat 失败 -> storekit.Write(空内容) 创建
  3) 检查体积: Stat 得到的 size; 若 >= maxSize -> 立即按第 7 节循环语义处理(截断为最新段/清空)
  4) 记录初始 size 到引擎内存计数, 供 flush 时判断
失败处理: 任一步失败 -> 返回错误(启动即暴露), 不静默降级为"只写控制台"
  (与项目既有取向一致: 构建期/启动期问题直接抛出)
```

## 11. 风险与取舍

```yaml
- 事件风暴: 若 intervalMs 过小或 maxBatch 过大, 前端仍会感到抖动; 参数需可配(第 10 节 A)
- 背压: stream 只做"丢最旧 + 计数", 不阻塞投递方(与 disk 一致); 极端情况下终端会缺行, 由 dropped 提示
- 单文件循环: 不保留历史轮转文件, 超出部分直接丢弃 —— 这是"循环文件"的固有代价(第 10 节 D 若要求多份需另设)
- 二级总线只在引擎进程内: 不跨进程(与 bridge 子进程日志的关系: 子进程日志经 bridge 引擎投递进本引擎, 再走 stream)
- 主总线不受影响: log.sync / log.dropped 仍走主总线; stream 走内部扇出, 二者互不干扰
```

```yaml
- 连续写入超过 8MiB: 文件大小稳定在 <= 8MiB, 内容为最新一段
- 退出应用: 末次 flush 仍落盘(现状保持); 终端筛选(搜索/级别/时间范围)行为不变
```

## 13. 排查记录: `task dev` 起不来窗(已修)

现象: `task dev` 后窗口始终不出现。用 CLI 形态跑完整启动链即可复现并定位(`version` 参数会走完
所有引擎的 Init/Start 再打印, 不需要 GUI):

```bash
go build -o /tmp/automan-probe .
timeout -s QUIT 15 /tmp/automan-probe version
→ registry: engine window init: log: stream out unavailable
```

```yaml
根因: 注册表(engine/registry)按 `Deps()` 做**拓扑排序**, 且对每个引擎是 **Init 与 Start 成对执行**。
      window 引擎只声明了 `{config, eventbus}`, 没有声明 `log` -> 它的 Init 可能排在 log 的 Init **之前**,
      此时 log 的 stream out 还没创建 -> `SubscribeStream` 返回错误 -> window.Init 失败 ->
      Unload 回滚 + 整个启动链中断 (所以窗口根本没机会创建)。
修法: window.Deps() 补上 "log" (`{config, eventbus, log}`) —— 它确实消费 log 的二级总线, 依赖声明本就该有。
验证: 同一条 CLI 探针 -> 正常打印 `automan 0.0.1` 并有序停机;
      桌面形态探针 -> 资源服务器已服务 `/`、`/assets/index-*.js`、`/auth-bg.jpg`(webview 已加载前端),
      主 goroutine 停在 GTK 事件循环 `application.(*App).Run`, 栈中 log 链只有 `stream.run` 停在自身 select,
      **没有** flush/fanout/store 阻塞帧 —— 证明 log 链路不再阻塞启动。
```

**由此确立的两条约定**:

```yaml
1. 引擎的依赖必须在 Deps() 里声明完整: 注册表按它拓扑定序, 且 Init/Start 成对;
   凡是在 Init 里 `enginekit.Of(...)` 取别的引擎, 就必须把它写进 Deps —— 否则会表现为
   "初始化失败 / 应用起不来", 而不是编译错误。
2. 排查启动期问题优先用 CLI 探针(`<binary> version`) + SIGQUIT 抓栈:
   不依赖 GUI, 能直接看到失败点是 Init 还是 Start、以及是否有 goroutine 卡在锁/IO 上。
```

**已知的取舍**(与"只转发启动后日志"一致): log 的 Start 早于 window 的 Init, 因此**在 window 订阅之前**
产生的记录(各引擎 Init 期间的启动日志)不会进入前端终端;窗口就绪后的日志正常下发。
