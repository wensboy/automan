# Notification(运行时提示)链路设计

> 协作约定: 实施前完整读一遍; `[!notice: ...]` 与方括号结论即决策。

## 1. 目标与边界

```yaml
核心: 运行时**领域提示**(业务/友好提示), 可 toast, 可在 notification 抽屉里回看, 无持久化。
与日志的差别:
  日志  : 完整记录底层执行动作, 有磁盘持久化(disk out), 供排障;
  notify: 面向人, 只留最近 N 条(内存环形), UI 清除即清空, 不落盘。
实现形态(按你的结论): notify 视为一种**特殊日志** —— service 调 Notifier ->
  进入 log engine -> 写入 notify out(环形) -> 经 eventbus 转发 -> 前端 toast + 抽屉列表。
```

## 2. 分层与文件

```yaml
domain/log:
  notice.go        # Notice{ID,Time,Level,Label,Title,Content}; **独立接口** Notifier
                   #   Notify(Notice) / Notices() []Notice / ClearNotices()
                   #   [!notice: 不复用 Logger 接口 —— 语义与投递目标都不同, 独立可避免耦合]
  out.go           # + OutNotify = "notify"
  record.go        # 复用 Record/Field(deliver 侧不变)
engine/log:
  notify.go        # notify out: 环形缓冲(容量常量 200) + Emit 追加 + 发布事件
                   # Notify(): 组装 Record -> DeliverTo(OutNotify, ...), 非阻塞
  log.go           # Init 里注册该 out; 实现 domainlog.Notifier
domain/event:
  topic.go         # + TopicNoticeAppended / TopicNoticeCleared
  event.go         # + NoticeAppended{ID,Label,Title,Content,At} / NoticeCleared{At}
engine/window:
  window.go        # 订阅两主题 -> Emit "notify:append" / "notify:cleared" 给前端
api/web:
  notice.go        # NoticeService: List() []service-notice / Clear()
  [!notice: 服务名用 Notice 而不是 Notification, 与前端抽屉(notice)一致]
前端:
  lib/notice.ts    # 内存 store: 初始化 List(), 订阅 notify:append(追加 + toast), notify:cleared(清空)
  components/custom/notice/notice-drawer.tsx  # 数据源换成 store; 清除按钮调 Clear()
  components/custom/notice/notice-item.tsx    # 类型换成 binding 的 Notice
  mock/notifications.ts                       # 删除
```

## 3. 投递语义

```yaml
Notify 非阻塞: 只做一次 DeliverTo(内部入队/环形追加), 不做 IO
环形: 容量 200, 超出丢最旧(与日志"丢弃计数"不同, notify 不做丢弃上报 —— 它不是审计)
去重: **不做**(每条都是显式调用产生的业务提示)
id: 由 log engine 生成(时间有序前缀 + 计数), 供前端 key 与 dismiss
清除: ClearNotices() 清空环形 + 发 TopicNoticeCleared(所有窗口同步)
[!notice: notify 不写盘, 也不进 disk/stream out —— 只走 notify out, 避免污染日志与终端]
```

## 4. 调用方(本轮接入一处, 作为链路证明)

```yaml
service/proxy: Start/Stop 成功后 Notify 一条(成功/失败各自文案), 便于在 UI 立刻看到结果。
其余服务按需接入(已有 toast 的业务提示可逐步迁移过来, 不强制一次性改)。
[!notice: 服务通过 Option 拿到 domainlog.Notifier(bootstrap 从 log 引擎解析), 不 import engine/log]
```

## 5. 前端交互

```yaml
收到 notify:append -> 追加到 store 顶部 + toast(成功用 success, warn/error 对应)
打开抽屉 -> 展示 store(倒序, 最新在上), 支持搜索/展开/单条 dismiss(仅本地)
点清除 -> 先调后端 Clear(), 再清本地(以后端事件为准, 失败时 toast 报错并保留列表)
```

## 6. 验证

```yaml
后端: go build/vet ; go test ./backend/... (新增 engine/log 的 notify 环形/清除测试)
前端: tsc + build; 产物含 notify:append / notify:cleared
手动: proxy 启动 -> toast + 抽屉出现该条; 再启动一次 -> 两条; 点清除 -> 抽屉空,
      重启应用后仍为空(无持久化)
```

### 双启动错误: 原因与修复

```yaml
现象: 对已在运行的代理再次点启动 -> 报错, 且该行状态被写成 error(实例其实还在跑)。

原因(starting 的约定): starting/lib/cli.js 的 start():
  4  isRunning(config.pid, cb) -> 已在运行则 callback(true, config.options)  // 第一个参数是"已运行"标记
  我们把这唯一的"已运行"回调当成了失败(err 真值) -> reject -> 上层 markStatus(error)
并发场景更糟: 双击时两次都走到 start, 第二个实例与第一个争抢同一组端口。

修复(三层, 各自独立生效):
  1) service/proxy.Start: 行状态已是 running -> **幂等返回**(runningItem: 回传现有 host/port/uiport,
     不调用 starter, 不写库, 日志 "proxy: already running")
  2) service/proxy.Start 失败分支: 只有原本不是 running 才 markStatus(error) —— 不再误伤运行中的行
  3) node/proxy.ts: ① instances 已有该 proxyId -> 直接回 proxy.started(不再拉起第二个实例);
                    ② starting 回调 err===true -> 视为"已在运行"成功(uiport 就绪校验仍然执行)
```

## 10. 收敛 notice 的使用面(只留业务友好提示)

### 规则(自本次起)

```yaml
只在这些场景调用 Notify: **面向用户的业务结果/友好提示**, 且"用户需要被告知、也值得回看"。
不调用(走日志):
  · 代理/桥接/会话的**事件通知**与**操作明细**(启动、停止、连接、登录...): 已有 eventbus 事件与 log 流,
    再发 notice 只会制造噪声;
  · 内部步骤、调试信息、周期性状态。
判定口径: 这条信息如果"关掉应用后用户不会想念它", 就不该是 notice。
```

### 本轮改动

```yaml
移除: service/proxy 的 3 处 notice(启动成功 / 启动失败 / 停止) —— 它们属于操作明细
保留: WithNotifier 注入与 s.notice() helper(供业务层后续使用, 当前无生产方)
引擎防护: Engine.Notify 丢弃**空标题**的提示(标题是给人看的一句话结论, 空标题只会渲染出空壳)
UI 防护: notice-item 仅在 title/content 非空时渲染对应行; 两者都空时用 label 兜底, 不再出现空卡片
```

### 关于"item 无 title"的定位结论

```yaml
实测(临时 Go 测试, 已删): Engine.Notify -> notifyOut -> 事件载荷 全程保留 Title(值未丢失)
Wails 侧: Event.Emit(name, data) 单参数时 event.Data = data 本身(不是数组), 前端按对象读取正确
因此"无 title"不是字段丢失, 而是这些卡片本身是**操作类信息**(标题/内容不具备"提示"语义);
按上面的规则移除生产方后, 该现象不再出现。若你期望的是"标题作为卡片 header(label 位置显示 title)",
需要你明确排版口径, 我再调整(当前 header=label, body=title+content)。
```

### 验证

```yaml
前端 tsc -> 0 ; npm run build -> ✓
生产方核对: grep 's.notice(' backend/service -> 仅剩 helper 定义(无调用)
```

## 11. label 缺失的处理口径(使用层避免)

```yaml
现象: notification 卡片出现"有 body、无 label"的不一致观感
根因: **混用 log 与 notice** —— 操作类信息(启动/停止/连接等)被当作 notice 投递, 它们没有"分类标签"的语义
处置(使用层): 按 §10 的规则移除这类生产方(已做, 当前无生产方)
UI 容忍: notice-item 的 label 视为**可选** —— 为空时整段不渲染, 操作按钮用 ml-auto 靠右,
         不再出现"头部空一截"的视觉差异
说明: 不为 label 造默认值(默认值本身就是混用的产物); 需要分类就让业务方在调用时明确给
      [!notice: label 是分类标记, 不是必填; 省略即"无分类", 由 UI 自适应]
```


## 12. 去除"事件触发 notice"的接线

```yaml
问题: 事件类动作(代理启停等)会连带产生 notice 效果(抽屉条目 + toast), 与 §10 的定位冲突。

处置(彻底断开事件 -> notice 的通路):
  · service/proxy: 删除 notifier 字段、WithNotifier Option、notice() helper
  · bootstrap: 不再把 log 引擎的 Notifier 注入 proxy
  · 结果: 仓库内 **没有任何 .Notify( 调用点**; notify:append 只可能来自将来显式接入的业务服务
保留: notify 链本身(domain/log.Notifier + engine/log 的 notify out + notify:* 事件 + 前端 store/抽屉),
      将来某个业务场景需要"友好提示"时, 在对应 service 注入 Notifier 并显式调用即可(不需要重建链路)

仍然存在的 toast(与 notice 无关, 保留):
  · 页面级操作反馈: proxy 页启动/停止/删除/保存的 toast.success / toast.error
  · 表单校验失败提示
  区分口径: 这类是"即时的操作反馈", 不入 notification 队列, 也不在抽屉里回看。
```

## 13. 修复: 普通日志混入 notification(无 label 条目)

```yaml
现象: 通知抽屉里出现 "bridge: asset ready" / "bridge: listening" / "settings: loaded" 这类**无 label** 条目,
      且每条日志都会产生一次 notice 效果(toast)。

根因: notify out 作为普通 Out 注册在引擎里, 而引擎的 **扇出投递 Deliver() 会发给所有 out**
      -> 每一条普通日志都被 notify out 收下, 转成 Notice(Title=日志消息, Label 为空) -> 发布 notify:append
      => 这正是"事件/日志触发 notice 效果"与"无 label"两个现象的共同来源。

修复(在 out 层做语义区分, 而不是在调用方):
  · Notify() 组装的记录带标记 Field{noticeKind: "notice"}
  · notifyOut.Emit 只接收带该标记的记录, 其余**直接跳过**(普通日志仍照常进 console/disk/stream)
  · 测试: 新增 TestNotifyIgnoresPlainLogs(普通记录不入队); 原有环形测试同步补标记
```

```yaml
验证:
  go test -count=1 ./engine/log -run TestNotify -> PASS(2 项)
  go build/vet -> 通过 ; go test -count=1 ./backend/... -> 9 个包全过 ; gofmt 0
  [!notice] 该过滤必须留在 out 层: 调用方无法阻止扇出投递, 只有 out 自己知道"什么才算提示"。
  提示: 抽屉里的旧条目在内存中, 重启应用即清空(本设计无持久化)。
```
