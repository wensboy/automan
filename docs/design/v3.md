# Automan 设计 v3 · Step 1 (迭代)

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v2.md` + 当前薄骨架实现
> 范围: 两项优化 —— ① 引擎改为**依赖拓扑加载** ② 根上下文**瘦身为纯契约**, 实现下沉为 **runtime 引擎**.
> 目标: 给出模块结构的调整方案, 使上述目标自然落地. 非编码任务.

---

## 0. 相对 v2 / 现实现的变更

| 维度 | v2 / 现实现 | v3 |
|---|---|---|
| 加载顺序 | `Tier()` 静态优先级 | `Deps()` 名称依赖 → **拓扑加载**, 依赖就绪才加载 |
| 循环依赖 | 未约束 | **显式禁止** (注册期检测报错) |
| 根上下文实现 | `domain/context` 内含 `runtime` struct | 契约与实现分离: 实现移入 `engine/runtime` |
| 根上下文职责 | 生命周期 + 数据 lookup + 能力 resolve | 生命周期 + **ereg**(引擎表) + **srvs**(服务编排) |
| 引擎能力获取 | `caps` 统一 `Provide/Resolve` | 经 **ereg 取引擎**后调用其方法 |
| 配置 | `ctx.Value` + `AttachBase` (统一 lookup) | **不在 ctx**: 取 config 引擎后调其 `Get` |
| logger/base/overlay | 根上下文字段 | **移除**, 后续由 log/config/settings 引擎提供 |

一句话: **根上下文只做"运行时骨架"(引擎表 + 服务表), 其余能力全部下沉到各自引擎, 由依赖拓扑驱动就绪**.

## 1. 核心观点

### 观点 A — 依赖驱动加载 (取代优先级)

- 引擎通过 `Name()` 标识自身, 通过 `Deps() []string` 声明所依赖的**引擎名称**.
- 加载器在**所有依赖就绪**后才加载该引擎; **不允许循环依赖** (注册期检测并报错).
- 相比 `Tier`: 依赖是精确、自描述、可校验的; 结构变化时只需改 `Deps`, 不需要维护全局优先级编号.

### 观点 B — 根上下文 = 纯契约 + runtime 引擎

- `domain/context` **只放契约** (接口 + 值类型), 不含任何实现 (无 struct/锁/map).
- 根上下文的实现是 **runtime 引擎** (`engine/runtime`): 它本身也是引擎, 是依赖图的根.
- 因此 "根上下文" 与 "runtime 引擎" 是同一物的两个视角: 对外是 `Context` 契约, 对内是一个引擎.

### 观点 C — 能力归属: ereg (引擎) vs srvs (服务)

- `ereg` (**引擎注册表**): 按名称持有引擎, 负责依赖图与生命周期. 需要某引擎的能力时**先取引擎, 再调其方法**.
- `srvs` (**服务注册表**): 由 `caps` 收窄而来, **只专注于 srv 编排管理** —— 服务层的编排产物, 供上层按接口解析.
- 结论: 引擎的能力 (如 config 的取值、event 的发布) **不再摊平到根上下文**, 而是留在引擎上; 根上下文只做编排骨架.

### 观点 D — 配置/日志/设置 由各自引擎提供

- **非必须字段**: `logger` (后续由 log 引擎提供), `base`/`overlay` (后续由 config/settings 引擎提供) —— 全部从根上下文移除.
- 配置相关方法**不要加到根上下文**: 运行期先定位 config 引擎, 再调 `Get(key)` 取值.

## 2. 引擎依赖拓扑加载

### 2.1 契约

```go
// domain/engine —— 纯契约
type Engine interface {
    Name() string
    Deps() []string                  // 依赖的引擎名称 (不含自身)
    Init(ctx context.Context) error
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
}

type Registry interface {
    Register(e Engine) error         // 重名/自依赖 -> 报错
    Load(ctx context.Context) error  // 拓扑校验 + 就绪波次加载
    Unload(ctx context.Context) error// 逆序停机
}
```

- `Name` 是依赖引用的唯一定位符 (spec: 显式 > 隐式; 不做隐式类型推断).
- `Deps` 只声明**引擎间**依赖; `runtime` 作为根被隐式依赖 (它提供 `Context`), 无需重复声明.

### 2.2 加载算法 (Kahn 拓扑)

```yaml
Load:
  1_索引: 按 Name 建索引; 重名 -> err
  2_校验: 所有 Deps 必须已注册; 缺失 -> err
  3_检测环: 入度拓扑; 存在未消解节点 -> err(循环依赖: 打印环路径)
  4_就绪波次:
      ready = 无依赖(或依赖已 Started)的引擎
      while ready 非空 (按注册序取, 保证确定性):
        e.Init -> e.Start
        成功: 标记 Started; 其直接后继入度 -1, 归零者进入下一波
        失败: 立即停止, 逆序 Unload 已 Started; 未被依赖满足者不启动
  5_完成: 全部 Started
Unload: 按 Started 列表逆序 Stop (依赖者先停)
```

- **确定性**: 同一波次按注册顺序执行, 保证多次运行行为一致 (spec: 显式行为).
- **就绪驱动**: 语义上 "所有依赖就绪即加载"; 实现上以波次表达, 后续可平滑升级为并发就绪调度.

### 2.3 边界情况

```yaml
重名:          Register 期报错
自依赖:        Deps 含自身 -> 报错
未知依赖:      依赖名未注册 -> 报错
直接/间接环:   拓扑检测 -> 报错并给出环路径
依赖失败:      后继引擎不加载; 已加载者逆序回滚
多根无依赖:    并行就绪, 按注册序依次加载
停机顺序:      始终为加载顺序的逆序
重复 Load:     幂等或报错 (需显式定义, 建议报错避免隐式重入)
```

### 2.4 示例依赖图

```yaml
runtime:  deps: []                       # 根 (提供 Context)
config:   deps: []
eventbus: deps: []
log:      deps: [config]
settings: deps: [config, eventbus]
browser:  deps: [config, log]
window:   deps: [config, eventbus]
```

```yaml
波次0: runtime, config, eventbus
波次1: log, settings, browser, window
停机:  window, browser, settings, log, eventbus, config   (逆序)
```

## 3. 根上下文 (runtime 引擎)

### 3.1 契约 (domain/context, 纯)

```go
// domain/context —— 只有契约与值类型, 无实现
type Mode string
const (
    ModeDesktop Mode = "desktop"
    ModeCLI     Mode = "cli"
)

// Context 是运行时骨架: 只管生命周期、引擎表(ereg)、服务表(srvs).
type Context interface {
    // 生命周期
    Done() <-chan struct{}
    Err() error
    Cancel()
    Mode() Mode

    // ereg: 引擎注册表 (按名称取引擎, 再调其方法)
    Engine(name string) (any, bool)

    // srvs: 服务编排表 (只服务编排, 不承载引擎能力)
    Register(key string, srv any) error
    Srv(key string) (any, bool)
}
```

- **不含**: `Logger` / `Value` `Set` / `AttachBase` `AttachOverlay` / `Provide` `Resolve` 等.
- `Engine(name)` 返回 `any` 是为**打破 context ↔ engine 的导入环** (engine.Engine 的方法需要 `context.Context` 参数, 两包互相引用). 类型安全由 `engine.Of[T]` 这一**无状态辅助**补齐 (见 4.3).

### 3.2 实现 (engine/runtime)

```go
// engine/runtime —— 根上下文的唯一实现, 同时是一个引擎
type Runtime struct {
    ctx    stdctx.Context
    cancel stdctx.CancelFunc
    mode   context.Mode
    ereg   *registry.Registry   // 引擎注册表 (拓扑加载)
    srvs   sync.Map             // 服务编排表 (key -> srv)
}

func (r *Runtime) Name() string        { return "runtime" }
func (r *Runtime) Deps() []string      { return nil }         // 根
func (r *Runtime) Start(context.Context) error { return r.ereg.Load(r) }
func (r *Runtime) Stop(context.Context) error  { return r.ereg.Unload(r) }
// ... 实现 Context 的生命周期 / Engine / Register / Srv
```

- `runtime` 是**根**: `Deps` 为空, 其 `Start` 驱动整个依赖图加载.
- 自举顺序: bootstrap 先建 `Runtime` → 把引擎注册进 `ereg` → 调用 `runtime.Start()`.

### 3.3 取值路径的变化 (关键)

```yaml
v2_旧路径:
  ctx.Value(config.AppKey)          # 配置摊平在根上下文
v3_新路径:
  cfg, ok := engine.Of[config.Provider](ctx, "config")   # 先取引擎
  info, ok := config.Get(cfg, config.AppKey)             # 再调方法
```

- 根上下文不再知道 config/settings 的存在; 取值是"找到对应引擎 → 调其方法".
- settings 若有"覆盖 config"的层叠语义, 该层叠由 **settings 引擎内部**处理 (它自己也依赖 config 引擎), 而非根上下文.

## 4. 模块结构优化

### 4.1 包布局

```yaml
backend:
  domain:                      # 纯契约, 无实现
    context:                   # Context 接口 + Mode
    key:                       # Key[T]/NewKey (跨领域复用的值基元, 叶包)
    engine:                    # Engine/Registry 契约 + Of[T] 无状态辅助
    srv:                       # 服务编排契约 + Register/Of 无状态辅助
    config:                    # Provider 契约 + 键 (AppKey ...)
    settings:                  # Store 契约 + 键
    event:                     # Bus 契约 + Topic
  engine:                      # 领域实现
    runtime:                   # 根上下文实现 (= runtime 引擎)
    registry:                  # 引擎注册表: 依赖图/校验/波次加载
    config/ eventbus/ log/ settings/ window/
  service:                     # 编排 (只依赖 domain)
  api:
    window/ cli/
  bootstrap:                   # 组合根: 建 runtime + 注册引擎 + 装配服务/暴露
```

### 4.2 依赖方向 (单向, 无环)

```yaml
domain/*          : 互不 import 实现; 只依赖更基础的 domain (key/context)
engine/runtime    : -> domain/context, domain/engine, engine/registry
engine/registry   : -> domain/context, domain/engine
engine/<x>        : -> domain/<x>, domain/context, domain/engine
service/*         : -> domain/*            (不 import engine/*)
api/*             : -> service/*, domain/* (不 import engine/*)
bootstrap         : -> 全部 (唯一的组合根)
```

### 4.3 契约归属与辅助函数

```yaml
context_包内      : 只有 Context 接口与 Mode; 零 struct / 零状态
key_包            : Key[T] 值基元 (跨 config/settings/srv 复用, 避免重复定义)
engine_包         : Engine/Registry 契约 + Of[T](ctx,name) —— 无状态, 仅做类型断言
srv_包            : Register/Of 无状态辅助, 围绕 srvs 键
原则:
  - 无状态辅助可放在契约旁; 有状态实现一律下沉到 engine/*
  - 使用者只面对"契约 + 辅助", 不 import 具体实现 (除 bootstrap)
```

### 4.4 ereg vs srvs 职责分层

```yaml
ereg (引擎注册表):
  内容: 引擎实例, 按 Name 索引
  用途: 生命周期 (拓扑加载/停机) + 引擎能力访问 (取引擎->调方法)
  示例: config.Get / event.Bus.Emit / log.Logger
srvs (服务注册表):
  内容: 服务层编排产物 / 以接口暴露的能力
  用途: 上层按接口解析, 跨层解耦 (api -> service, service -> service)
  示例: service/app 暴露的应用服务
约束:
  - 引擎的底层能力走 ereg, 不摊入 srvs (srvs 只做 srv 编排)
  - 两者键空间独立 (Name vs srv key)
```

### 4.5 需改动的现有文件 (映射)

```yaml
domain/context/context.go:
  拆分 -> 契约留在 domain/context; runtime struct 移入 engine/runtime
domain/engine/engine.go:
  Tier() -> Deps(); 新增 Of[T]
engine/registry/registry.go:
  按 tier 排序 -> 依赖图 + 校验 + 波次加载 + 逆序停机
engine/config|eventbus|settings/window:
  Tier() -> Deps(); 能力由 Provide 改为"引擎自身即能力载体"
domain/config|settings/event|key?srv?:
  键与契约就地定义; 去掉 ctx.Value/AttachBase 依赖
service/app, api/window, bootstrap:
  去掉 Value/Resolve; 改为 engine.Of + 引擎方法 / srv 解析
```

## 5. 启动链路 (更新)

```
main → api/cli → bootstrap
 └─ runtime.New(mode)                        # 建 Runtime (含 ereg/srvs)
 └─ ereg.Register(config, eventbus, log, settings, window)   # 声明 Deps
 └─ runtime.Start()
     └─ ereg.Load(ctx)                        # 拓扑校验 -> 波次加载
         ├─ wave0: runtime, config, eventbus
         ├─ wave1: log, settings, browser, window
         └─ 任一失败 -> 逆序回滚
 └─ 服务编排: 装配 service/app -> ctx.Register(srvKey, svc)
 └─ api 暴露: api/window 解析 srv; window.Run() (desktop)
 └─ 停机: runtime.Stop() -> ereg.Unload 逆序
```

要点:
- 加载由**依赖就绪**驱动, 不再有 tier 编号.
- 根上下文全程只参与"生命周期 + 表管理", 不参与业务/配置取值.

## 6. 考虑要点

### 6.1 循环与缺失依赖 (fail-fast)
- 校验在 `Load` 入口一次性完成 (索引/缺失/环), 任何问题**启动即失败**, 不做运行期兜底.
- 环检测输出**环路径**, 便于定位 (spec: 考虑边界情况).

### 6.2 并发与确定性
- 语义是"依赖就绪即加载"; 初版用**波次顺序**实现, 保证确定性.
- 若后续改为并发加载, 需重新定义: 同波次内的初始化副作用是否可并行, 以及失败时的回滚语义.

### 6.3 停机顺序
- 严格为加载顺序的逆序 (依赖者先停), 与波次无关, 保证被依赖者最后释放.
- `Cancle` 根 ctx 作为全局停机信号; 各引擎在自己的 `Stop` 里响应.

### 6.4 契约环的取舍
- context ↔ engine 互为引用 (Engine 方法需 `context.Context`). 取舍: 让 `Context.Engine` 返回 `any`, 用无状态 `engine.Of[T]` 补类型安全; 避免为解环引入"把 ctx 存进引擎字段"的反模式 (违背 v1 "函数传递上下文" 的初衷).

### 6.5 srv 注册一致性
- `Register` 语义需显式: 重名 -> 报错 (fail-fast), 不做静默覆盖.
- 解析在同一进程内进行, 键空间与 ereg 的 Name 隔离.

### 6.6 与 spec 呼应
- **0 冗余**: 无状态辅助集中一处 (key/engine/srv), 各引擎只留自身实现.
- **不做代码预留**: log/settings 引擎未落地前, 根上下文不预埋 logger/overlay 字段.
- **显式 > 隐式**: 依赖靠 `Deps` 名称显式声明, 加载顺序可推导、可打印.
- **代码清晰**: 契约前置 (domain), 实现后置 (engine), pub 在前 private 在后.

## 7. 待澄清项

- `engine.Of[T]` 与领域自带的 `From(ctx)` 辅助是否重复? 建议只保留一种 (倾向 `engine.Of` 通用 + 领域键)。
- `srvs` 是否需要依赖顺序 (服务间也可能有编排依赖)? 当前设计仅引擎有依赖图。
- `log` / `settings` 引擎的落地时点 (决定 `logger`/`overlay` 何时回归, 但**不再回到根上下文**)。
- `Runtime` 是否要在 ereg 中显式登记 (当前定位为"根 + 加载器", 由 bootstrap 直接持有)。
