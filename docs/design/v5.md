# Automan 设计 v5 · log 引擎

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md` + `docs/design/v4.md` + 当前薄骨架实现
> 范围: 新增 **log 引擎** —— 对外统一日志调用, 对内把消息**投递**分发到多个 out; 控制面走 ebus; 内存环形缓冲经 `log.sync` 落盘(经 store).
> 目标: 明确实现要点与边界. 非编码任务.
> 落位: 空目录 `backend/domain/log` 与 `backend/engine/log`; `data/conf/log.json` (已有存根).

---

## 0. 定位与边界

```yaml
核心功能:
  对外: 暴露唯一的统一日志调用接口 (所有引擎/服务只认这一套)
  对内: 统一管理日志消息 -> 分发到不同 out (console / file / ...)
  形态: 投递式日志 —— 消息由投递方投递, 投递控制权在投递方
交互:
  数据面 (写日志): 经 ereg 取 log.Logger, 调统一接口
  控制面 (事件)  : 主要走 ebus (如 log.sync 触发落盘)
不是:
  - 不是 slog 的包装层 (不引入第二套概念)
  - 不许各引擎自建第二套日志 (IO 收敛到 store, 日志收敛到 log)
  - 不由引擎隐藏地定时刷盘/重试 (显式 > 隐式)
```

---

## 1. 核心观点

### 观点 A — 日志的本质是"消息"

- 日志 = **时间戳 + 指定级别 + 必要信息** 的消息, 与"往哪写/怎么写"无关:

```go
// domain/log —— 消息模型
type Level int
const (
    LevelDebug Level = iota
    LevelInfo
    LevelWarn
    LevelError
)

type Field struct {
    Key   string
    Value any
}

type Record struct {
    Time   time.Time
    Level  Level
    Msg    string
    Fields []Field
}
```

- `Fields` 用**有序切片**而非 map: 保证输出可复现 (spec: 显式/可复现).

### 观点 B — 统一调用面保持极小

```go
// domain/log —— 统一日志调用 (单一方法, 不做 Debug/Info/Warn 方法族)
type Logger interface {
    Deliver(record Record)
}
```

- 与 store 的"指令式"同理: **接口 O(1), 能力靠 Record 承载**, 新增信息类型不改接口.
- 引擎从 ereg 取: `engine.Of[log.Logger](ctx, "log")`, 在各自 `Init` 持有.

### 观点 C — 投递式 + 投递方控制

- 消息**由投递方投递**, 引擎只做"接收 → 分发", 不替投递方做决定.
- 投递控制权在投递方: 级别、字段、时间戳、何时触发落盘 (`log.sync`) 都由投递方掌握.
- **引擎侧无隐藏定时刷盘、无隐藏重试**; 唯一例外是停机时的末次 flush (见 §7).

### 观点 D — 内部 fan-out 到多个 out

- 引擎把每条消息分发给所有已注册 out; 每个 out 自持策略 (过滤/格式化/批量/缓冲).
- out 是唯一的写出口; 落盘不另开通道, 统一经 **store** 引擎写.

### 观点 E — 控制面走 ebus, 数据面走契约

- 写日志: `Logger.Deliver` (ereg 解析).
- 事件/生命周期协作: ebus (topic 集中定义在 `domain/event/topic.go`).

## 2. 日志消息与级别 (domain/log)

```yaml
level.go:
  Level 常量 + String() + ParseLevel(string) (未知 -> 报错/缺省 Info, 需显式定)
  比较: Rank() int 用于阈值过滤
record.go:
  Record{Time, Level, Msg, Fields}
  Field{Key, Value}
logger.go:
  Logger 接口 (Deliver)
  构造辅助 (无状态):
    New(level, msg, fields...) Record      # 填当前时间戳
    F(key, value) Field                    # 字段糖
out.go:
  Out / Flusher / Registrar 契约
```

- `Record` 只描述"是什么"; **不描述"往哪写"**, 目标选择不在消息里.

---

## 3. out (投递目标)

### 3.1 契约

```go
// domain/log

// Out 是日志出口; 批量由投递方给出, 处理策略由 out 自持.
type Out interface {
    Emit(records []Record) error
}

// Flusher 由需要缓冲的 out 实现 (如落盘 out).
type Flusher interface {
    Flush() error
}

// Registrar 是扩展点: 注册/替换 out.
type Registrar interface {
    Register(name string, out Out) error   // 重名/启动后 -> 报错
}
```

### 3.2 内置 out

```yaml
console:
  目标: stderr
  策略: 立即格式化输出; 级别阈值由自身决定
disk:
  目标: 磁盘文件 (经 store 引擎写)
  策略: 先追加到内存环形缓冲; 收到 log.sync 时批量落盘并清空
  批量: 单次 flush 一次写入 (减少 IO 次数)
```

- **环形缓冲属于 disk out**, 不是引擎的全局结构 → 引擎只 fan-out, 无重复写风险.
- 级别阈值**由各 out 自持** (console 与 disk 可不同), 引擎不设全局阈值 (呼应观点 C).

## 4. 分发与缓冲

```yaml
Deliver(record):
  -> 引擎: 对每个 out 调 Emit([]Record{record})   # 投递方给批量, out 决定怎么处理
  -> 立即返回 (不阻塞投递方; 日志绝不能拖垮业务)
ring (disk out 内):
  有界环形缓冲, 容量 conf/log.buffer (缺省内置)
  溢出: 丢最旧 + 计数 (Stats.Dropped), 不阻塞
sync:
  收到 log.sync -> 对实现 Flusher 的 out 调 Flush()
    disk: 把 ring 内记录经 store 批量 append 落盘, 成功后清空 ring
```

- 落盘失败: **吞掉并计数**, 不反噬业务; 可观测量走 Stats / `log.dropped`.

---

## 5. 与其他引擎交互

```yaml
写日志 (数据面):
  引擎在 Init 取 log.Logger 并持有 -> 需要时 Deliver
控制面 (ebus):
  log.sync    : 请求落盘 (由投递方发出; 无定时器)
  候选:
    log.dropped : ring 溢出/落盘失败 (便于外部观测)
    log.flushed : 落盘完成 (便于停机观测)
约束:
  topic 常量 -> domain/event/topic.go
  载荷类型   -> domain/event/event.go
```

- 谁发 `log.sync`: 由投递方决定 (bootstrap 关机前 / 上层按需 / 未来定时器另置) —— 见 §11.

## 6. 依赖与生命周期

```yaml
Name: "log"
Deps: ["config", "eventbus", "store"]     # store 用于落盘; config 取参数; ebus 订阅/广播
Init :
  - 从 config 取参数 (buffer/batch/级别/路径)
  - 取 ebus 并订阅 log.sync
  - 注册内置 out (console/disk)
Start:
  - 标记就绪 (sealed, 之后不允许再注册 out)
Stop :
  - 末次 flush (有界): 关机不丢日志 —— 见下方说明
```

依赖图更新 (相对 v4):

```yaml
runtime  : []
config   : []
eventbus : []
store    : [config, eventbus]
log      : [config, eventbus, store]      # 落盘依赖 store
settings : [config, eventbus]             # 接入 store 持久化属 v4 step3
window   : [config, eventbus]
```

- store 先于 log 就绪 → log 才拿得到写入口.
- **停机末次 flush 是对"无隐藏刷盘"的显式例外**: 关机丢日志不可接受; 它不是"定时器策略", 而是生命周期动作.

```json
    "dir": "logs",

    "batch": 256,

```

```yaml
键示例:
  conf/log.buffer       环形缓冲容量
  conf/log.batch        单次落盘批量上限
  conf/log.dir|file     落盘相对路径 (经 store 解析到存储根内)
  conf/log.consoleLevel 控制台阈值 (out 自持, 放这里便于统一配置)
  conf/log.fileLevel    落盘阈值
缺省: 由引擎内置 (对齐 v4 §3.4)
```

- 路径是**相对存储根**的 (store 会做逃逸校验), 不是绝对路径.

## 8. 考虑要点

### 8.1 投递不阻塞
- `Deliver` 必须快速返回; 任何 IO 都不得发生在投递路径上 (落盘只在 flush 时).
- 反例: 直接同步写文件 → ring/store 的设计就失去意义.

### 8.2 溢出与丢弃 (显式)
- ring 满: 丢最旧 + `Dropped++`; 绝不阻塞生产者.
- 丢弃必须可见 (Stats / `log.dropped`), 不静默.

### 8.3 无隐藏策略
- 无隐藏定时刷盘、无隐藏重试、无隐藏级别过滤 (阈值由 out 自持并显式配置).

### 8.4 并发安全
- 多 goroutine `Deliver` → 引擎与每个 out 内部需同步 (ring 加锁/原子).
- out 注册与 store 一致: `Start` 后 sealed.

### 8.5 与 store 的边界
- log 只发 **append** 指令 (批量), 不直接碰 `os`.
- 落盘失败不回退到"自己写文件" (不搞第二套 IO).

### 8.6 观测
- `Stats` (只读): Delivered / Dropped / Flushed / Buffered / OutCount.
- 与 v4 §8 一致: 指标优先 `Stats()` 只读暴露.

### 8.7 与 spec 呼应
- **0 冗余**: 全局只有一个日志出口; 各引擎不再各调 `fmt.Fprintln`.
- **不做代码预留**: 只实现 console/disk 两个 out; 其余按需注册.
- **显式 > 隐式**: 刷盘时机、阈值、丢弃策略全部显式.
- **考虑边界**: ring 溢出/落盘失败/关机 flush/并发投递.

## 10. 待澄清项

```yaml
- "store 内部订阅日志 sync 落盘事件" 的确切含义:
    现按"log 引擎内部的落盘组件(disk out)订阅 log.sync"设计;
    若你指的是 store 引擎自身持有环形缓冲并订阅, 请指出 (那会改变职责边界).
- 统一接口是否要返回句柄 (类比 store.Submit 的 Future)? 倾向 fire-and-forget + Stats. [日志不需要考虑基于结果处理, 即使没有投递成功业务也不需要做任何处理.]
- 是否提供 Info/Warn/Error 语法糖? 倾向不加 (New+Deliver 已足够, 避免接口膨胀). [不需要]
- 级别阈值归属: out 自持 (本设计) vs 引擎预过滤 (省一次函数调用)? [out自持, 引擎自身应当认为所有记录在投递前都是有效的, 不过滤任何记录]
- log.sync 由谁发出: bootstrap 关机 / 上层按需 / 未来加定时器? [考虑未来加定时器定时sync, 同时考虑特殊节点也需要手动emit日志同步]
- 落盘失败是否需要有限重试? (日志优先不阻塞, 倾向不重试 + 计数)
- batch 与 buffer 的关系: batch 是否必须 <= buffer? [考虑影响, 当前影响小则后续引入]
- 是否需要 console 之外的标准出口 (syslog/OTLP)? [当前不考虑]
- Stats 只读暴露是否同时发 log.dropped 事件? [触发]
```
