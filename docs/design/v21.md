# Workspace(工作区)链路设计

> 协作约定: 实施前完整读一遍; `[!notice]` 与方括号结论即决策。

## 1. 目标与关系

```yaml
目标: 在 user 之下再隔离一层资源(当前是 proxy), 不同工作区互不可见。
关系: user 1:n workspace 1:n proxy
  · workspace.user_id  -> 归属用户
  · proxies.workspace_id -> 归属工作区
  · 因此: 不同用户可同名 workspace; 不同 workspace 下 proxy 可同名(唯一性限定在同一 workspace)
存储: sqlite(workspace 表), 与其它表同风格(文本 id / unix 毫秒 / 逻辑删除)
```

## 2. 表结构(迁移 000004)

```sql
CREATE TABLE IF NOT EXISTS workspaces (
    id         TEXT    PRIMARY KEY,
    name       TEXT    NOT NULL,
    user_id    TEXT    NOT NULL,              -- 归属用户(不加外键, 同 proxies.user_id 的取舍)
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    deleted_at INTEGER NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_workspaces_user_name
    ON workspaces (user_id, name) WHERE deleted_at = 0;

ALTER TABLE proxies ADD COLUMN workspace_id TEXT NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS idx_proxies_workspace ON proxies (workspace_id, deleted_at);
```

```yaml
[!notice] proxies.workspace_id 默认空串: 历史行不自动归属(与 user_id 的处置一致, 需要时用一次性 SQL)。
```

## 3. 分层与文件

```yaml
service/workspace/workspace.go   # 领域编排: 列表/创建/删除/当前工作区
  · List(ctx) []Workspace                 # 只返回当前用户的(未删除)
  · Create(ctx, name) (Workspace, error)  # 同名(同用户内)拒绝
  · Delete(ctx, id) error                 # 逻辑删除; 若删的是当前工作区则清空当前
  · Current(ctx) string                   # 当前工作区 id(内存记录, 不落库)
  · SetCurrent(ctx, id) error             # 切换(校验归属)
  · EnsureDefault(ctx) (Workspace, error) # 当前用户无工作区时创建 "Default"
  [!notice] 当前选择记录在 **workspace 服务内**(内存 map[userID]workspaceID), 不落到别的服务 ——
           单一职责: 谁拥有数据, 谁记录"当前".
api/web/workspace.go             # WorkspaceService: List/Create/Delete/Current/SetCurrent
service/proxy                    # 新增 WithCurrentWorkspace(func() string), 查询/写入按 workspace 收束
bootstrap                        # 解析 workspace srv -> proxy WithCurrentWorkspace(ws.Current)
前端:
  store/workspace.ts             # 当前工作区 id 与列表(唯一信息, 允许入 store)
  sidebar/team-switcher.tsx      # team -> workspace: 列表 + hover 删除 + 底部 popover 添加
```

## 4. 收束规则

```yaml
proxy 查询:  `user_id = ? AND workspace_id = ?`(两者都由服务注入的取值函数提供)
proxy 写入:  Create 时写入当前 workspace_id
唯一性    : name 唯一性检查在 (user_id, workspace_id) 内 —— 不同工作区可同名
未登录/无工作区: 取值为空 -> **不做该维度收束**(与 user 收束的取舍一致, 便于测试与早期阶段)
删除工作区: proxies 保留(逻辑删除 workspace), 其代理不再被有效查询到(同 user 删除的处置)
```

## 9. 修复: 工作区列表报 "missing destination name created_at"

```yaml
现象: 创建成功但服务层报错; 再次创建则报 duplicate workspace name。
根因: workspace.Workspace **只有 json tag, 没有 db tag** —— store 引擎用 sqlx 按列名映射,
      查询 SELECT id,name,created_at,updated_at 时找不到 created_at 的落点:
      "missing destination name created_at in *[]workspace.Workspace"
      => List 失败(看起来像"操作失败"), 而 INSERT 已经成功 -> 再点一次自然重名。
修复: 结构体补 db tag(id/name/created_at/updated_at), 注释写明"必须带 db tag"。
加固: 新增 service/workspace/sql_test.go —— **真实 sqlite** 集成测试(复用仓库迁移):
      自动 Default -> 创建 -> 重名拒绝 -> 切换 -> 逻辑删除 -> 跨用户隔离。
      这类测试专门拦 db tag/列名不匹配(与 session 的 sql_test 同一思路)。
顺带: data/conf/error.json 的 20000001 文案是占位符 "xxx fail" -> 改为 "service fail"
      (否则所有服务错误都会显示 "[20000001] xxx fail: ...")。
```

```yaml
验证:
  go test ./service/workspace -> 5 项全过(4 假 store + 1 真实 sqlite)
  go build/vet -> 通过 ; go test -count=1 ./backend/... -> 12 个包全过 ; gofmt 0
```

```yaml
连带修复: engine/database 的迁移测试仍断言旧的 idx_proxies_name_active,
          已改为断言 idx_proxies_workspace_name(000004 起唯一性口径变化),
```

## 10. 三条规则落地(单用户 / 列表不缓存 / 去掉默认工作区)

### ① 同一时间只有一个有效登录用户

```yaml
service/session:
  · 新增 enforceSingleUser(userID): 遍历会话缓存, 把"其它用户"的会话全部删除
  · 在 setCurrentUser(由 SignUp/SignIn/Resume 触发)时调用
  · 效果: 后登录的用户会顶掉先前的用户 -> 旧 token 的 Current/Resume 直接失效
测试: TestSingleActiveUser(先 alice 再 bob -> alice 的 token 失效, 当前用户为 bob)
```

### ② 工作区列表不缓存(修跨用户显示)

```yaml
根因(前端): store/workspace 里 items 是常驻内存副本, 且用 `loaded` 只加载一次;
          登录/登出/切换用户都不会重建它 -> 下一个用户看到的是上一个用户的列表。
修复:
  · store 去掉 loaded 标记: load() 每次都真实请求 List + Current
  · 新增 reset(): 清空 items/currentId
  · workspace-switcher 订阅 session 的 user.id: 变化时先 reset() 再 load();
    未登录时只 reset 不发请求(避免登录页弹 "requires a signed-in user")
```

### ③ 去掉默认工作区 + 无工作区时约束资源

```yaml
service/workspace:
  · List 不再自动创建 Default(也不自动选中)
  · 删除 EnsureDefault
service/proxy:
  · 新增 requireWorkspace(): 无当前工作区 -> "no workspace selected, create or pick one first"
  · Create / Update / Delete / Start / Stop 前置校验
  · List: 无工作区直接返回空页(Total 0), 不跨工作区/跨用户读
测试:
  · workspace: TestListDoesNotCreateDefault(空列表不写库) + 真实 sqlite 用例同步调整
  · proxy: 新增 TestRequiresWorkspace(创建/删除/启动被拒, 列表为空)
  · 既有 proxy 用例统一注入 currentWorkspace="w-test", 断言里补上收束参数
```

## 11. 工作区数量上限 + "配置不显示"的根因

### 根因(数据层缺一层)

```yaml
设置项要显示, 必须**三层同时存在**:
  ① data/default/settings.user.json        值(bottom 默认层)
  ② data/schema/settings.user.schema.json  键声明  <-- 你这次缺的就是这层
  ③ frontend/src/static/default/settings.json  UI 元数据(label/type/description)
现象: ①②③里只有 ①③ 有 general.workspace.limit -> 设置引擎只下发 schema 声明过的键,
      UI 拿不到该键的值 -> 行不渲染(看起来就是"没显示")。
修复: 补 schema(general.workspace.limit: number, minimum 1, maximum 1024, default 32)。
核对: default 19 键 = schema 19 键, limit 三层一致(default 32 / schema default 32 / UI type number)。
[!notice] 满足"只改 data/ 与 src/static/ 即可自动显示"的前提是: **schema 也算 data/**
          (它在 data/schema/ 下) —— 三处任一缺失都不会显示, 且不需要改任何 Go/TS 代码。
```

### 上限落地(服务层)

```yaml
service/workspace:
  · WithSettings(settings engine) 注入; 上限键 keyLimit = "general.workspace.limit"
  · limit(): 读生效值(兼容 int/int64/float64), 非法或缺省 -> 32
  · Create: 先查重名, 再统计未删除工作区数, 达到上限 -> "workspace limit reached (max N)"
  · 上限**实时生效**: 每次 Create 都读当前生效值(不需要重启)
bootstrap: 工作区服务构造时注入 settingsEngine
测试: TestCreateRespectsLimit(limit=2 -> 第三个被拒)
```

## 12. 服务构造统一约定(风格重构, 行为不变)

```yaml
约定(全部 service 一致):
  New() *Service                      # 只做基础初始化(时间/ID 生成器、缓存、handler 表、空 map 等),
                                      #   **不接收任何外部依赖, 返回源变量指针**
  WithXxx(value) *Service             # 每个 With 只设置一个外部依赖, 返回自身以支持链式调用
示例:
  组合根: serviceworkspace.New().WithStore(db).WithLogger(logger).
            WithSettings(settingsEngine).WithCurrentUser(sessionSrv.CurrentUserID)
  代理  : serviceproxy.New().WithStore(db).WithLogger(logger).WithData(data).
            WithRoot(root).WithCurrentUser(fn).WithCurrentWorkspace(fn).WithBridge(sender, receiver)

落地明细:
  · 删除 proxy 的 `type Option func(*Service)` 与所有 WithXxx(...) Option 形态, 统一为方法链
  · session: 依赖注入点前移 —— WithSettings 注入后立即 refreshConfig();
             WithEventBus 注入时订阅 settings.changed/reloaded(与原先 New 内订阅等价)
  · proxy: WithData / WithRoot 注入后各自触发一次 loadData()(幂等; WithRoot 用新根重解析 basedir)
  · settings/user/command/help/workspace: New 去掉形参, 外部依赖改由 WithStore/WithLogger/
             WithData/WithFields/WithDefaults/WithEventBus/WithSettings 注入
  · bootstrap 与全部测试调用点同步改为链式(测试里直接改字段的写法保持不变)

验证(仅风格变化):
  go build/vet -> 通过 ; go test -count=1 ./backend/... -> 12 个包全过 ; gofmt 0
  服务测试逐个通过(proxy 24 / session 11 / workspace 6 / settings / user / help 4 / command 3)
  残留检查: 无 `func With...(x) Option` 与 `type Option func(*Service)`
```

## 13. bootstrap 拆分: service.go + 依赖结构体 + 先取引擎再注册

```yaml
结构调整:
  bootstrap/bootstrap.go    # 只剩启动流程: 建运行时 -> 注册引擎 -> win/CLI -> 服务装配调用
  bootstrap/service.go      # **服务装配**: serviceDeps / serviceEngines / resolveServiceEngines / registerServices
  bootstrap/userconfig.go   # 用户目录同步(未变)

形参 -> 结构体:
  type serviceDeps struct { runtime *rtengine.Runtime; data fs.FS;
                            fields map[string]schemakit.Field; defaults map[string]any }
  · 以后新增装配输入只加字段, 调用方与函数签名都不动
  · 调用处: registerServices(serviceDeps{runtime: rt, data: data, fields: fields, defaults: defaults})

先取引擎, 再注册服务:
  resolveServiceEngines(rt) 一次性解析 settings / database / log / eventbus(必需) 与
  store.Rooter / bridge.node(可选), 任一必需项缺失 -> 立即返回明确错误;
  之后 registerServices 才开始按依赖顺序注册服务(settings -> user -> session -> workspace ->
  proxy -> help -> command), 不会出现"注册了一半才发现缺依赖"。
```
