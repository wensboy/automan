## 0. 定位与边界

```yaml
角色: 被桥接进程 (ws over uds 的客户端), 由 Go 侧桥接引擎拉起并连入其监听 socket
核心目录: backend/bridge/node/
技术选型: [ts, esbuild, pnpm, node]
不做:
  - 不做进程守护/重启 (属 Go 侧桥接引擎, v9/v12)
  - 不做 sock 的创建/清理 (属 Go 侧 peer, v12)
  - 不定义协议 (协议由两端共同遵守, 以 Go 侧为准: v12)
必须做到:
  - 与 Go 侧**逐字一致**的帧标准与信封 (§4), 否则对端无法解码
```

## 1. 技术选型与工具链


```yaml
不引入: ts-node / tsx / bundler 全家桶 / 框架 (保持最小)
说明: esbuild 负责产物, tsc 只做"类型是否正确"的门禁 —— 两者职责不重叠。
```

## 2. 目录与文件落位

```yaml
backend/bridge/node/
  package.json        # 只放 name/type/scripts/deps (不放大杂烩配置, 见 §3)
  pnpm-lock.yaml
  tsconfig.json       # 独立配置文件: 目标/lint 级别/moduleResolution
  esbuild.config.ts   # 独立配置文件: 入口/产物/目标平台/外部依赖
  src/
    index.ts          # 入口: 参数 -> 连接(含重连) -> 握手 -> 注册处理器 -> 消息循环
    bridge/           # 协议与传输 (与业务无关, 独立可测)
      protocol.ts     # Kind 常量 / ProtocolVersion / 类型定义
      frame.ts        # 帧标准编解码 (json + base64, 与 Go 侧逐字一致)
      envelope.ts     # 信封编解码 (kind/name/data)
      handshake.ts    # 握手 (客户端侧)
      client.ts       # 连接与重连 (uds + ws)
      loop.ts         # 单读循环 + 按 name 分派 + 发送
    service/          # 服务处理骨架 (业务)
      index.ts        # 注册业务处理器 (骨架先放 echo 用于联调)
  dist/               # 构建产物 (入库: 与源码一起提交, 见 §11)
```

```yaml
为什么把 bridge/ 与 service/ 分开: 协议/传输不掺业务, 业务不碰 socket 细节 —— 与 Go 侧
"peer 只管传输 / engine 只管业务" 的切分对称。
```

## 3. 风格规约落实 (逐条对应 readme)

| readme 要求 | 落实方式 |
|---|---|
| 配置独立, 避免 package.json 大杂烩 | esbuild 用 `esbuild.config.ts`, 类型用 `tsconfig.json`; `package.json` 只留 `name/type/scripts/dependencies` |
| ESM 导入导出 | `"type": "module"` + `import/export`; tsconfig `module: NodeNext` |
| 类型明确 | 协议类型集中在 `bridge/protocol.ts`; 跨模块边界必须显式类型; 不用 `any` 兜底 |
| 驼峰式命名 | 变量/函数/类型一律小驼峰/大驼峰; 文件名小写单词 (`frame.ts`/`handshake.ts`) |
| 面向过程 > 面向对象 | 只用函数 + 普通对象 + 闭包; **不写 class** (无继承/无 this) |
| 注释: 代码清晰性 >> 注释 | 只在关键决策处写注释 (如"为什么 base64"、"为什么不用内置 WebSocket") |

## 4. 与 Go 侧的协议契约 (逐字对齐)

### 4.1 帧标准 (ws 文本帧, 一行 json)

```json
{"id":"<string>","payload":"<base64>"}
```
```yaml
编码: base64(Buffer.from(payloadBytes).toString('base64'))
解码: Buffer.from(frame.payload ?? "", "base64")
为什么 base64: payload 是不透明字节 (业务负载), 传输不假设其格式 —— 与 Go 侧一致 (v12 §4.1)
```

### 4.2 信封 (payload 字节的 json, 业务标准)

```json
{"kind":"stream|event|error","name":"<string>","data":"<base64>"}
```
```yaml
data = base64(业务负载字节); 业务负载结构由 name 决定 (本项目为 json 对象)
注意: 与 Go 侧同样是"两层 base64"(帧层 + 信封 data 层), 不要省掉任何一层
```

### 4.3 握手 (会话首条消息, 进入分派前)

```yaml
请求: id="bridge.handshake", kind="stream", name="bridge.handshake"
      data = base64(json({daemon, codec, version, token?}))
应答: id/name 同上, kind="stream", data = base64(json({daemon, codec, version}))
失败: kind="error", data = base64(json("原因字符串"))
version: 2   (与 Go 侧 ProtocolVersion 对齐; 不一致时握手会被拒)
codec  : "json" (仅作断言: 两端必须一致, 不协商)
```

### 4.4 Kind 与语义

```yaml
stream : 1:n / n:n 关系的消息 (流的唯一含义)
event  : 单向通知 (无应答)
error  : 失败消息, business payload 为 json 字符串 (原因)
关联   : 由业务层用 id 约定 (1:1 时两端沿用同一个 id); 传输/引擎不做配对
```

### 4.5 连接与心跳

```yaml
sock   : 绝对路径, 由父进程注入 (argv --sock= 优先, 否则 env AUTOMAN_BRIDGE_SOCK)
心跳   : 父进程(服务端)按间隔发 ws Ping -> ws 自动回 Pong
         关键: 不得阻塞事件循环, 否则 Pong 发不出, 父进程在回归窗口后断开
关闭   : 父进程可能随时关闭; node 侧读循环结束时按 §5 重连
```

## 5. 运行时结构 (连接 / 重连 / 消息循环)

```yaml
启动:
  1. 解析参数 (--sock / env)
  2. connect: net.connect({path}) -> ws 升级 (自定义 createConnection, 不监听 TCP)
  3. 握手 (§4.3); 失败则记录并重连
  4. 注册业务处理器 (service/index.ts)
  5. 进入单读循环

读循环 (loop.ts):
  收帧 -> 解帧 (frame) -> 解信封 (envelope) -> 按 name 找处理器 -> 交给处理器
  未注册 name -> 丢弃 + 一行日志 (与 Go 侧一致: 不自动应答)
  连接结束/出错 -> 触发重连

发送 (loop.ts):
  send({ id, kind, name, data }) -> 信封编码 -> 帧编码 -> ws.send(文本帧)
  data 由业务给出 (对象 -> json -> 字节); 编码失败立即报错, 不静默

重连 (client.ts):
  指数退避 (基数/上限/最大次数可配, 缺省 200ms -> 5s, 无上限)
  重连成功后重新握手; 未完成消息的归宿由业务层决定 (与 v12 §5 一致)
```

## 6. 启动参数与父进程拉起

```yaml
父进程 (Go 侧桥接引擎) 需要:
  - WithCommand("node", "backend/bridge/node/dist/index.js")
  - 注入 sock: argv "--sock=<绝对路径>" 或 env AUTOMAN_BRIDGE_SOCK
  - 可选 WithDir / WithEnv / WithOutput (继承 stdout/stderr)
实现备注 (Go 侧需要一处小改动):
  当前引擎的 args/env 是静态的, 而 sock 路径在 Start 时才算出 ->
  启动子进程时把 AUTOMAN_BRIDGE_SOCK 注入 env (一行), node 侧优先读 argv。
```

## 7. 服务处理骨架 (实现步骤的第一步)

```yaml
目标: 先跑通链路, 再谈业务
src/service/index.ts 先注册两个处理器:
  - "node.echo" : 把收到的业务负载原样回一条 (id 沿用, kind=stream) —— 用于端到端自检
  - "node.ping" : 回一条 { pong: Date.now() } —— 用于确认双向连通与延迟
约定:
  - 处理器是普通函数 (process-oriented), 输入 Packet, 输出"要发的消息"或直接调用 send
  - 处理器内不得阻塞 (长任务需自行分片/异步), 以免影响心跳与其它消息
```

## 8. 构建与运行 (esbuild -> tsc -> run)

```yaml
scripts (package.json 内只放脚本, 配置放独立文件):
```

## 9. 日志与错误

```yaml
日志: 现阶段直接写 stdout/stderr (父进程继承, 可在 Go 侧终端看到)
      需要归集时再走协议 (kind=event, name="node.log") —— 见 §11
错误: 连接/握手/解码失败 -> 一行 stderr + 继续重连 (不直接退出)
      业务处理器抛错 -> 记录 + 回一条 kind="error" (id 沿用), 让对端知道失败
```

## 10. 端到端联调方式

```yaml
1. Go 侧: 桥接引擎以 command 方式拉起 node (WithCommand + sock 注入)
2. Go 侧: eng.Send({id, kind:"stream", name:"node.echo", data}) -> node 回同 id 消息
3. 反向: node init 后主动发一条 {name:"node.ready"} (可选) 让父进程确认就绪
4. 异常: 杀掉 node -> 父进程收到断开事件; 重启后重连 + 重新握手
5. 心跳: 父进程按间隔 Ping, node 侧自动 Pong; 观察回归窗口内是否稳定
```

## 11. 待澄清项

```yaml
- dist/ 是否入库: 你之前提到"包含完整源代码和构建后的产物"; 若入库, 需在 .gitignore 里放开 [不入库, 构建时打包]

- node 侧是否也需要主动探活 (自 Ping 检测父进程假死)? 当前依赖父进程 Ping + 连接断开 [需要考虑]

- 业务负载是否统一 json, 还是允许二进制 (当前信封 data 是 base64, 天然支持二进制) [允许二进制, 当前考虑json处理]
- node 侧是否需要"就绪"通知 (node.ready) 让父进程确认初始化完成 [需要]
- 重连参数 (基数/上限/次数) 放在 argv/env 还是代码缺省 [考虑放在 argv]
```
