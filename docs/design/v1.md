# Automan 设计 v1 · Step 1

> 状态: 设计草案 (Design, 不含实现)
> 依据: `docs/spec.md`
> 范围: 只做方案思考, 不落代码. 聚焦启动链路 / 引擎编排 / domain / 上下文 / 组件接入.

---

## 0. 目标

把当前"入口硬编码 + 单文件窗口启动"的骨架, 收敛为一条**可编排、可扩展、可多形态启动**的全链路:

1. 应用信息从代码里移出, 落到配置, 由 config 引擎统一加载.
2. domain 层引入**全链路上下文**, 用类型化解耦参数传递.
3. 把 **web 应用自身也视为一个 engine**, 与其它引擎统一注册、统一生命周期.
4. 由 service 编排引擎, 在 api 层按形态暴露 (web 绑定 / cli 命令).

一句话: **配置驱动 → 上下文贯穿 → 引擎编排 → 多 api 暴露**.

---

## 1. 核心观点

### 观点 A — 应用信息由 config 引擎统一加载

- 现状: `application.json` 已存在 (`name/description/version`), 但真正的应用信息硬编码在 `main.go` 的 `application.Options` 与窗口参数里, 两者割裂.
- 目标: 应用元信息**唯一事实来源**为 `src/data/conf/application.json`; 启动时先由 config 引擎读取并注入上下文, 后续所有消费者 (web 窗口标题、版本展示、日志前缀、api 元数据) 都从上下文取, 不再各自硬编码.

```yaml
# src/data/conf/application.json (现状保持, 语义收敛为"应用元信息")
name: automan
description: An automated application for environmental agents.
version: 0.0.1
```

### 观点 B — domain 层全链路上下文

- 所有跨层函数以 `ctx` 作为统一入口载体, 承载三件事:
  - **启动态**: 生命周期信号 (Done/Err)、应用信息、运行模式.
  - **数据传递**: 跨引擎/服务的中间数据 (避免层层加固定入参).
  - **处理传递**: 回调/handler/事件订阅的挂载点 (避免函数签名被写死).
- 关键手法: 上下文用**泛型 Key**做类型化存取, 新增数据 = 新增 Key, **不改函数签名**. 解决"入参类型固定导致修改困难".

### 观点 C — web 也是 engine

- 把 wails 应用 (窗口/资源服务/前端绑定) 封装为 `web engine`, 纳入同一注册表与生命周期.
- 收益: 启动窗口不再散落在 `main.go`, 而成为被 service/cli 编排的一环; 桌面模式与 server 模式 (headless) 只是同一个 engine 的不同配置.

## 2. 程序启动链路

### 2.1 现状 (待重构)

```12:43:src/main.go
app := application.New(application.Options{
    Name:        "automan",
    ...
    Services:    []application.Service{},
    ...
})
app.Window.NewWithOptions(...)
err := app.Run()
```

问题: 元信息硬编码、无配置引擎、无引擎注册、无 service 编排、无 cli 入口.

### 2.2 目标链路

```yaml
阶段:
  1_引导(bootstrap):
    输入: 进程启动 (desktop / cli)
    动作: 创建根 Context, 解析启动模式
    产物: ctx(根)
  2_配置(config engine):
    动作: 读取 data/conf/application.json -> AppInfo 注入 ctx
    产物: ctx.App() 可用
  3_注册(registry):
    动作: 声明式收集 engines (显式清单, 顺序即依赖序)
    产物: 有序 engine 列表
  4_启动(lifecycle):
    动作: 逐个 Init -> Start, 失败则逆序回滚
    产物: 引擎就绪
  5_编排(service):
    动作: service 依赖引擎, 组装业务能力
    产物: service 实例
  6_暴露(api):
    动作: 按形态暴露
      - web: api/web 注册为 wails service (前端绑定) + web engine 建窗
      - cli: api/cli 解析命令 (如 `automan window` 启动窗口)
    产物: 可交互入口
  7_运行(run):
    动作: web engine Run() 阻塞 / cli 执行后退出
  8_退出(shutdown):
    动作: 逆序 Stop engines, cancel ctx
```

### 2.3 时序 (desktop 窗口模式)

```
main
 └─ bootstrap               构建根 ctx, 判定模式(desktop)
     └─ registry.Start
         ├─ config engine  : 读 application.json -> ctx.Set(AppKey, AppInfo)
         ├─ ...其它 engine : Init/Start, 从 ctx 取所需
         └─ web engine     : 用 ctx.App() 建 wails Options + Window
     └─ service.Assemble   注入引擎, 组装业务
     └─ api.Expose
         ├─ api/web  : wails Service 绑定(前端 call 目标)
         └─ api/cli  : 命令表(window/execute/...)
     └─ web.Run             app.Run() 阻塞
     └─ shutdown            ctx cancel -> 逆序 Stop
```

### 2.4 阶段职责边界

```yaml
bootstrap: 只做"定调", 不碰业务, 不碰具体引擎
config_engine: 只负责"读配置 -> 结构化", 不负责消费
registry: 只负责"注册 + 顺序 + 回滚", 不理解引擎语义
service: 只负责"编排", 不感知 wails/cli 载体细节
api: 只负责"暴露形态适配", 不做业务决策
```

## 3. 引擎 + Service 编排

### 3.1 分层职责 (对齐 spec l2)

```yaml
domain  : 能力接口 + 默认实现, 领域之间互不依赖
engine  : 实现 domain 能力的具体引擎 (适配外部/系统)
service : 编排引擎, 对外提供完整服务
api     : 对外暴露 (web / cli / sdk)
```

依赖方向单向: `api -> service -> engine -> domain`; `domain` 不反向依赖任何层.

### 3.2 Engine 契约 (置于 domain)

引擎是"可注册、有生命周期"的领域实现, 契约宜由 domain 定义 (能力接口).

```go
// 示意 (非实现)
type Engine interface {
    Name() string
    Init(ctx context.Context) error   // 只做依赖装配/校验, 不启动
    Start(ctx context.Context) error  // 真正开始工作
    Stop(ctx context.Context) error   // 释放资源
}
```

设计要点:
- `Init` 与 `Start` 分离: 便于"全部 Init 成功后再统一 Start", 降低半启动状态.
- 契约不感知业务, 只表达生命周期.

### 3.3 Registry 与生命周期

```go
// 示意
type Registry interface {
    Register(e Engine)              // 显式注册, 顺序即依赖序
    Start(ctx context.Context) error  // 正序 Init -> Start
    Stop(ctx context.Context) error   // 逆序 Stop
}
```

规则:
- **显式清单**: 引擎列表写死在 bootstrap 一处 (spec 原则"显式行为优于隐式"), 便于阅读全貌.
- **顺序即依赖**: `config` 最先 (产出 AppInfo), `web` 最后 (依赖全部就绪).
- **失败回滚**: 任一 `Start` 失败 → 逆序 `Stop` 已启动者; 未启动者不 Stop.

### 3.4 Service 编排

- service 是**业务语义单元**, 组合多个引擎完成一件事 (如"启动一次自动化探索").
- service 只依赖 domain 接口 (拿引擎能力), 不 new 具体引擎 (具体实例在 bootstrap 装配).
- 装配方式: bootstrap 建好引擎实例 → 注入 service 构造. 上下文作为运行时参数传入, 而非装配期字段.

```yaml
# 示意: service 与引擎关系
service:
  explore:
    engines: [config, browser, agent]
    exposes: [Run(ctx), Pause(ctx), Status(ctx)]
```

### 3.5 API 暴露

- **api/web**: 作为 wails `application.Service` 注册, 前端通过生成的 bindings 调用 (`Call.ByID`). 只做入参适配 + 调 service + 结果整形.
- **api/cli**: 命令表, 暴露**完整执行接口**, 例如:
  - `automan window` → 走同一 bootstrap, 触发 web engine 建窗并 Run.
  - `automan run <task>` → 走 service 编排, 无窗口执行 (headless / server 模式).
- 两者共用同一条启动链路, 差异仅在 bootstrap 的"模式判定"与最终暴露形态.

### 3.6 web 作为 engine

```yaml
web_engine:
  职责:
    - 持有 wails application 实例
    - 用 ctx.App() 构建 application.Options / 窗口参数
    - 注册 wails Services (来自 api/web)
    - Start: 建窗; Run: 阻塞事件循环; Stop: 优雅退出
  模式:
    desktop: 建窗 + Run 阻塞
    server : 仅 HTTP/资源服务, headless (对应 Taskfile build:server)
  依赖:
    - ctx.App() : 名称/描述/版本
    - api/web  : 待注册的 service 列表
```

关键: 窗口参数 (Title/Width/Height/背景色) 与 `application.Options.Name/Description` 都应来自 `AppInfo`, 消除 `main.go` 硬编码.

## 4. domain 设计

### 4.1 分层与依赖方向

```yaml
domain:
  context: 上下文契约 + 默认实现 (贯穿全链路的横切能力)
  engine : Engine/Registry 契约 (+ 默认 Registry 实现)
  config : 配置读取能力契约
  <domain>: 业务领域能力 (agent/browser/... step 后续展开)
原则:
  - 领域之间互不依赖
  - domain 不 import engine/service/api
  - 数据用泛型 Key 传递, 而非跨领域 struct 直接引用
```

> 说明: 上下文与引擎契约都是"被所有层共同依赖"的横切能力, 放 domain 可避免循环依赖.
> domain 之间的解耦 (spec: "无相互依赖") 正是靠**泛型 Key + 上下文**实现, 而非相互 import.

### 4.2 上下文 (Context)

上下文是 step1 的核心, 承载: 生命周期、应用信息、数据通道、日志/事件挂载点.

```go
// 示意 (非实现) — 拆分为窄接口, 遵循接口隔离 (SOLID-I)
type Context interface {
    Lifecycle // Done() <-chan struct{}; Err() error; Cancel()
    Data      // Get/Set 泛型 Key; App() AppInfo
    Meta      // Mode() Mode (desktop|server|cli); Logger(); Emitter()
}
```

设计意图:
- **不写死入参**: 函数只收 `ctx`, 通过 Key 读取自己需要的部分 → 新增依赖不改签名.
- **处理传递**: `Emitter` 提供事件挂载, 让引擎/服务以"注册回调"方式协作, 替代硬编码调用链.
- **单一入口**: 全链路共用一个 ctx, 生命周期统一收敛 (根 ctx cancel = 全局停机信号).

### 4.3 类型化 Key (解耦核心)

```go
// 示意
type Key[T any] struct{ name string }

func NewKey[T any](name string) Key[T]
func Get[T any](ctx Context, k Key[T]) (T, bool)
func Set[T any](ctx Context, k Key[T], v T)

var AppKey = NewKey[AppInfo]("app")   // 由 config engine 写入
```

价值:
- 类型安全 (`Get[AppInfo]` 编译期校验) 同时 domain 之间零 import.
- 新增跨层数据 = 新增一个 Key, **零改动既有函数签名**.

### 4.4 domain 清单 (step1 只定框架)

```yaml
先定(框架):
  - context : Context/Key/AppInfo/Mode
  - engine  : Engine/Registry
  - config  : Loader (读 data/conf/*.json)
后定(step 后续, 占位不实现):
  - browser / agent / storage / notify ...
```

> 依 spec "不做代码预留": step1 只落框架三件套, 业务领域留白, 不提前写空接口.

## 5. 考虑要点

### 5.1 依赖与循环
- 唯一可能成环的是"多个领域都要拿 AppInfo/日志" → 一律走 `ctx` Key, 不做领域间 import.
- engine 只依赖 domain 接口; 具体注入在 bootstrap, 保持 DIP.

### 5.2 配置加载策略
- 生产: `data` 以 `//go:embed` 打包, config 引擎从 `embed.FS` 读 `conf/application.json`.
- 开发: 允许外部文件覆盖 (便于改配置不重编). 加载优先级需显式定义 (外部 > 内嵌).
- 失败策略: 应用元信息缺失属**必需项**, 加载失败应终止启动并报明确错误 (不做兜底默认值, 避免隐蔽问题).

### 5.3 生命周期与失败回滚
- 顺序: 注册序 `Init → Start`; 停机逆序 `Stop`.
- 半启动: 任一失败 → 逆序回滚已启动引擎; 保证无资源泄漏.
- ctx 是停机唯一信号: 根 ctx cancel → 各引擎响应.

### 5.4 并发与数据一致性
- 上下文数据需并发安全 (引擎可能并发读写): 内部加锁或要求"启动期单线程写入, 运行期只读".
- 明确 `Set` 的可见时机, 避免运行期竞态.

### 5.5 运行模式
- 一进程一模式: `desktop`(建窗阻塞) / `server`(headless) / `cli`(执行即退).
- 模式在 bootstrap 判定一次, 写入 ctx; 引擎据 `ctx.Mode()` 决定行为, 而非各自判断环境.
- 对齐现有 `Taskfile.yml` 的 `run` / `run:server` 目标.

### 5.6 观测与错误
- 日志: 引擎/service 统一从 ctx 取 logger, 带应用名/版本前缀.
- 错误: 引擎启动错误向上冒泡到 bootstrap, 统一格式化 (含引擎名), 便于定位.

### 5.7 待澄清项
- `go.mod` 模块名仍为占位 `changeme`, 直接影响 wails 绑定路径 (`frontend/bindings/changeme`) 与 import 路径; 是否在 step2 改为 `automan`?
- 非业务 string (如窗口默认宽高/背景色) 应入 `application.json` 还是保留代码常量? (spec: 非业务 string 不过度配置)

## 6. 接入其他组件

```yaml
wails_v3:
  接入点: web engine + api/web
  方式: application.New(Options) 取自 ctx.App(); Service 用 application.NewService 注册
事件总线:
  接入点: ctx.Emitter()
  方式: 引擎/服务 publish-subscribe, 替代硬编码调用 (解耦观点 B 的"处理传递")
日志:
  接入点: ctx.Logger()
  方式: 统一格式与级别, 贯穿启动链路
持久化:
  接入点: domain/storage (step 后续)
  方式: data/<domain>/ 存放领域数据 (对齐 spec l3)
前端:
  接入点: frontend + 生成的 bindings
  方式: 只依赖 api/web 暴露的方法签名, 后端内部布局对前端透明
CLI:
  接入点: api/cli
  方式: 复用同一 bootstrap, 暴露 window/run 等完整执行接口
```

```yaml
    api:

    domain/
      context/          : Context + Key + AppInfo + Mode
      engine/           : Engine/Registry 契约
      config/           : 配置读取契约

    conf/application.json
```
